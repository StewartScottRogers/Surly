=== STOMP Logins over TLS from an Agent

==== Problem

Your Simple Text Oriented Messaging Protocol (STOMP) client logs in with a user name and password, and the password must not cross the network in clear. You want an artificial intelligence (AI) agent to see the login refused over plain STOMP, accepted over Transport Layer Security (TLS), and a wrong password told from no password at all, with Model Context Protocol (MCP) tool calls and no shell.

==== Solution

The program is the agent's side: it starts `surl-mcp` and `curl-mcp`, calls `start_server` for a STOMP broker with one account and one queue, sends a message with `curl-mcp`{apos}s `curl` tool, and asks the broker what the queue holds with `browse_queue`. ==== Discussion

`StdioClientTransport` starts each host by name from `PATH`, and `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine both to the folder the program runs in, which is where `server.pem` and `server.key` are. The arguments after `--` pick the scenario: the scheme and the login, then optional words.

`start_server` takes `listen_urls`, here `stomps://127.0.0.1:0`, port 0 for a free one, and answers a `server_id` with `bound_urls`. The rest goes in `arguments`, `surl`{apos}s own options one list item each: `--user alice:s3cret` is the account, `--queue jobs` a queue that exists from the start, and `--cert` and `--key` the certificate and its private key. `--allow-plaintext-auth` is added in one case only; it loosens security (<<surl-readme>>).

`curl-mcp`{apos}s `transfer` tool has no field for a login or a certificate to trust, so the agent uses the `curl` tool, which takes `curl`{apos}s arguments as a list with no shell and no quoting: `-u` is the login, `--cacert server.pem` the certificate to trust, `-d hello` the message, sent to the destination in the URL path, `/queue/jobs`, and `-sS` hides the progress meter but keeps the error text (<<curl-readme>>). The answer is text holding JSON; the program reads `exitCode` and `standardError`, which is null when empty.

A STOMP client logs in in its first frame, `CONNECT`, and the server answers `CONNECTED` or an `ERROR` frame (<<stomp12>>). The right password over `stomps` is accepted: `curl` exits `0`. A send is not acknowledged, so before it looks, the program waits with `wait_for_event` for the end of the client's exchange, which the broker records after applying the message; `browse_queue` then shows one message, `hello`, without taking it. A wrong password, a user name with no account and no login at all are each refused: `curl` exits `67` with `STOMP server sent ERROR: Authentication failed`, the same words for all three, and the queue is empty. Plain `stomp` refuses the right password in the same words, because the server does not check a password that crosses the network readable; it is accepted once `--allow-plaintext-auth` is given. Without `--cacert`, the `curl` tool exits `60`: it does not trust a certificate that signed itself and never sends the login (<<rfc8446>>).
