=== Logging In to Socket.IO

==== Problem

Your Socket.IO client sends a login when it joins. You want the join refused without it, refused over plain Socket.IO, and accepted over Transport Layer Security (TLS).

==== Solution

Serve Socket.IO with a certificate and give it an account with `--user`; `curl` logs in with `-u` and trusts the certificate with `--cacert`. The `openssl` line makes the certificate and key. The `curl` command joins, emits one event and gets it back:

==== Discussion

A Socket.IO client logs in in the packet that joins a namespace: the login travels in the request to join, and the server answers with a refusal or a welcome (<<socketio-protocol>>). `socketios://` is the same server inside TLS, negotiated before any of that is sent (<<rfc8446>>). Nothing is loosened: `--user alice:s3cret` is the account, `--cert server.pem` the certificate and `--key server.key` its private key. On the `curl` side, `-u alice:s3cret` is the login and `--cacert server.pem` the certificate to trust; `-d` emits one event, written as a JSON array whose first item is the event name, and `surl` sends it back to its sender, which `curl` writes as a line. A Socket.IO session has no end of its own, so `-m 3` stops `curl` after three seconds, exit `28`, with the event already written, and `-s` hides the progress meter while `-S` still prints an error (<<curl-readme>>). Without `--cacert`, `curl` does not trust a certificate that signed itself, never sends the login and exits `60`.

Every refusal is the same: `curl` exits `22`, writes nothing, and prints `Socket.IO server refused namespace /: {"message":"Not authorized"}`. A wrong password, a user name `surl` has no account for and a client with no login at all are indistinguishable, which gives a client nothing to learn from. Plain `socketio://` refuses the right password in the same words: the password would cross the network readable, so `surl` does not check it. `--allow-plaintext-auth` would take it and loosens security (<<surl-readme>>); this recipe shows it working on a third server so that the default can be seen as a choice.

A token account, started as `--user :tok123`, is meant to take a login that is only a token. In this build it does not: the join is refused with the same `Not authorized` even with the right token, a fault that is fixed in the Surl source and not yet in this build (Curl and Surl backlog item BL-1589). The last case records the refusal as it is today; once the build carries the fix, that case is the one to replace with an accepted login.
