=== Requiring MCP Logins in C#

==== Problem

Your Model Context Protocol server must not hand its tools to anyone who connects, and you want a .NET test to show that the tools are listed only for a client that logs in over Transport Layer Security (TLS), and refused without a login.

==== Solution

Host `mcps` with `Surl.Api`, your certificate and a token account, and ask for the tool list with `Curl.Api`, trusting the certificate and sending the token; the argument picks what the client does differently:

==== Discussion

A Model Context Protocol (MCP) server over Hypertext Transfer Protocol (HTTP) takes OAuth 2.1 Bearer tokens as its logins, sent in an `Authorization: Bearer` header with every request (<<mcp-spec>>, <<rfc6750>>). `SurlServerOptions` describes the server as `surl`{apos}s command line would (<<surl-readme>>). The listen URL `mcps://127.0.0.1:0` is MCP inside TLS from the first byte, on a free port (<<rfc8446>>); `CertificateFile` and `KeyFile` are `--cert` and `--key`, the files the `setup` step made with `openssl`. `Accounts` takes each `SurlAccount`; one whose user name is empty makes its password a Bearer token, as `--user :agent-token-1` does. `Files` holds the file the tools read. `SurlServer.StartAsync` returns once the listener is bound, and `BoundUrl` names it.

On the client side, `CurlClientOptions` carries two things. `Tls` holds a `CurlTlsPeerOptions` whose `CertificateAuthorityBlob` is the certificate's bytes, so `Curl.Api` trusts it as its own authority, as `--cacert` does. `Authentication` holds a `CurlAuthenticationOptions` whose `XOAuth2Bearer` is the token, sent as `--oauth2-bearer` sends it (<<curl-readme>>). A request to `/mcp` with no body opens the session and lists the tools, one line each: name, tab, description (<<curl-protocols>>). `Curl.Api` 0.2.0 sends no `tools/call` (a body is ignored), so this test checks the gate on the list; the console recipe also calls a tool through it.

Every refusal is a `CurlException` thrown by `SendAsync`, and its `Code` is the exit code `curl` would give. No token: `surl` answers `401`, `LoginDenied`, `67`. Another token: the same. A user name and password, even those of the account `alice`, is not a login the MCP endpoint takes: `400`, `WeirdServerReply`, `8`, so a client cannot fall back to a password. Without the certificate as an authority, the handshake fails first, `PeerFailedVerification`, `60`, and the token is never sent.

A server that cannot start throws instead: `mcps` with no `CertificateFile` (nor `SelfSigned`) makes `StartAsync` throw `SurlServerStartException`, whose `ExitCode` is `CertificateProblem`, `58`, and whose message is `surl`{apos}s own.

Over plain `mcp://`, the right token is refused without being checked, `401`, `67`: a token sent in clear is one anyone on the path can read and reuse. `AllowPlaintextAuthentication`, which is `--allow-plaintext-auth`, turns that off, and the same token is checked and accepted. `AllowAnonymous`, which is `--allow-anonymous`, lists the tools to a client with no token at all, account or not. Both are for a test that wants to skip the login; a test of the login itself, like this one, leaves them off.
