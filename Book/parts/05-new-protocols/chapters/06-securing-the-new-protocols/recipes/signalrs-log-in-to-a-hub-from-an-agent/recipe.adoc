=== SignalR Hub Logins from an Agent

==== Problem

Your SignalR client logs in to its hub. You want an artificial intelligence (AI) agent to see the negotiate refused without a login, and accepted with one over Transport Layer Security (TLS), with Model Context Protocol (MCP) tool calls and no shell.

==== Solution

The program is the agent's side: it starts `surl-mcp` and `curl-mcp`, calls `start_server` for a hub with one account, and logs in and calls the `Echo` method with `curl-mcp`{apos}s `curl` tool. The certificate and key come from the `openssl` line, run first:

==== Discussion

`StdioClientTransport` starts each host by name from `PATH`, and `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine both to the folder the program runs in, which is where `server.pem` and `server.key` are. The arguments after `--` pick the scenario: the scheme and the login, then optional words.

`start_server` takes `listen_urls`, here `signalrs://127.0.0.1:0`, port 0 for a free one, and answers a `server_id` with `bound_urls`. The rest goes in `arguments`, `surl`{apos}s own options one list item each: `--user alice:s3cret` is the account, `--cert` and `--key` the certificate and its private key. `--allow-plaintext-auth` is added in one case only; it loosens security (<<surl-readme>>).

`curl-mcp`{apos}s `transfer` tool has no field for a login, a certificate to trust or a message to send, so the agent uses the `curl` tool, which takes `curl`{apos}s arguments as a list with no shell and no quoting: `-u` is the login, `--cacert server.pem` the certificate to trust, `-d` the one message sent after the handshake, an invocation of `Echo` whose result `curl` writes alone, and `-sS` hides the progress meter but keeps the error text (<<curl-readme>>). The answer is text holding JSON; the program reads `exitCode`, `standardOutput` and `standardError`, either of which is null when empty.

A SignalR client starts with an HTTP request, `negotiate`, and the login is judged there (<<signalr-hub-protocol>>). The right password over `signalrs` is accepted: `curl` exits `0` and writes `"hi"`. A wrong password, a user name with no account and no login at all are each refused with HTTP `401`, exit `22` and `The negotiate request failed with HTTP status 401.`; the status does not say which of the three it was. Plain `signalr` answers differently: the right password is refused `403`, forbidden, because the server does not check a password that crosses the network readable, while a client with no login is still `401`. The same login is accepted once `--allow-plaintext-auth` is given. Without `--cacert`, the `curl` tool exits `60`: it does not trust a certificate that signed itself and never sends the login (<<rfc8446>>).
