=== Mapping Topics between Protocols from an Agent

==== Problem

Two teams named the same stream differently: the orders service publishes on the NATS subject `orders.created`, and the shop reads the Message Queuing Telemetry Transport (MQTT) topic `shop/orders/new`. You want an agent, driving `surl-mcp` and `curl-mcp`, to start a server whose topic map makes one name mean the other, both ways, and show that it does.

==== Solution

The program starts both hosts and a server for NATS and MQTT with one `--topic-map`, publishes with the `curl` tool over NATS, waits for the bus to keep the message, and reads it back as the MQTT topic:

==== Discussion

`start_server` takes the listen URLs, here a `nats://` and an `mqtt://` URL on port 0, and in `arguments` `surl`{apos}s own options (<<surl-readme>>); it answers a `server_id` and the `bound_urls` in the order given. Both listeners share one message bus. `--allow-anonymous` lets clients in with no login; `--topic "#;retain"` keeps the last message on every topic. `--topic-map nats:orders.created=mqtt:shop/orders/new` says that the NATS name on the left means the topic the MQTT name on the right has, each a scheme, a colon and a name in that scheme{apos}s own spelling.

The `curl` tool runs `curl`{apos}s own arguments and answers `exitCode`, `standardOutput` and `standardError` as JavaScript Object Notation (JSON). `-d paid` to `nats://` with the subject as the path is a publish (<<nats-protocol>>); `-s` keeps the progress meter out and `-S` keeps an error in. A NATS publish is not acknowledged, so the program calls `wait_for_event` for a `store_changed` event of the `bus` store named `shop/orders/new`, bounded at ten seconds, before it reads. `read_retained_message` reads the bus by the MQTT name and answers the `text` kept: `paid`. The `curl` tool{apos}s MQTT subscriber, no `-d` and the topic as the path (<<mqtt311>>), is sent the same message and writes the topic{apos}s length in two bytes, the topic and the payload.

The other way needs a NATS subscriber in place first, since NATS keeps nothing for a late one. The program calls the `curl` tool for `orders.created?count=1`, which ends after one message, with `-m 10` as its bound, and does not await the call; `curl-mcp` runs it beside the next calls. It then publishes `shipped` over MQTT to `shop/orders/new` every half second until the subscriber{apos}s call returns, at most twenty times. The subscriber writes `shipped` and a newline.

With no map, `surl` turns the subject into a topic by swapping dots for slashes: the publish is kept on `orders/created`, and `read_retained_message` of `shop/orders/new` answers `retained` false. A map joins names, not filters, so `nats:orders.*` makes `start_server` a tool error whose `exit_code` is `2` and whose first line says `not a valid name for nats`. Without `--allow-anonymous` the publish with no login is refused, `-ERR 'Authorization Violation'`, and the `curl` tool answers `exitCode` `67`: `surl` asks for a login by default.
