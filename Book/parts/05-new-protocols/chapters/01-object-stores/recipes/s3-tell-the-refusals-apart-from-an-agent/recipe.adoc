=== Telling S3 Refusals Apart from an Agent

==== Problem

Your client must explain why S3 said no: unsigned, unknown key, bad signature. You want your agent to produce each refusal on purpose, name it, and read from the server what it judged, with anonymous reads allowed only when you say so.

==== Solution

An agent starts two S3 servers with `surl-mcp`, one with an account and nothing loosened and one that also allows anonymous callers, sends `curl-mcp` the requests that the first refuses for three reasons, and reads the logins the server judged:

==== Discussion

Amazon Simple Storage Service (S3) says why it refused a request in the error body, in a short code (<<aws-s3-api>>), and `surl` answers as S3 does. Every request must be signed with AWS Signature Version 4, the scheme S3 uses, by an account: `--user AKIAIOSFODNN7EXAMPLE:s3cret` gives `surl` an access key ID and its secret access key, and `curl -u` with a pair makes `curl` sign with it. The recipe <<s3-tell-the-refusals-apart>> does the same on a console.

`start_server` of `surl-mcp` starts a server. `listen_urls` is `s3://127.0.0.1:0`, where port `0` takes a free port that `bound_urls` reports, and `arguments` are `surl`{apos}s own options: `--cert server.pem` and `--key server.key`, because S3 is spoken over Transport Layer Security from the first byte (<<rfc8446>>) and the listener needs a certificate, `--user` for the account, and for the second server `--allow-anonymous` and `--allow-uploads` (<<surl-readme>>). Both files are in the folder `SURL_MCP_ROOT` names, which the `openssl` line filled. `files` is the content in memory, where `photos/hello.txt` is the object `hello.txt` in the bucket `photos`. The answer carries a `server_id`, which later calls name.

`curl` of `curl-mcp` runs `curl`{apos}s own arguments, in the folder `CURL_MCP_ROOT` names, and answers in text as JSON: `exitCode`, and `standardOutput` and `standardError`, each an object whose `content` is the text. `--connect-to ::127.0.0.1:<port>` sends the connection to the server whatever bucket host name the URL gives, as `curl` would send it to `photos.s3.us-east-1.amazonaws.com`, and `--cacert server.pem` trusts the certificate. An error is exit `22` with `S3 returned error 403: AccessDenied: Access Denied` in `standardError`, and the agent reads the status and the error name out of it; that is how it explains why S3 said no.

Three codes are about the login, and each is a different mistake. A request with no `-u` is unsigned, and the answer is `403 AccessDenied`. A request signed with an access key the server does not hold is `403 InvalidAccessKeyId`: the account is the mistake. A request signed with the right access key and the wrong secret is `403 SignatureDoesNotMatch`: the account is known, and the signature the server worked out for it is not the one it was sent.

`AccessDenied` is also the answer to a request that is signed correctly and not allowed. The first server has neither `--allow-uploads` nor `--list-directories`, so a signed put, with `-T note.txt` from the agent{apos}s folder, and a signed listing, `s3://photos/`, are each `403 AccessDenied`, in the same words an unsigned get gets, `Access Denied`. The code and the message alone do not tell them apart; what the agent sent does, and so does the server. `get_events` of `surl-mcp`, with `kinds` set to `login_judged`, lists the logins the server judged, each with the `account` it named and whether it was accepted: the unknown key refused, the right key with the wrong secret refused, and the right key accepted. The unsigned request is not among them, because it named no account to judge. A signed request that is answered `AccessDenied` is in the list, accepted, which is how an agent knows the key is not the trouble. A key with no object is `404 NoSuchKey` and a bucket that is not in the store is `404 NoSuchBucket`; both come to a request that was signed and allowed, and an agent that treats every `403` and `404` alike will retry the wrong thing.

Anonymous reads are off until you say so. On the second server, `--allow-anonymous` serves an unsigned get, so a test can read with no keys, and so can anyone who can reach the listener: it is for tests only, and `surl` warns on every start while it is on (<<surl-readme>>). It loosens nothing else. An unsigned put is still `403 AccessDenied`, `--allow-uploads` given, and a request that does carry a login is still judged, so an unknown access key is `InvalidAccessKeyId` and a wrong secret `SignatureDoesNotMatch` on that server too.
