=== Mapping a Bucket to a Folder

==== Problem

Your test data sits in a folder whose name is not the bucket name your app uses. You want the bucket mapped onto that folder and its files served as objects.

==== Solution

==== Discussion

In the S3 server, each top-level folder of the store is a bucket named for the folder, and the path under it is the key (<<aws-s3-api>>, <<surl-readme>>). That fits a store built for the test, but not data that exists already: your app asks for the bucket `pics` and the folder is `gallery`. `--bucket <name>=<path>` maps a bucket name onto a path in the store, so the bucket `pics` is the folder `gallery` of `--directory data`, and `sunset.txt` in it is the key `sunset.txt`. The path is a path in the store, not on the disk: it starts with a slash and is read from the root that `--directory` names, so `/gallery` is `data/gallery`. In Git Bash on Windows, a word that holds `=/` is rewritten as a path before `surl` sees it; set `MSYS_NO_PATHCONV=1` for the shell first.

The mapping adds a name and removes none. The folder `gallery` is still a bucket under its own name and reads the same file, and a folder `--bucket` does not mention, `other` here, is a bucket under its own. A bucket that is neither mapped nor a folder is `404 NoSuchBucket`. A mapping is read both ways: listing `s3://pics/` lists the folder, and a signed put into the bucket writes a file into `data/gallery`, which the second URL of the last claim gets back. Putting needs `--allow-uploads` and listing needs `--list-directories`, as in <<s3-list-a-bucket>>.

Bucket names belong to the object-storage servers only. The main server also listens on `https`, over the same store, and there the file is at the folder{apos}s own path, `/gallery/sunset.txt`; the path `/pics/sunset.txt` is not found, which `curl -f` turns into exit `22`. That is on purpose, so a file server and an object server share files without sharing names. The account is the same, sent with HTTP Basic (<<rfc7617>>), which is safe because the connection is encrypted.

The folder is checked when `surl` starts. A bucket mapped to a folder that is not there is not served as an empty bucket: `surl` exits `37` and names the folder and the bucket, before any request.

`curl` reaches `surl` as in <<s3-put-and-get-an-object>>: `--connect-to ::127.0.0.1:8080` sends every connection to `surl` whatever host the URL names, and the bucket is read back from the Amazon host name, `pics.s3.us-east-1.amazonaws.com`, which `curl` keeps. The certificate therefore names every bucket in the region with a wildcard as well as `127.0.0.1`, and `--cacert server.pem` makes `curl` trust it, since S3 is spoken over Transport Layer Security from the first byte (<<rfc8446>>). `--cert server.pem` and `--key server.key` are the certificate and key `surl` serves, `-u` signs each request with the account of `--user`, and `-T up.txt` puts the local file `up.txt`, so the last claim puts and gets in one command. In the checked claims, `-s` silences `curl`{apos}s progress meter and `-S` puts the error message back.
