=== Telling S3 Refusals Apart in C#

==== Problem

Your client must explain why S3 said no: unsigned, unknown key, bad signature. You want each refusal produced on purpose and named from C#, and anonymous reads allowed only when you say so.

==== Solution

Start two Surl.Api servers, one with an account and nothing loosened and one that also allows anonymous callers, send Curl.Api three requests that the first refuses for three reasons, and name each refusal from the exception:

==== Discussion

Amazon Simple Storage Service (S3) says why it refused a request in the error body, in a short code (<<aws-s3-api>>), and `surl` answers as S3 does. Every request must be signed with AWS Signature Version 4, the scheme S3 uses, by an account: `SurlServerOptions.Accounts` holds a `SurlAccount`, the pair that `--user AKIAIOSFODNN7EXAMPLE:s3cret` makes, an access key ID and its secret access key, and a `CurlAuthenticationOptions` with `UserName` and `Password`, which are `-u`, makes Curl.Api sign with it. The recipe <<s3-tell-the-refusals-apart>> does the same with the two programs on a console.

`SurlServer.StartAsync` starts the server a `SurlServerOptions` describes. `ListenUrls` holds `s3://127.0.0.1:0`, where port `0` takes a free port that `BoundUrl` reports. `CertificateFile` and `KeyFile` are `--cert` and `--key`: S3 is spoken over Transport Layer Security from the first byte (<<rfc8446>>), so the listener needs a certificate, and the `openssl` line makes one for `127.0.0.1` and for every bucket host name in the region. `Files` is the content in memory, where `photos/hello.txt` is the object `hello.txt` in the bucket `photos`. `AllowAnonymous` is `--allow-anonymous` and `AllowUploads` is `--allow-uploads` (<<surl-readme>>).

`CurlClient.Create()` makes the client and `SendAsync` sends one `CurlRequest`. Its `Tls`, a `CurlTlsOptions` whose `Origin` is a `CurlTlsPeerOptions`, holds the certificate as `CertificateAuthorityBlob`, which is `--cacert`. Its `Network`, a `CurlNetworkOptions`, holds `ConnectTo`, which is `--connect-to`: the URL names the bucket as its host, so Curl.Api would send the request to `photos.s3.us-east-1.amazonaws.com`, and `::127.0.0.1:` with the port sends the connection to the server instead, while the name stays in the request and in the certificate check. A request with a `Body` is a put: `Curl.Api` uploads the bytes as `curl -T` does. The `CurlResponse` has the `StatusCode` and a `Body` stream.

A refusal is not a response. Where `curl` exits `22`, `SendAsync` throws `CurlException`, whose `Code` is `HttpReturnedError`, the number `22`, and whose `Message` carries the status and the S3 error: `S3 returned error 403: AccessDenied: Access Denied`. The code is the same for every refusal, so it cannot tell them apart; the message can, and the program reads the status and the error name out of it with a regular expression, which is what a client does to explain why S3 said no. A request with no credentials is `403 AccessDenied`. A request signed with an access key the server does not hold is `403 InvalidAccessKeyId`: the account is the mistake. A request signed with the right key and the wrong secret is `403 SignatureDoesNotMatch`: the account is known, and the signature the server worked out for it is not the one it was sent.

`AccessDenied` is also the answer to a request that is signed correctly and not allowed. The first server has no `AllowUploads`, so a signed put of `note.txt` is `403 AccessDenied`, and no `ListDirectories`, so a signed listing, `s3://photos/`, is too, both in the same words an unsigned get gets, `Access Denied`. The code and the message alone do not tell them apart; what you sent does. The signed get of `hello.txt` is served, which is how to confirm that the key is not the trouble. A key with no object is `404 NoSuchKey` and a bucket that is not in the store is `404 NoSuchBucket`; both come to a request that was signed and allowed, and a client that treats every `403` and `404` alike will retry the wrong thing.

Anonymous reads are off until you say so. On the second server, with `AllowAnonymous`, a request with no credentials is served, so a test can read with no keys, and so can anyone who can reach the listener: it is for tests only, and `surl` warns on every start while it is on (<<surl-readme>>). It loosens nothing else. An unsigned put is still `403 AccessDenied`, though that server has `AllowUploads` too, and a request that does carry a login is still judged, so an unknown access key is `InvalidAccessKeyId` and a wrong secret `SignatureDoesNotMatch` on that server too.
