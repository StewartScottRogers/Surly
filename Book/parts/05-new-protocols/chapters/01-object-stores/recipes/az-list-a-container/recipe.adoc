=== Listing a Blob Container

==== Problem

Your app lists the blobs in a container before it downloads them. You want the listing refused until it is allowed, then the blob names under a prefix.

==== Solution

Make a certificate, give `surl` a folder, a Bearer token and `--list-directories` on an `az` listen URL, and send `curl` to it, naming the prefix as a URL that ends in a slash:

==== Discussion

Azure Blob Storage lists a container with List Blobs, a `GET` on the container with a prefix and a delimiter that answers the blob names starting with the prefix, folding any that continue past the delimiter into one prefix of their own (<<azure-blob-api>>). `surl` on an `az` listen URL answers it from its store, in which each top-level folder is a container and the path under it the blob name, so `store/photos/2026/jan.jpg` is the blob `2026/jan.jpg` in the container `photos` (<<surl-readme>>). In the Curl port, an `az://` URL in the emulator{apos}s path style, `az://<host>:<port>/<account>/<container>/`, whose path ends in a slash is a listing, and `curl` writes the names to standard output, one to a line, in order (<<curl-protocols>>).

So `az://127.0.0.1:8080/devstoreaccount1/photos/2026/` is the blobs under the prefix `2026/` and the same URL ending at `photos/` is the top of the container: one level only, the folders shown as prefixes that end in a slash and the blobs at that level by name. A prefix with nothing under it lists nothing and exits `0`; a container that is not a folder of the store is `404 ContainerNotFound`. A get of one blob is a URL with a name and no trailing slash, as in <<az-put-and-get-a-blob>>.

The credentials are those of that recipe. `--user :t0ken-abc` is an account with an empty user name, whose password `surl` reads as a Bearer token (<<rfc6750>>), and `--oauth2-bearer t0ken-abc` sends it; `--user devstoreaccount1:c2VjcmV0` is the account whose base64 key signs a request when `curl` is given `-u devstoreaccount1:c2VjcmV0`. Either gets the listing. A listing with neither is `401 NoAuthenticationInformation`, although the server allows listings.

Listing is off until it is asked for. Without `--list-directories`, the `nolist` server refuses a listing that carries the token with `403 AuthorizationPermissionMismatch`, and still serves a get of a blob by its name. The option decides whether a client may enumerate what is stored, not whether it may read it, and a listing tells a client every name in the container, which a client that knows only one name should not learn. `--allow-anonymous`, on the `open` server, serves a listing with no token, so a test needs none, and so does anyone who can reach the listener; it is for tests only, and `surl` warns on every start while it is on (<<surl-readme>>).

`--directory store` is the store, with each top-level folder a container, so `store/photos/` is the container `photos`. The token and the signature travel only inside Transport Layer Security (TLS) (<<rfc8446>>): `curl` speaks Hypertext Transfer Protocol Secure for an `az://` URL, and `surl`{apos}s `az` listener is TLS from the first byte, so it needs a certificate. The `openssl` line makes one for `127.0.0.1`; `--cert server.pem` and `--key server.key` serve it, and `--cacert server.pem` makes `curl` trust it, which no authority signed. For every error status `curl` writes nothing to standard output, names the Azure error on standard error, and exits `22`. `-s` silences `curl`{apos}s progress meter and `-S` puts the error message back.
