=== Sending WebTransport Datagrams in C#

==== Problem

Your game client uses WebTransport datagrams for its state and one-way streams for its logs, and you want a .NET test to host the server, send both through a session that needs a login, and check what comes back.

==== Solution

Host WebTransport with `Surl.Api`, your certificate and an account, send the data with `Curl.Api`, choosing datagram or stream with `?wt=`, and read the echo and what `surl` recorded; the argument picks what the client does differently:

==== Discussion

WebTransport is a session inside HTTP/3: the client sends an extended `CONNECT` with `:protocol` `webtransport-h3`, and once the server answers `200`, both sides can open streams and send datagrams that belong to the session (<<webtransport-http3>>, <<rfc9114>>). HTTP/3 runs over QUIC, which is always encrypted with Transport Layer Security (TLS) 1.3 (<<rfc9000>>, <<rfc8446>>).

`SurlServerOptions` is `surl`{apos}s command line as properties (<<surl-readme>>). The listen URL `webtransport://127.0.0.1:0` takes a free User Datagram Protocol (UDP) port. `CertificateFile` and `KeyFile` are `--cert` and `--key`, the files the `setup` step made with `openssl`; without them `StartAsync` throws `SurlServerStartException`, whose `ExitCode` is `CertificateProblem`, `58`, since QUIC cannot run without a certificate. `Accounts` gets one `SurlAccount`, `player1`, and from then on a session needs its login. `surl` accepts a session at any path, `/game` here, and echoes each stream and datagram back. `RecordExchanges` keeps every exchange for the test to read.

`CurlClientOptions` makes the client: `Tls` holds a `CurlTlsPeerOptions` whose `CertificateAuthorityBlob` trusts the certificate, as `--cacert` does, and `Authentication` holds a `CurlAuthenticationOptions` with the user name and password, as `-u` does (<<curl-readme>>). A `CurlRequest` for `webtransport://`, the bound port and `/game` opens the session and sends its `Body` as `curl -d` sends data; the query parameter `wt=` picks how (<<curl-protocols>>). Each call is bounded by a ten-second cancellation token, so a session or datagram that never answers fails instead of hanging.

`?wt=datagram` sends the body as one datagram, and the response body is the datagram `surl` echoes. A datagram is not retransmitted if lost and not ordered with anything else, which suits game state, where the next update replaces this one. It must also fit in one QUIC packet: 1,099 bytes, with the one-byte quarter stream ID that ties it to the session, make 1,100 and come back whole; 1,100 bytes do not fit, and `SendAsync` throws a `CurlException` whose `Code` is `SendError`, `55`, the exit code `curl` gives, naming the limit. `?wt=uni` sends the body on a unidirectional stream, and `surl` echoes it on one of its own. A stream is reliable and ordered and carries any amount, so 100,000 bytes come back whole; that suits logs. With no `wt=`, the body goes on one bidirectional stream and the echo comes back on it. Any other mode, such as `wt=dgram`, is refused before anything is sent, `UrlMalformat`, `3`.

`SurlExchangeRecord` is one exchange as `surl` saw it, and each `SurlExchangeChunk` one read or write, tagged with its layer. The `Decoded` chunks are the HTTP/3 header blocks as text: the `CONNECT` received, with `:protocol: webtransport-h3` and `:path: /game`, and the `:status` sent back. `FindEvents` with a `SurlEventQuery` for `LoginJudged` gives each `LoginJudgedEvent`: the account, the mechanism, and whether the login was accepted. With the right password the `CONNECT` is answered `200` and the login is `player1`, `Basic`, accepted. With none, `surl` answers `401` and judges nothing; `SendAsync` throws a `CurlException` with `HttpReturnedError`, `22`, and a message naming the refused session. A wrong password is the same `401`, and the event records `player1` as not accepted, which is what a test of a lock-out or an audit log wants to see. Without the certificate as an authority, the QUIC handshake fails before any `CONNECT`: `PeerFailedVerification`, `60`.
