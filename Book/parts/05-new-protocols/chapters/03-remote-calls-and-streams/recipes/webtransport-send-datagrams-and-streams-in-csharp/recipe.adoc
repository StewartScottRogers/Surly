=== Opening a WebTransport Session in C#

==== Problem

Your game client uses WebTransport datagrams for its state and one-way streams for its logs, and you want a .NET test to host the server, open a session against it, and check that a session without a login is refused.

==== Solution

==== Discussion

WebTransport is a session inside HTTP/3: the client sends an extended `CONNECT` with `:protocol` `webtransport-h3`, and once the server answers `200`, both sides can open streams and send datagrams that belong to the session (<<webtransport-http3>>, <<rfc9114>>). HTTP/3 runs over QUIC, which is always encrypted with Transport Layer Security (TLS) 1.3 (<<rfc9000>>, <<rfc8446>>).

`SurlServerOptions` is `surl`{apos}s command line as properties (<<surl-readme>>). The listen URL `webtransport://127.0.0.1:0` takes a free User Datagram Protocol (UDP) port. `CertificateFile` and `KeyFile` are `--cert` and `--key`, the files the `setup` step made with `openssl`; without them `StartAsync` throws `SurlServerStartException`, whose `ExitCode` is `CertificateProblem`, `58`, since QUIC cannot run without a certificate. `Accounts` gets one `SurlAccount`, `player1`, and from then on a session needs its login. `RecordExchanges` keeps every exchange for the test to read.

`CurlClientOptions` makes the client: `Tls` holds a `CurlTlsPeerOptions` whose `CertificateAuthorityBlob` trusts the certificate, as `--cacert` does, and `Authentication` holds a `CurlAuthenticationOptions` with the user name and password, as `-u` does (<<curl-readme>>). A `CurlRequest` for `webtransport://` and the bound port, path `/game`, opens the session; `SendAsync` returns once the server has accepted it, and the call is bounded by a ten-second cancellation token so a session that never answers fails instead of hanging.

`SurlExchangeRecord` is one exchange as `surl` saw it, and each `SurlExchangeChunk` one read or write, tagged with its layer. The `Decoded` chunks are the HTTP/3 header blocks as text: the `CONNECT` received, with `:protocol: webtransport-h3` and `:path: /game`, and the `:status` sent back. `FindEvents` with a `SurlEventQuery` for `LoginJudged` gives each `LoginJudgedEvent`: the account, the mechanism, and whether the login was accepted. With the right password the `CONNECT` is answered `200` and the login is `player1`, `Basic`, accepted. With none, `surl` answers `401` and judges nothing; `SendAsync` throws a `CurlException` whose `Code` is `HttpReturnedError`, `22`, the exit code `curl` gives, and whose message names the refused session. A wrong password is the same `401`, and the event records `player1` as not accepted, which is what a test of a lock-out or an audit log wants to see. Without the certificate as an authority, the QUIC handshake fails before any `CONNECT`: `PeerFailedVerification`, `60`.

That is as far as `Curl.Api` 0.2.0 goes: it opens and closes the session but does not send the request's `Body` as a datagram or on a stream, so nothing is echoed and the response body is empty. To send the game state and logs themselves, and see them echoed, use `curl` with `?wt=datagram` and `?wt=uni` (<<webtransport-send-datagrams-and-streams>>, <<curl-protocols>>), or an agent's `curl-mcp` (<<webtransport-send-datagrams-and-streams-from-an-agent>>), against the same server.
