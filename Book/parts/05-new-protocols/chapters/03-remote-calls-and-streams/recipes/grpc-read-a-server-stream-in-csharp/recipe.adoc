=== Reading gRPC Streams in C#

==== Problem

==== Discussion

`SurlServer.StartAsync` starts the server, and `SurlServerOptions` is the options of `surl` as properties: a `ListenUrls` of `grpc://127.0.0.1:0` takes a free port, and `AllowAnonymous` is `--allow-anonymous`. The built-in `surl.test.Echo` service has the method `Expand`, which answers `count` replies, each with the request{apos}s `message` and its own `index`.

`CurlClient` and `CurlRequest` make the call. A `POST` whose `Body` is the request as JSON is the request message; the types come from the server{apos}s reflection, as for `curl` on the console. `CurlResponse.Body` holds the replies as JSON objects, one after another, in the order sent, and the first has no `index` because its value is `0`. A stream with no replies is a success: `count` `0`, and no `count`, give an empty body and no exception.

The body is a `Stream` that is filled as the replies arrive. With `delayMilliseconds` holding each of ten replies back 300 milliseconds, a read cancelled after one second has seen some of them and not all ten; the program counts the objects it read and reports some or all. A `CancellationToken` is how a C# program stops waiting, as `-m` is on the console. The first request `Curl.Api` makes in a process takes about four seconds of one-time set-up, so the program makes one untimed request before any timing.

A failure is an exception. A `count` above 1000 is refused `INVALID_ARGUMENT`, `request field out of range`, and `SendAsync` throws a `CurlException` whose `Code` is `HttpReturnedError`, 22, the exit code `curl` would give. So does a stream that ends in a status other than `OK`: `count` 3 with `statusCode` 13, `INTERNAL`, throws with `grpc-status 13 (INTERNAL): boom`. The difference from the console is that the replies sent before the status are not handed to the program; `curl` prints them, and `Curl.Api` throws instead. A program that needs those replies should not ask for a status it expects to follow them.
