# Review: webtransport-open-a-stream
Verdict: accept with fixes (flaky until Curl finding 7 is fixed)
Checked against local builds on 2026-11-19 (not releases): surl 1.0.0 (Surl commit 763754785), Curl port (Curl commit b9ca725077): 14 of 14 cases pass on windows.
## Findings
1. Platform: WebTransport over HTTP/3 works end to end on Windows with this pair of builds: bidirectional stream, `?wt=uni` and `?wt=datagram`, certificate verified with `--cacert` (cert from `setup:`), and a login with `-u`.
2. Readiness: the listener is UDP only, so every server is `ready: none` and verify sleeps 0.2 s. The first case, `wait-for-start`, uses `curl --retry 5 --retry-all-errors --retry-delay 1` (a real reader's answer to the same race) so the later cases do not race; `main` starts last, so the account servers have had longer. Probed: against a port with nothing on it, `curl` retries five times on exit 7 and then gives up with 7; with CoAP, a `curl` started 3 s before `surl` succeeds with the same options.
3. Harness finding (lead): one run in six failed every case with exit 7. The servers' logs showed `surl: (45) Could not bind webtransport://127.0.0.1:64954/: Permission denied`: verify.py's `free_port()` checks only TCP, and on this machine Windows reserves UDP ranges that are free for TCP (`netsh int ipv4 show excludedportrange protocol=udp`: 64891-64990, 62797-63496 and others). Because `surl` exits after the 0.2 s start check, verify does not retry on fresh ports. Fix in verify.py: in `free_port()`, bind a UDP socket on the same port too. Affects every UDP recipe (`tftp-download-a-file`, `coap-get-a-resource`).
4. `nothing-listening` (exit 7 at once on a UDP port with no listener) is the ICMP port-unreachable path on Windows; another platform may wait and give 28. Check on Linux and macOS.
5. Login: with no account, `surl` opens a session for anyone (the `CONNECT` is judged as a read, `IsWrite: false` in `WebTransportConnectAuthentication`); once an account exists, a session needs a login. `surl --aihelp webtransport` says "without an account a login is refused unless `--allow-anonymous` is given", which reads as if the default refused anonymous sessions. Not a defect (consistent with the auth topic's GET rule), but the help text is misleading; listed for the author.
6. The answer is written with no newline; the cases use exact `stdout` without one.
7. Program finding (Curl, needs the author): under load, about 1 run in 30 of a plain bidirectional echo (`curl --cacert server.pem -d "hello over a stream" webtransport://127.0.0.1:<port>/echo`, 120 runs, three loops side by side) fails with exit 56 and `curl: (56) WebTransport session failed: QUIC: the datagram channel failed: The I/O operation has been aborted because of either a thread exit or an application request.` Alone, 40 of 40 pass. No datagram is sent in that exchange, so the datagram channel should not end it. In verify runs this shows as one random case failing with exit 56 (seen twice in eight runs). The recipe keeps its cases; it will be flaky until Curl fixes this.
8. Updated 2026-11-19 for Surl 763754785 and Curl b9ca725077: surl now refuses a session with no login unless `--allow-anonymous`, even with no account; `main` gains `--allow-anonymous` (and the Solution says so), new server `plain` and case `refused-by-default` (401, exit 22) show the default, and the login paragraph is rewritten. Finding 5 is resolved by the change.
