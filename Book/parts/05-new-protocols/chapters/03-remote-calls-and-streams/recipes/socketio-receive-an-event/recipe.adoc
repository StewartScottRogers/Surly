=== Receiving a Socket.IO Event

==== Problem

You want to emit an event to a Socket.IO server and see the events it sends back, from the command line, in a test that ends on its own.

==== Solution

==== Discussion

Socket.IO carries named events between a server and its clients. A client opens a WebSocket (<<rfc6455>>) at the path `/socket.io/`, joins a _namespace_, and then each side may emit events, each a JavaScript Object Notation (JSON) array whose first element is the event's name and whose rest are its arguments (<<socketio-protocol>>). Upstream curl has no `socketio` scheme; the Curl port adds it, and `surl` serves it (<<curl-protocols>>, <<surl-readme>>).

`-d` is the event `curl` emits once it has joined, here `["greeting","hello from surl"]`. The URL's path names the namespace, and `/` is the main one. `surl` answers an event by sending it back to the sender, the same array byte for byte, and `curl` writes each event it receives as one JSON array per line.

A Socket.IO session has no last message: `curl` keeps listening until the server disconnects, and `surl` does not disconnect it after the echo. `-m 3` ends it after three seconds, which is far longer than the echo takes, and `curl` exits `28`, the time-out, with the event already written. That exit code is the expected end of every run here that joins. `-s` keeps `curl` quiet; in the claims, `-S` still shows the error when there is one.

An event named `broadcast` comes back to its sender exactly once too. With no `-d`, `curl` joins and only listens; with no one emitting, nothing is written before `-m 2` ends the run.

`curl` checks `-d` before it connects: data that is not a JSON array starting with the event's name is refused with exit `2`. `surl` serves the main namespace only, so `socketio://127.0.0.1:8080/admin` is refused with `Invalid namespace`, and `curl` exits `22`. The server answers only at `/socket.io/`: any other path on the same port is `404 Not Found`, which `-s -o /dev/null -w "%{http_code}"` shows: `-o` throws the body away and `-w` prints the status.

`--allow-anonymous` lets a client with no credentials join. A Socket.IO client logs in with the namespace request itself, and `curl` without `-u` sends no credentials there, so against the second server in the claims below, `plain`, which has neither an account nor `--allow-anonymous`, it is refused with `Not authorized` and exits `22` without writing an event. That is the default because a server that lets anyone join sends its events to anyone.

The loosening is for tests. The secure form is an account: the third server, `account`, has `--user alice:secret`, and `curl -u alice:secret` puts that login in its namespace request, so it joins and gets its event back like the anonymous client; a wrong password is refused with `Not authorized`, exit `22`. That server also has `--allow-plaintext-auth`, the loosening that lets a password be checked over plain `socketio`, which has no encryption. The fourth server, `clear`, has the same account without it, and refuses even the right password with `Not authorized`, so a password never counts over plain `socketio` unless you say it may.
