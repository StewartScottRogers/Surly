[[xmpp-require-tls-before-login]]
=== Requiring TLS before XMPP Login

==== Problem

Your chat client must upgrade with STARTTLS before it sends a password. You want a login refused before Transport Layer Security (TLS), accepted after STARTTLS, and accepted at once over XMPPS, the Extensible Messaging and Presence Protocol with TLS from the first byte.

==== Solution

Start `surl` with a certificate and an account, on an `xmpp` listen URL and an `xmpps` one, and have `curl` log in over the first, trusting the certificate:

==== Discussion

An `xmpp` connection starts in clear. The client sends its stream header, the server answers with its features, and a server that wants TLS first says so with `<starttls><required/></starttls>`; the client then asks for it, both sides run the TLS handshake on the same connection and start the stream again, and only then is a login offered (<<rfc6120>>). `surl` on an `xmpp` listen URL does exactly that when it has a certificate, `--cert` and its private key `--key` (<<rfc8446>>), and `curl` does the client{apos}s half: with `--cacert` naming the certificate, which is its own authority, it upgrades and logs in as the account `-u` names, using one of the mechanisms the server then offers (<<curl-readme>>, <<curl-protocols>>). Both are extended: upstream curl has no `xmpp` scheme, so the two programs are judged by the specification and not by curl (<<surl-readme>>). The path of the URL, `127.0.0.1`, is the server{apos}s domain, and with no `-d` `curl` prints the server{apos}s answer to a discovery question, which is a proof that the login worked.

`curl` cannot show what a client that skips the upgrade would see, because it never skips it. So two claims send the bytes by hand: `-T` uploads a file, and over `telnet://`, which does nothing to the bytes, it is a raw client. `open.xml` is a stream header and nothing else; the server{apos}s answer is its own header and one feature, STARTTLS, marked required, and no login mechanism. `login.xml` is the header followed by a SASL PLAIN login with the right password (<<rfc4616>>, the account name and the password after a NUL byte each, in base64): the answer is the failure `encryption-required` and nothing is accepted. A telnet connection stays open, so `-m 3` ends the wait for more, with exit `28`, a timeout; the output is what the server had sent by then. The stream `id` is random, so the pattern accepts any hex digits.

The same login is accepted at once over `xmpps://`. There, TLS comes first, from the first byte, and there is no upgrade to demand. Either way the certificate is checked. Without `--cacert`, `curl` does not trust it, ends the upgrade before it sends a password, and exits `60`; the wording of that error is the TLS library{apos}s, so the claim is the exit code. Once TLS is up, a wrong password is refused with the SASL error `not-authorized`, and no `-u` leaves `curl` nothing to log in with: it exits `67`, because the server offers no anonymous login. Both are exit `67`, login denied.

`surl` does not serve `xmpp` without TLS unless it is told to. With no `--cert` and no `--self-signed`, it exits `58` and says the listen URL needs a certificate, so the login never has to be refused in clear: there is no server to send it to. `--allow-plaintext-auth` is the loosening for a test. It lets `xmpp` run with no certificate, and the server then offers its mechanisms at once, PLAIN among them and no STARTTLS, accepts the PLAIN login that was refused above, with a `success`, and checks the password for `curl` as well, so a wrong one is `not-authorized`. It warns on start while it is on, because anyone who can watch the network reads the password as it is sent (<<surl-readme>>). `--user` adds the account.

In the checked claims, `-s` silences `curl`{apos}s progress meter and `-S` puts the error message back, so the reason shows on standard error.
