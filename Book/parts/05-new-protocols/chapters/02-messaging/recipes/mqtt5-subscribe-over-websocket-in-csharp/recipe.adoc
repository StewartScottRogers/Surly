=== MQTT over WebSocket in C#

==== Problem

Your browser dashboard speaks MQ Telemetry Transport (MQTT) over WebSocket, while your devices publish over TCP. You want a C# test in which a retained message is published over TCP and read over WebSocket from the same broker, with the broker in the same program and the clients from `Curl.Api`.

==== Solution

Start a `SurlServer` with a TCP listen URL and a WebSocket one, publish through the first with a `CurlClient`, and read through the second:

==== Discussion

`SurlServerOptions.ListenUrls` holds two URLs, `mqtt://127.0.0.1:0` and `mqtt5+ws://127.0.0.1:0`, each on a free port, and `server.BoundUrls` gives them back in that order. They are one broker, with one message bus, so what is published through the first is read through the second. `mqtt5+ws` is MQTT 5.0 over WebSocket (<<rfc6455>>, <<mqtt5>>), the form a browser can use. The devices use `mqtt://`, MQTT 3.1.1, because `Curl.Api` 0.2.0 does not publish over `mqtt5://`: a `POST` there sends a subscribe, and nothing is kept. That is also why the recipe has no case that publishes over WebSocket, which the console recipe has. `Topics` is `--topic`, and `"dash/#;retain"` keeps the last message published under `dash/`, whatever the RETAIN flag of the publish, which a client sends clear. `AdditionalArguments` carries `--mqtt5-disconnect-after-retained`, which has no property: it makes the broker end a subscription once the retained messages are sent, so a read returns instead of waiting (<<surl-readme>>).

The clients are one `CurlClient`, and each call is a `CurlRequest`. The publisher is a `CurlRequest` with `HttpMethod.Post` and a `Body` of `CurlContent` bytes, and the reader a `CurlRequest` with `HttpMethod.Get`; the path of the URL is the topic, and the `CurlResponse.Body` is the retained messages, the payloads alone (<<curl-readme>>). The message stays on the topic, so a second client that reads later is given it too; a filter ending in the multi-level wildcard, written `%23` in the URL, reads every topic below it, one payload after the other, in no promised order, which the program sorts; a topic outside the filter keeps nothing, and an empty publish clears a topic.

A client that is not an MQTT client is turned away. A `GET` of `ws://` to the path `/mqtt` asks for an upgrade with no `mqtt` subprotocol, and the broker refuses it with `400`; any other path is `404`. `SendAsync` throws a `CurlException`, whose `Code` is `22` and whose `Message` is `Refused WebSocket upgrade` with the status.

The login rules are those of `mqtt5://`. `SurlServerOptions.Accounts` takes `SurlAccount` values, the `--user` options, and `AllowAnonymous` is left off; the login is a `CurlAuthenticationOptions` holding the `UserName` and `Password`. A client that sends none is refused in the connect acknowledgement with reason code `0x87`, not authorized, and `SendAsync` throws a `CurlException` of `Code` `67`, login denied. The right password over the WebSocket is refused with `0x87` too, unchecked, because `mqtt5+ws` is not encrypted and the password crossed the network in clear. `AllowPlaintextAuthentication` is `--allow-plaintext-auth`, a loosening for a test: the password is then checked, the right one accepted, and a wrong one refused with `0x86`, bad user name or password.

A publish is not acknowledged, so `SendAsync` can return before the broker has applied it, and a read straight after can be stale: this can happen on macOS. The program does not sleep. `RecordExchanges` is on, and after each publish it calls `WaitForEventAsync` with a `SurlEventQuery` for the next `SurlEventKind.ExchangeEnded`, which the broker records once what the client sent has been dealt with, keeping the `SurlEvent`{apos}s `Sequence` as the point to wait after, with a ten second bound that a failure alone ever reaches.
