=== Sharing a Subscription between Workers

==== Problem

Several workers subscribe as one shared group so each message reaches only one of them. You want an MQTT 5 shared subscription whose messages are split among its members, and a test that shows no message goes to two workers.

==== Solution

==== Discussion

MQTT 5 is version 5.0 of the publish and subscribe protocol MQTT; `mqtt5://` is `surl`{apos}s broker for it (<<surl-readme>>) and `curl`{apos}s client (<<curl-protocols>>). A subscription to `jobs` is sent every message published to `jobs`. A shared subscription is one subscription held by a group: its filter is `$share/`, a share name, `/`, and the topic filter, and each message that matches is sent to one member of the group only (<<mqtt5>>, section 4.8.2). Two workers subscribed to `$share/workers/jobs` therefore split the jobs between them, while the monitor, subscribed to `jobs` on its own, is sent all six.

Each `curl` without `-d` subscribes and writes each payload it is sent as it arrives; `-o` names the file and `-m 60` is a ceiling on how long it stays. A job is published by a `curl` with `--data-binary @-`, which sends what `printf` writes, line feed included, so each job is a line. `-s` keeps every `curl` quiet. `--allow-anonymous` lets clients connect with no login, a loosening for a test on your own machine; a broker without it refuses a worker at `CONNECT` with reason code `0x87`, Not authorized, and `curl` exits `67`.

A worker is subscribed some time after its `curl` starts, and a job published before then would be lost to the test. So the script publishes `ping` until all three files hold something: the group hands each ping to one worker, so both workers{apos} files fill only when both are members. It then publishes the six jobs, waits until the workers hold six between them, stops the three with `kill`, and counts the lines holding `job`. Each worker was sent at least one and at most five, and between them they were sent each job once. Which member is sent which message is left to the broker (<<mqtt5>>), so the test claims only that neither worker was left out.

`--topic "jobs;retain"` keeps the last message on `jobs`, here `job-6`, for subscribers that come later. A worker that joins the group after the run is not sent it, since retained messages are not sent for a shared subscription (<<mqtt5>>, section 3.3.1.3), and its `curl` ends at `-m 3` with exit `28`, nothing written. A plain subscriber to `jobs` as late is sent `job-6`.

The share name must be followed by `/` and a topic filter. `$share/workers` has none, and `curl` refuses it before subscribing: exit `3`, `Invalid MQTT 5 topic: "$share/workers" has no ShareName followed by '/'`; `-S` shows the error that `-s` would hide.
