=== Logging In to NATS with a Token

==== Problem

Your service connects to NATS with an auth token rather than a user and password. You want the token refused over plain NATS until allowed, accepted over NATSS, and a wrong token answered Authorization Violation, with the token kept out of the log.

==== Solution

Give `curl` the token as the user name, with nothing after the colon, and publish to a `nats` listen URL:

The others, one that holds a token, one that also accepts it in clear, and one that serves `natss`, are there for the checked claims below, and so are the `openssl` line and the small `sh` script, which needs a POSIX shell (Git Bash on Windows). ==== Discussion

The NATS client protocol lets a client log in in two ways, with a user name and a password, or with a single token, and sends either in its `CONNECT` line, a token as the field `auth_token` (<<nats-protocol>>). `surl` on a `nats` listen URL is a core NATS server, an extended server that upstream curl has no client for; the Curl port has one (<<surl-readme>>, <<curl-protocols>>). `-u tok123:`, a user name and an empty password, makes `curl` send `tok123` as the token, and a user and a password make it send those; `-d paid` publishes the message `paid` to the subject in the path of the URL. `--allow-anonymous` is the other way in for a test: the server accepts every `CONNECT`, a token among them, without looking at it, which is why the Solution can succeed with a token no account holds. On the server side a token is an account with no name, `--user :tok123`; the token is what stands after the colon (<<surl-readme>>).

The first thing that stops a token is where it travels. `nats://` has no encryption, so `surl` refuses a token it was sent in clear without looking at it, with the error `Authorization Violation`, and `curl` exits `67`, login denied. The server{apos}s log says why: the login was refused as `RefusedPlaintext`, so the token was never compared. `--allow-plaintext-auth` loosens that for a test, and `surl` warns on start while it is on, because anyone who can watch the network reads the token as it is sent. With it, the token is judged: the one the server holds is accepted, and the log says `RefusedCredentials` for one that does not match. The log shown here is made with `-v` and `--log-file`; the script waits, at most ten seconds, for the line to be there, because `surl` writes an exchange{apos}s last lines a moment after its client has gone.

The way in without that option is `natss://`, the same server over Transport Layer Security (TLS), which needs a certificate, `--cert` and its private key `--key` (<<rfc8446>>). There the token is judged with no loosening option. `curl --cacert` trusts the certificate, which is its own authority; the token the server holds is accepted and the message published, exit `0`, and a wrong token, or none, is answered `Authorization Violation`, `67`. Without `--cacert`, `curl` does not trust the certificate, sends nothing, and exits `60`. A `natss` server requires TLS before `CONNECT`, whether the client starts it at once or after the plain INFO that says so, and `curl` with `nats://` is told so by that INFO and stops, exit `35`, with no token sent. `--ssl-no-revoke` is on every `natss` command because the Windows build of `curl` fails the handshake against this certificate without it; the option does nothing elsewhere.

The log never holds the token. A `CONNECT` is logged with the value of `auth_token`, and of `pass`, replaced by four asterisks, and the token appears nowhere in the file, though clients sent it and it was accepted, so the log can be kept and shared (<<surl-readme>>). A user name and a password work the same way (<<nats-publish-and-subscribe>>).

In the checked claims, `-s` silences `curl`{apos}s progress meter and `-S` puts the error message back, so the reason shows on standard error.
