=== NATS Token Logins in C#

==== Problem

Your service connects to NATS with an auth token rather than a user and password. You want a C# test that shows the token refused over plain NATS until allowed, judged over NATSS, and a wrong token answered Authorization Violation, with the server in the same program and the client from `Curl.Api`.

==== Solution

Start a `SurlServer` on a `nats` listen URL that takes anonymous clients, and publish with a `CurlClient`, giving the token as the user name:

The Solution uses a server that takes anonymous clients. The others, built by the same program, hold a token, accept it in clear, or serve `natss`, and are there for the checked claims below.

==== Discussion

The NATS client protocol lets a client log in with a user name and a password, or with a single token, sent in its `CONNECT` line as the field `auth_token` (<<nats-protocol>>). `SurlServerOptions.ListenUrls` holds `nats://127.0.0.1:0`, a core NATS server on a free port, and `server.BoundUrls[0]` gives the URL back. On the server side a token is an account with no name: `Accounts` takes `SurlAccount` values, the `--user` options, and `new SurlAccount("", "tok123")` is `--user :tok123` (<<surl-readme>>). `AllowAnonymous` is `--allow-anonymous`, a loosening for a test, which makes the server accept every `CONNECT`, a token among them, without looking at it; that is why the Solution succeeds with a token no account holds.

The client is a `CurlClient`, and a `CurlRequest` with `HttpMethod.Post` and a `Body` of `CurlContent` bytes publishes the message to the subject in the path of the URL. A `CurlAuthenticationOptions` with a `UserName` and no `Password` makes `Curl.Api` send the user name as the token, and one with both sends a user and a password (<<curl-readme>>). A refusal is an exception: `SendAsync` throws a `CurlException`, whose `Code` is `67`, login denied, and whose `Message` is `NATS server refused the login: Authorization Violation`.

The first thing that stops a token is where it travels. `nats://` has no encryption, so the server refuses a token it was sent in clear without looking at it, the one it holds included. Its log says why: `Log` is a `TextWriter` and `LogLevel` is `LogLevel.Verbose`, which logs each `CONNECT` and the reason a login was refused, and the program reads it once the server has stopped, when every line is in it, and finds `RefusedPlaintext`: the token was never compared. `AllowPlaintextAuthentication` is `--allow-plaintext-auth`, a loosening for a test, since the token travels in clear. With it the token is judged, and the log says `RefusedCredentials` for a wrong one.

The way in without that option is `natss://`, the same server over Transport Layer Security (TLS), which needs a certificate: `CertificateFile` and `KeyFile` are `--cert` and `--key`, the files `openssl` made in the recipe{apos}s `setup` (<<rfc8446>>). The client trusts it through a `CurlClientOptions` whose `Tls` is a `CurlTlsOptions`, and its `Origin`, a `CurlTlsPeerOptions`, holds a `CertificateAuthorityFile` of `server.pem`, a self-signed certificate being its own authority, and `SslOptions.NoRevoke`, which the Windows build needs here and which does nothing elsewhere. There the token is judged with no loosening option: a wrong token, or none, is `Authorization Violation`, `67`. A client without the certificate sends nothing, and `SendAsync` throws a `CurlException` of `Code` `60`; the message is the TLS library{apos}s, so the program prints the code alone. A `natss` server requires TLS before `CONNECT`, so a client that connects with `nats://` is told so by the server{apos}s INFO and stops, `Code` `35`, with no token sent.

The log never holds the token. A `CONNECT` is logged with the value of `auth_token`, and of `pass`, replaced by four asterisks, and no line of the log holds the token the server holds, which the program counts after sending it (<<surl-readme>>).

One thing the recipe cannot show is a token accepted. In the build it was checked against, the server also refuses the token it holds, over `natss` and with the loosening alike, with the same error; the last claim records it, so the recipe will fail, and be finished, when that is fixed.
