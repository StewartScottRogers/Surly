=== Asking What XMPP Offers

==== Problem

Your chat client checks what a server offers with service discovery before it relies on a feature. You want the server's answer written out, for the server itself and for an account, and you want to know what `curl` can and cannot ask.

==== Solution

==== Discussion

XMPP, the Extensible Messaging and Presence Protocol, is the protocol of Jabber chat: a client opens an Extensible Markup Language (XML) stream to a server's domain, logs in with Simple Authentication and Security Layer (SASL), binds a resource, and exchanges stanzas (<<rfc6120>>). One kind of stanza is the IQ, a question and its answer, and service discovery is a question asked in one: an IQ with a `query` in the `disco#info` namespace asks what an entity is and which features it answers. `surl` on an `xmpp` listen URL is an XMPP server, an extended server that upstream curl has no client for; the Curl port has one (<<curl-protocols>>, <<surl-readme>>).

In the URL `curl` takes, the host is the server and the path is the entity to ask. With no `-d`, `curl` logs in, sends the disco info question to the path, writes the answer on standard output and closes the stream. For the server's own domain the answer is an identity of category `server` and type `im`, an instant-messaging server, and three features: `disco#info` and `disco#items`, the two discovery questions, and `urn:xmpp:ping`, the ping. For an account's bare Jabber identifier (JID), `alice@127.0.0.1`, it is an identity of category `account` and type `registered` and the two discovery features, with no ping. `?disco` in the query says the same as no query.

The question is asked after the login, not before: the Solution logs in as alice, and `curl` with no `-u` asks for SASL `ANONYMOUS`, which this server does not offer, so it exits `67` with no answer. A wrong password is answered `not-authorized`, also `67`. `--cert server.pem` and `--key server.key` are the certificate and key `surl` serves, made by the `openssl` line in setup. `surl` with a certificate requires Transport Layer Security (TLS) before a login: it offers `STARTTLS`, and `curl` takes it and verifies the certificate, so `--cacert server.pem` is `curl` trusting that certificate (<<rfc8446>>). Without it, `curl` stops before it logs in, exit `60`. `--user alice:s3cret` is the account, and `-u alice:s3cret` the login, sent inside TLS.

`curl` asks info and nothing else. The other discovery question, `disco#items`, asks which entities the server has under it; a second word after `?disco;`, such as `items`, does not change the question, and `curl` prints the info answer again. A query type other than `disco` is refused by `curl` before it connects, exit `3`, naming the type. The C# recipe in See Also shows the items answer from a client that writes the stanza itself. `?disco;node=x` asks about a node of the entity, a part of it that discovery can ask about separately; `x` is not one here, and `surl` answers the stanza error `item-not-found`, which `curl` reports and exits `8`, a reply it could not use.

Entities `surl` cannot answer for are stanza errors too. `bob` has an account, but `surl` answers for the streams it holds, and bob has none bound, so asking `bob@127.0.0.1` is `service-unavailable`; alice can be asked because `curl` holds her stream while it asks. A domain `surl` does not serve, `example.com`, is `remote-server-not-found`: `surl` talks to no other server. `--mail-domain chat.example` on the second `surl` gives the server a domain beside its listen host, and it answers the same way under both names.

In the checked claims, `-s` silences `curl`{apos}s progress meter and error messages, and `-S` puts the error message back, so the stanza or SASL error shows on standard error.
