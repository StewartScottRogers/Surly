=== Reading a Kafka Log from an Agent

==== Problem

Your producer under test wrote records to a Kafka topic, and you want an artificial intelligence (AI) agent to read the topic{apos}s log by offset, with Model Context Protocol (MCP) tool calls and no shell, without consuming it.

==== Solution

Write the agent{apos}s side as a C# program on the official MCP software development kit (SDK): it starts `surl-mcp` and `curl-mcp`, starts a Kafka broker, lets the producer write through the `curl` tool, and reads the log with `read_log`:

==== Discussion

The program starts `surl-mcp`, the MCP server for `surl`, and `curl-mcp`, the one for `curl`, by name from the path, over standard input and output, each confined to the program{apos}s folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT` (<<mcp-spec>>). The argument picks the scenario. `start_server` takes `listen_urls`, here one `kafka` listener on a free port, and answers the `server_id` and, in `bound_urls`, the URL it bound. `arguments` passes `surl`{apos}s own options, and `--allow-anonymous` lets the producer connect with no login, a loosening for a test on one machine (<<surl-readme>>, <<kafka-protocol>>). Every topic has one partition.

The producer is the `curl` tool, which takes `curl`{apos}s own arguments; `-s` and `-S` keep the progress meter out and the error message in, and `--max-time` bounds each call. With `-d`, `curl` sends a record: `curl -d order-1001:placed kafka://host:port/orders` appends one record to the topic `orders`, and the program writes four, one for each step of an order (<<curl-readme>>). `curl-mcp` answers in text that is JavaScript Object Notation (JSON), with `exitCode`, `standardOutput.content` and `standardError.content`. The broker acknowledges a record before `curl` returns, so the log holds it at once and the agent needs no wait before it reads.

`read_log` takes the `server_id`, a `topic`, `from_offset`, `0` by default, and a `limit`. It answers `records`, each with an `offset` and the `text` of its value, in order, with `next_offset`, the offset to ask for next, and `has_more`. The agent reads offsets `0` to `3` and the four values the producer should have written, in order. `from_offset` `2` answers the last two. With a `limit` of `2` the first answer holds offsets `0` and `1`, `next_offset` is `2` and `has_more` is true, and a read from `next_offset` holds the rest with `has_more` false.

The call reads and takes nothing, because a Kafka topic is a log and not a queue. A consumer that uses `curl` with `?offset=2` after the agent has read still gets the records at offsets `2` and `3`, and a second `read_log` answers the same four. An offset past the end is a tool error and not an empty answer: `Offset 9 is outside the log, which holds 0 to 4.`, which tells the agent how long the log is. A topic nobody wrote to is a tool error as well, `No log for topic refunds.`, which is how the agent learns the producer used another name or never reached the broker.

Last, a broker without `--allow-anonymous` closes the producer{apos}s connection before it says anything. `curl` exits `56` and writes `Connection disconnected`, and the agent{apos}s read finds no log for the topic, so what the producer reported and what the broker holds can be told apart.
