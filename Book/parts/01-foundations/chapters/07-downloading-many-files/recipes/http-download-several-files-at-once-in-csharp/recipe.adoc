=== Downloading Files in Parallel in C#

==== Problem

Your .NET code needs to fetch a dozen files at once, with a limit on how many connections it opens, and your test wants to see from the server how many were open together.

==== Solution

Start a server in the test process with `Surl.Api`, let it record its events, and fetch twelve files with one `CurlClient` whose `MaxConnectionsPerHost` is 4. The program takes a scenario name as its argument, so each claim below runs the same file with a different cap:

==== Discussion

`SurlServerOptions.Files` holds twelve small files in memory, and `ListenUrls` of `http://127.0.0.1:0` takes a free port. `RecordExchanges = true` makes the server keep events, which the program reads with `FindEvents` and `SurlEventQuery`: one `ExchangeStarted` when a connection opens and one `ExchangeEnded` when it closes. Walking them in order, up at a start and down at an end, gives the most connections open together. `SurlFault.Delay` with `Stage = FaultStage.Command` is the library's spelling of `--fault "delay;stage=command;ms=1000"`: it holds every request for a second, so requests that run together overlap and the events can see them. It is a fault on purpose, a measuring aid, not a loosening.

On the client side, `CurlClient.Create` takes a `CurlClientOptions`, and `MaxConnectionsPerHost` is the cap: it plays the part of `--parallel-max` on the console. With 4, `Task.WhenAll` over twelve `SendAsync` calls runs four at a time, and a fifth waits for a free connection. The server's events agree, four open at once, and the twelve, held a second each in three rounds, take three seconds or more. With no cap, which is the default `0`, the same twelve calls open more than four connections; the exact number is the library's scheduling, so it is claimed as a range. On an idle machine they finish in about the second the server holds them, but a busy one can take several, so the case claims the connections, not the time. Awaiting each call before starting the next uses one kept-alive connection and takes as long as the sum of the holds, and a cap of 1 on calls started together does the same.

Each fetch is a `CurlRequest` with `HttpMethod.Get`, and its `CurlResponse` carries `StatusCode` and the `Body` stream. Each response is read through that stream and compared with the text the server holds; `12 of 12 fetched` says every one was a `200` with the right body. The first request a process makes with `Curl.Api` pays a one-time set-up of a few seconds, so the program makes it against a second server first. Otherwise the set-up would land in the timed part, and its connection would count against the measured server. The wait loop at the end gives the server up to ten seconds to see every connection close before the count is taken, since a connection ends after the client has gone.
