=== Reporting Download Progress

==== Problem

Your C# tool fetches large files over Hypertext Transfer Protocol (HTTP), and you want it to print a progress line as the bytes arrive, from Curl.Api's own progress reports rather than by counting bytes yourself.

==== Solution

Set `Progress` on the `CurlRequest` to an `IProgress<CurlTransferProgress>` that prints a line each time another quarter of the body has arrived:

==== Discussion

The server is `surl` in-process (<<surl-readme>>): `SurlServerOptions` holds a 16 mebibyte (MiB) `big.bin` in `Files` on a free port. `CurlClientOptions.Timeout` of 60 seconds bounds every transfer, so a run that goes wrong fails instead of hanging, and the program makes one untimed request first, because the first Curl.Api request in a process spends a few seconds setting the engine up.

`CurlRequest.Progress` takes any `IProgress<CurlTransferProgress>`. The engine calls its `Report` each time libcurl would call a transfer's progress callback, `CURLOPT_XFERINFOFUNCTION` (<<libcurl-api>>), with a `CurlTransferProgress`: `DownloadNow` and `DownloadTotal` for the response body, `UploadNow` and `UploadTotal` for a request body, the average speeds, and `Phase`. `DownloadTotal` comes from the response's `Content-Length`, here 16777216. The reports come while `CurlClient.SendAsync`{apos}s `CurlResponse` body is being read: each quarter line is printed before the program's own `body read to its end`, so the line tracks the bytes as they arrive, not after. They never go back, there are ten or more for this file, and the last says 16777216 of 16777216.

`Report` runs on the engine's own thread, one report at a time and in order, so `QuarterLine` keeps its state in plain fields and writes from there. That is why it implements `IProgress<T>` itself rather than using .NET's `Progress<T>` class, which hands each report on to another thread to be handled later. Keep `Report` short; the transfer is the engine's to get on with.

`Phase`, a `CurlTransferPhase`, says which way the bytes are moving: `Connecting` until the response body has a size or a byte, then `Downloading` (`Uploading` belongs to a request body). For a path the server does not have, the answer is `404 Not Found` (<<rfc9110>>) with a short text body of 14 bytes, and the reports treat it as any other download: they reach `Downloading` and `QuarterLine` prints all four quarters of 14 bytes. Progress counts bytes, not success, so read `StatusCode` before telling anyone the fetch finished. A `DownloadTotal` of 0 means the size is not known; Curl.Api documents it for a body whose size is not known yet (<<curl-readme>>), and `QuarterLine` prints no percentage then, so a tool facing a server that sends no `Content-Length` would need a byte count instead.
