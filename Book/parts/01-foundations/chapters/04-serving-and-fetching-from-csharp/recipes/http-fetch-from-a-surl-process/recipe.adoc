==== Discussion

The server here is the one from <<http-serve-a-directory>>: `surl` with `--directory site` serves every file under `site` at its relative path, so `site/hello.txt` is `http://127.0.0.1:8080/hello.txt`. The program knows nothing about it except the URL on its command line, which is the point: `Curl.Api` is a client for any server, and a `surl` process is one.

`CurlClient.Create()` makes a client over an engine it owns. `CurlRequest` is the method and the URL; `CurlClient.SendAsync` sends it and returns a `CurlResponse` once the status line and headers are in. `Body` is the body as a stream still arriving, disposed when done.

There are two different kinds of bad news, and the program sees them differently. A server that answers with an error status has still answered: a path the directory does not hold comes back as a `CurlResponse` whose `StatusCode` is `404`, and nothing throws, exactly as `curl` exits `0` on a `404` unless `-f` is given. This program plays `-f`: it writes the status to standard error and exits `22`, as `curl -f` would. That choice is the program's, not the library's.

No answer at all is a `CurlException`, and its `Code` is the `CurlCode` the `curl` command line would exit with for the same failure, so the program returns it as its own exit code. A port nothing listens on is `7`, `CouldntConnect`. A URL that cannot be parsed is `3`, `UrlMalformat`. A scheme `curl` has no protocol for is `1`, `UnsupportedProtocol`. The exception's message is `curl`{apos}s own error text. `CurlException` lives in the `Curl.Api.Errors` namespace and `CurlCode` in `Curl.Api.Codes`, so a program that names either needs the matching `using`.
