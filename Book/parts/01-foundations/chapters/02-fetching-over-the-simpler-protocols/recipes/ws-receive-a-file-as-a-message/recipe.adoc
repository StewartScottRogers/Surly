==== Discussion

A WebSocket connection starts as a Hypertext Transfer Protocol (HTTP) `GET` that asks to _upgrade_; a server that agrees answers `101 Switching Protocols`, and from then on the two sides exchange messages on the same connection instead of requests and responses. `surl` has nothing to say of its own on such a connection, so it sends the file at the request path: `--directory site` makes `ws://127.0.0.1:8080/hello.txt` the file `site/hello.txt`, sent as one message and followed by a close (<<surl-readme>>). `curl` writes the message's bytes as it would a download, to standard output or, with `-o copy.txt`, to that file, byte for byte.

`-w "%{http_code}"` prints the status of the upgrade: `101` when it was accepted. `-s` keeps the progress meter and error messages quiet, and `-o /dev/null` (`NUL` on Windows) throws the body away when only the status matters.

`surl` refuses an upgrade it will not take with an ordinary HTTP status, as the WebSocket protocol says it should: a path that is not there, or a file whose name begins with a dot, `404 Not Found`; a method other than `GET`, which `-X POST` sends here, `405 Method Not Allowed` (<<rfc9110>>). For `curl`, any answer to an upgrade but `101` is a failure, so it exits `22` whether or not `-f` was given, where an ordinary HTTP transfer would exit `0`.

A plain HTTP `GET` with no upgrade, sent to the same listener as `http://127.0.0.1:8080/hello.txt`, is answered `426 Upgrade Required`: the listener speaks only WebSocket. That is an ordinary HTTP transfer, so `curl` exits `0` and reports the `426`.

No login is needed because no account is configured; once one is, the upgrade needs one, as an HTTP `GET` would (<<surl-readme>>, and see <<wss-log-in-over-tls>>).
