=== Downloading Anonymously over File Transfer Protocol

==== Problem

A test needs to download a file over File Transfer Protocol from a local server, with no accounts to set up and no passwords to manage.

==== Discussion

File Transfer Protocol (FTP) has no request without a login: every session starts with `USER` and `PASS`. When the URL names no user, `curl` logs in as `anonymous` with a placeholder password, and that is all this recipe asks the server to take. `-v` shows the conversation on standard error, `USER anonymous` included; `-o` sends the file itself elsewhere while you read it.

`--directory site` serves the files under `site` at their relative paths, so `site/hello.txt` is `ftp://127.0.0.1:8080/hello.txt`. A file whose name begins with a dot is not served, anonymous or not.

`--allow-anonymous` is what lets the login in. It logs in every `USER` and `PASS`, checking nothing: `curl`'s anonymous login, and equally any made-up name and password given with `-u`, sent in clear over a connection anyone on the network could read. It is not the default because anyone who can reach the listener then gets everything `surl` serves, with no login at all. Without it, `surl` refuses `curl`'s anonymous login with `530` and `curl` exits `67`, login denied (<<surl-readme>>); and since a password sent over `ftp://` without Transport Layer Security (TLS) is refused unchecked, the way to download without this option is an account and a TLS-protected login (see <<ftp-protect-the-login-with-tls>>). Use `--allow-anonymous` for a test on your own machine, and nowhere a stranger can connect. `surl` writes a `surl: warning:` line when it starts with the option on, so the loosening is never silent.

A file that is not there is answered `550`, and `curl` exits `78`, remote file not found, writing nothing; `-s` keeps `curl` from printing its progress meter and error message, so the exit code is the only answer. Exit `0` means the whole file arrived (<<curl-readme>>).
