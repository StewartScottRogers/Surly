=== Running curl from an Agent

==== Problem

You want an artificial intelligence (AI) agent to run `curl` with the options it already knows from the command line and read back its exit code and output, as a script would.

==== Solution

Write the agent's side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it starts a server with `surl-mcp`{apos}s `start_server`, then calls `curl-mcp`{apos}s `curl` tool with `curl`{apos}s arguments as a list and prints the answer:

==== Discussion

`curl-mcp` is `curl` as an MCP server, and `surl-mcp` is `surl` as one. The program starts both by name from `PATH` with `StdioClientTransport`, as an agent's MCP client would, and confines each to the folder it runs in with `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. `start_server` here only gives `curl` something to talk to: a Hypertext Transfer Protocol (HTTP) server on a free port with `hello.txt` in memory, whose first `bound_urls` entry the program keeps in `url`. The argument after `--` picks which `curl` arguments the program sends; with none, it sends the solution's.

The `curl` tool takes `args`, `curl`{apos}s command-line arguments without the program name, one list item per argument, so there is no shell quoting to get wrong. It runs `curl` in-process and answers, in text the program parses as JavaScript Object Notation (JSON), `exitCode`, `standardOutput` and `standardError`, each stream as an object whose `content` is the text; the program prints each `content` as JSON spells it, so a line feed shows as `+\n+`. `-s` keeps the progress meter out of `standardError`, which matters more here than on a terminal: the agent reads every byte of it.

`-w "%{http_code}"` prints the status after the body. The `404 Not Found` for a missing path carries a short text body, `404 Not Found` and a line feed, so `standardOutput` is that line with `404` after it; read the status from the end, where `-w` put it. `curl` exits `0`, because to `curl` a 404 is a successful conversation. The call is not a tool error. `-f` asks `curl` to fail on an error status, and it exits `22`. A nonzero exit is a tool error, `IsError` on the result, and the program exits 1. The answer is still the whole result: `exitCode` is 22, and `failure` has `kind` `CurlExit`, the same code, and a `text` naming it, `HttpReturnedError`. `-S` with `-s` restores `curl`{apos}s own error message, `The requested URL returned error: 404`, which then appears in `standardError` and at the head of the failure's `text`. An agent should branch on `exitCode`, and read the message only to explain.

`-o` writes the body to a file, so `standardOutput` holds only what `-w` prints, `200`, and the program finds `hello.txt` in its folder holding the body. Every file `curl` reads or writes must be inside the folder `CURL_MCP_ROOT` names, and a relative path resolves against it. A path outside it, such as `../hello.txt`, is refused before `curl` runs: the tool error's `failure` has `kind` `PathRefused` and names the folder, and `exitCode` and both streams are null, because there was no `curl` to exit. An option `curl-mcp` does not know is refused the same way, since it cannot tell whether that option names a local path. That is the host being surly on purpose: an agent reaches the disk only where the person who started the host allowed.
