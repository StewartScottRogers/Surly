=== Receiving a File over WebSocket

==== Problem

You want an artificial intelligence (AI) agent to fetch a file over WebSocket and check that what arrived is exactly what the server holds.

==== Solution

Write the agent's side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it starts a WebSocket server with `start_server`, receives the file with `curl-mcp`{apos}s `curl` tool, and compares it with `surl-mcp`{apos}s `read_file`:

==== Discussion

`StdioClientTransport` starts `surl-mcp` and `curl-mcp` by name from `PATH`, and `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine both to the folder the program runs in. The argument after `--` picks the scenario.

`start_server` with the listen URL `ws://127.0.0.1:0` starts a WebSocket (<<rfc6455>>) server on a free port. `files` puts `hello.txt` in its store as text and `files_base64` puts `logo.bin` there as bytes. A WebSocket server in `surl` serves files: a client that opens a connection on a file{apos}s path is sent the file as one message.

The `curl` tool runs `curl` with the `args` list as its command line, here `-s` and the URL, and answers in text as JavaScript Object Notation (JSON). `curl` given a `ws://` URL opens the connection and writes the message it receives to standard output. The tool hands standard output back as `standardOutput`: `content` is the text, `totalBytes` its size, and `isBase64` says whether `content` had to be base64 because the bytes are not UTF-8.

`read_file` reads the same path from the server{apos}s store directly, with no protocol in the way, and answers `text` when the bytes are UTF-8 and `base64` when they are not. For `hello.txt` both tools answer the same 16 bytes as text; for `logo.bin` both answer the same six bytes as base64. Comparing like with like, the agent knows the message is the file, not just a file of the right size.

`get_exchanges` shows the conversation as the server saw it: the upgrade request, the `101 Switching Protocols` head, then the frames in base64. The first frame starts `0x82`: the final frame of a binary message. The second byte, `0x10`, is the length, 16, and the 16 bytes follow.

A path the server does not have is refused at the upgrade, before any message: `curl` exits `22`, the `curl` tool answers it as a tool error with `standardOutput` empty, and `read_file` says `No file at /missing.txt.`. An agent that only read `content` would see an empty file; `exitCode` and the tool error tell it there was none.
