=== Reading the Client's Request from an Agent

==== Problem

Your artificial intelligence (AI) agent is testing a client and needs to see the exact request it put on the wire, headers and all, not only what the client printed.

==== Solution

Write the agent's side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it starts a server with `surl-mcp`'s `start_server`, lets `curl-mcp` make the request, then calls `get_exchanges` with the server's ID and prints what crossed the wire:

==== Discussion

The program starts `surl-mcp` and `curl-mcp`, the two programs' MCP servers, by name from `PATH` with `StdioClientTransport`, and confines each to the folder it runs in with `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. `start_server` starts a Hypertext Transfer Protocol (HTTP) server on port 0, a free port, and answers its `server_id` and `bound_urls`, which the program keeps in `id` and `url`. `transfer`, from `curl-mcp`, is the client under test: one `GET` for `hello.txt`. The argument after `--` picks the scenario; with none, the program runs the solution.

`get_exchanges` answers, in structured content, what each client sent to the server and what the server sent back, byte for byte, oldest first. Each exchange has an `exchange_id` counting from 1, the `listen_url` and `scheme` it came through, and `chunks`: each with a `direction` (`received` from the client, `sent` to it), the `layer` (`wire`, the bytes on the connection) and the `data`, as text when the `encoding` is `text`, as it is here. The program prints each exchange's first and last chunk, with the `data` as JavaScript Object Notation (JSON) spells it, so each carriage return and line feed shows as `+\r\n+`. The first chunk is the whole request: request line, `Host` naming the port the server bound, `Accept: */*`, and the blank line that ends the header section (<<rfc9110>>). There is no `User-Agent` line: `transfer` sends none when not asked to. The response follows in later chunks, its body last.

The `curl` tool is the second client, in the other scenarios. Its `-s` keeps it quiet, and `-A` names the `User-Agent` it sends, which the second exchange shows on the wire as `User-Agent: surly-reader`.

The record grows with every request, so `get_exchanges` pages it. `after_exchange_id` asks for the exchanges after one already read, and `has_more` false says the agent has the rest. `max_exchanges` caps one answer, and `has_more` true says to ask again. `scheme`, matched without regard to case, and `listen_url`, spelled as `bound_urls` spells it, keep only what came through that kind of listener or that one listen URL; on a server with one listener, they keep everything, here both exchanges. A server ID this host is not running is a tool error, `IsError` on the result, whose text is `no running server has ID s9`; the program prints it and exits 1.
