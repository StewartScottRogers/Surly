=== Serving and Fetching Files from an Agent

==== Problem

You want an artificial intelligence (AI) agent to stand up a throwaway Hypertext Transfer Protocol (HTTP) server with a file in it and fetch that file back, with Model Context Protocol (MCP) tool calls and no shell.

==== Solution

Write the agent's side as a C# program on the official MCP software development kit (SDK): it starts `surl-mcp` and `curl-mcp`, calls `start_server` with a listen URL on port 0 and the file's content, then calls `transfer` on the URL the server bound:

==== Discussion

`surl-mcp` and `curl-mcp` are the two programs' MCP servers. The program is the agent's MCP client: `StdioClientTransport` starts each host by name from `PATH` as a process on standard input and output, and `McpClient.CreateAsync` performs the MCP handshake. `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine each host to the folder the program runs in. They are environment variables rather than arguments because on Windows the SDK starts a host through `cmd.exe`, which mangles a path with a space in it. `mcp.json` beside this recipe is the same configuration for an agent's own client. The argument after `--` picks the scenario; with none, the program runs the solution.

`start_server` starts a server that answers as `surl` with the same options would. `listen_urls` is `surl`{apos}s listen URLs, and port 0 asks the system for a free port, so two agents never fight over 8080. `surl-mcp` answers in structured content, which the SDK hands over as `StructuredContent`, a JavaScript Object Notation (JSON) element. It echoes `listen_urls` as given and adds `bound_urls`, the URLs actually listening, with the real port; the program fetches from `bound_urls`, never from what it asked for. `files` puts content in the server's store in memory, relative path to UTF-8 text.

`transfer` makes one request described by fields rather than a command line: `url` is the only one this recipe needs. `curl-mcp` answers only in text, so the program parses the one `TextContentBlock` as JSON. The answer has `statusCode`, `headers` as a list of `name` and `value` pairs (the `headers` scenario finds `Content-Type: text/plain` among them), and `body` with its `content` as text and `isBase64` false when the bytes are valid UTF-8. A `404 Not Found` (<<rfc9110>>) is an answer, not a failure: `statusCode` is 404, `failure` is null, the body is the one line `404 Not Found`, and the call is not a tool error. The agent reads the status; nothing is thrown at it. The program prints whether its last call was a tool error, `IsError` on the result, and exits 1 if it was.

The two hosts are surly in the same direction. A second server on an address and port already in use is a tool error whose structured content carries `surl`{apos}s own exit code, `exit_code` `45` with `exit_code_name` `BindFailed`, and whose text is `surl`{apos}s message, so an agent can act on the code as a script acts on `surl`{apos}s. A listen host that is not loopback, such as `0.0.0.0`, is refused outright: exposing a test server to the network is a decision for whoever starts `surl-mcp`, with `--allow-non-loopback`, not for the agent driving it. `transfer` refuses `file:` URLs as an `InvalidRequest` and says to use the `curl` tool, which confines local files to its root (see <<http-run-curl-from-an-agent>>).
