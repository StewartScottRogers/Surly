=== Choosing the HTTP Version from an Agent

==== Problem

You want an artificial intelligence (AI) agent to fetch a file in HTTP/1.0, HTTP/1.1 and HTTP/2 with prior knowledge (the versions of the Hypertext Transfer Protocol), and report which version answered each.

==== Solution

Write the agent's side as a C# program on the Model Context Protocol (MCP) software development kit (SDK): it starts a server with `surl-mcp`, runs `curl-mcp`{apos}s `curl` tool once per version option with `-w "%{http_version}"`, and reads what the server received with `get_exchanges`:

==== Discussion

`start_server` on `surl-mcp` starts one plain `http://` listener on a free port and answers its `bound_urls` in structured content. One listener is enough: `surl` speaks HTTP/1.0, HTTP/1.1 and HTTP/2 on it alike.

The version is chosen with the `curl` tool, which takes `args`, the arguments of a `curl` command line, and answers in text a JavaScript Object Notation (JSON) object with `exitCode`, `standardOutput` and `standardError`. The options are `curl`{apos}s own: `--http1.0`, `--http1.1`, and `--http2-prior-knowledge`, which starts talking HTTP/2 at once over plain `http://` instead of asking to upgrade. `-o body.txt` keeps the body out of `standardOutput`, which the tool writes inside `CURL_MCP_ROOT`; `-w "%{http_version}"` then makes `standardOutput` the version of the answer, `1.1` or `2`; `-s` keeps the progress meter out.

The `transfer` tool cannot do this. Its arguments describe a request, `url`, `method`, `headers` and a few more, but not the version: it answers `info.httpVersion` `1.1`, and `surl` received an HTTP/1.1 request. For any choice `transfer` has no field for, the `curl` tool is the way.

The answer{apos}s version is not the whole story. `get_exchanges` on `surl-mcp` answers each exchange{apos}s `chunks`, and the first one the server received holds the request. For `--http1.0` its first line is `GET /hello.txt HTTP/1.0`, yet `-w` reports `1.1`: `surl` answers an HTTP/1.0 request with an HTTP/1.1 status line, which a server may do (<<rfc9110>>). An agent asked to prove the client spoke HTTP/1.0 must read the request, not the response. For `--http2-prior-knowledge` the request is binary frames, so the chunk comes back base64-encoded and the program decodes it; it starts with the HTTP/2 connection preface, `PRI * HTTP/2.0` (<<rfc9113>>), and the answer is `2`.
