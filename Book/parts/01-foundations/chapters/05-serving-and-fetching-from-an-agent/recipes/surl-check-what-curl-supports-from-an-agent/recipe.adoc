=== Checking What curl Supports

==== Problem

You want an artificial intelligence (AI) agent to learn which protocols and features this `curl` has before it plans a task, so that it does not build a plan on a scheme `curl` cannot speak.

==== Solution

Write the agent{apos}s side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it starts `curl-mcp` and calls `version`, which takes no arguments, and reads the protocols and features from the answer:

==== Discussion

`curl-mcp` and `surl-mcp` are the two programs{apos} MCP servers; the program is the agent{apos}s MCP client, and `StdioClientTransport` starts each by name from `PATH`. `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine each to the folder the program runs in, as environment variables rather than arguments because on Windows the SDK starts a host through `cmd.exe`, which mangles a path with a space in it. The argument after `--` picks the scenario; with none the program asks `version` and prints the fields it needs.

`version` reports what `curl -V` reports about `curl`{apos}s transfer engine, as JSON in a text answer. `version` is the number, `8.22.0` or whatever this build is, and `versionLine` the first line of `curl -V`, which begins with it. `protocols` lists the schemes `curl` speaks, such as `ftp` and `tftp`; `extendedProtocols` lists more, which this `curl` speaks beyond the stock ones, such as `redis`, so an agent must look in both. `features` lists the build{apos}s features, `SSL` among them, and `tlsBackend` names the library that does the Transport Layer Security (TLS) work. Which features and which backend a build has depends on the platform it was built for, so the program prints only that `SSL` is a feature and that the backend has a name. An agent that needs another feature asks for it by name and plans around a missing one.

The second scenario runs `curl -V` through the `curl` tool, which runs `curl` with `args` as its command line, and compares: its first line is `versionLine`, every protocol that `version` lists is in its `Protocols:` line, and its `Features:` line holds the same features. The two are one source of truth in two shapes, and the agent can take whichever is easier to read.

The third scenario is the plan. For each scheme the agent{apos}s task needs, the program asks both hosts: `version` whether `curl` speaks it, and `start_server` with `listen_urls` of that scheme on port 0 whether `surl` serves it. A scheme `surl` does not know, here `carrier-pigeon`, is a tool error from `start_server` and absent from `curl`{apos}s lists, so the plan is changed before any work is done. Each host is asked, because each answers only for itself.
