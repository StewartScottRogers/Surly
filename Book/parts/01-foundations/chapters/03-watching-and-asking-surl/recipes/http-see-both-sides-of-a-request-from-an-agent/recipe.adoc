=== Seeing Both Sides from an Agent

==== Problem

An artificial intelligence (AI) agent{apos}s upload is answered `405 Method Not Allowed`. You want the agent to compare `curl`{apos}s verbose output with the bytes the server recorded, and explain the refusal from both, with Model Context Protocol (MCP) tools only.

==== Solution

Write the agent{apos}s side as a C# program on the official MCP software development kit (SDK): it uploads with `curl-mcp`{apos}s `curl` tool and `-v`, then reads `surl-mcp`{apos}s `get_exchanges` and the `login_judged` events from `get_events`, and prints the lines that matter from each:

==== Discussion

`StdioClientTransport` starts each host by name from `PATH`, and `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine both to the folder the program runs in, where `notes.txt` is. The argument after `--` picks the scenario.

`start_server` starts a server with one account, `--user alice:s3cret` in `arguments`, and without `--allow-uploads`. The `curl` tool runs `curl -T notes.txt`, a `PUT` of the file, with `--digest -u alice:s3cret` for Digest access authentication (<<rfc7616>>) and `-w "%{http_code}"` for the status (<<curl-manual>>); `-o reply.txt` keeps `surl`{apos}s short text body, such as `405 Method Not Allowed`, out of standard output. `-v` writes `curl`{apos}s side of the conversation to standard error, which the tool returns in `standardError.content`: lines marked `>` were sent and `<` received. On Windows they can end in a carriage return, so the program trims them. The upload is answered `405`, and the call is not a tool error: `curl` exits 0 for any status without `-f`.

`curl`{apos}s side shows the `PUT` sent twice. Digest needs a challenge, so the first goes without credentials and is answered `401 Unauthorized`; the second carries the answer to the challenge and is answered `405` with `Allow: GET, HEAD`, the methods the server takes there (<<rfc9110>>). `get_exchanges` shows the same exchange from the server{apos}s side, chunk by chunk, `direction` `received` or `sent`, with the `Authorization` header kept exactly as it arrived; the program prints only up to its first comma. Where the two sides agree, the bytes are not the problem.

`get_events` with `kinds` `["login_judged"]` gives the reason the bytes cannot: one event for `alice`, `mechanism` `Digest`, `is_accepted` true. A refusal after an accepted login is the server{apos}s configuration, here uploads not allowed. The server judges the login before the method (<<surl-readme>>), so the three answers an agent can meet read differently. With the wrong password both answers are `401` and the event says `refused`. With no login there is one `401` and no event, because nothing was offered to judge. With a good login and `405`, the method is the problem, and against a server started with `--allow-uploads` the same call is answered `201 Created`. Uploads are off by default because a server that accepts writes is a decision for whoever starts it, not for the agent writing to it.
