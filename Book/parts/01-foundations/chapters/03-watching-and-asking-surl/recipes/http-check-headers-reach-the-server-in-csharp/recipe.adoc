=== Checking Headers Reach the Server in C#

==== Problem

Your C# client adds an application programming interface (API) key and a trace ID header to every Hypertext Transfer Protocol (HTTP) request it makes. You want a test that reads the requests as the server received them and fails unless each header arrived exactly once.

==== Solution

==== Discussion

`SurlServerOptions.RecordExchanges` makes the in-process server keep every byte of every exchange; it is off by default, and reading `SurlServer.Exchanges` with it off throws. Each `SurlExchangeRecord` is one connection, so the two requests here, sent by one `CurlClient` over a kept-alive connection, may share one record. The test does not care: it joins the `Received` bytes of every record and splits them at the blank line that ends each request head. These requests have no body, so what lies between two blank lines is exactly one head.

`Build` stands in for the code under test. It makes each `CurlRequest` with `Headers`, a list of name and value pairs that `CurlClient` sends in that order and with that casing, beside the one `Accept` header it adds of its own. `CurlResponse.Body` is drained before the next request, so the connection is free for it.

`Headers` is sent as given, duplicates included; nothing merges two entries of the same name. When the caller adds a trace ID the helper already added, both arrive, in order, and the test exits `1`. That is the failure this test is for: a header added at two layers of a client reaches the server twice, and the server may keep either value.

An empty value goes on the wire as the name, a colon and nothing else, `X-Api-Key:`. The count still finds one, so a test that cares whether the key is right must compare the value too. `RemovedHeaders` names default headers the client should not send: `["Accept"]` leaves the request with no `Accept` at all, as `-H "Accept:"` does on the console.
