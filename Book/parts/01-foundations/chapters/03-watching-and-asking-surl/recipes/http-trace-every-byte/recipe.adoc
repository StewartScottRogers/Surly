=== Tracing Every Byte surl Sends and Receives

==== Problem

A client and `surl` disagree about what was said, and the log lines are not enough: you want every byte that went each way, with the time it went.

==== Solution

Start `surl` with `--trace-ascii` and `--trace-time`, then make the request:

Stop `surl` with kbd:[Ctrl+C], then read the trace file.

==== Discussion

`--trace-ascii site/trace.txt` sets the trace level and names the file the trace goes to: the bytes `surl` receives and sends, shown as text. A `+<= Recv data+` line gives how many bytes came in, in decimal and in hexadecimal, and the bytes follow as text, one line each, led by their offset in hexadecimal. `+=> Send data+` does the same for what went out: one block for the Hypertext Transfer Protocol (HTTP) response head and one for the body. A byte that is not printable text is shown as a dot, which is why the body `hello from surl` and its newline appear as `hello from surl.`. The log lines come along in the same file, such as the `*` line saying what was served and from which file, so the trace reads as one story.

The trace file is inside `site`, which `--directory site` serves, only so that the checks below can fetch it with `curl`; keep yours outside the served folder, since anyone who can reach the listener can otherwise read every byte anyone else sent.

`--trace-time` stamps each entry with the time of day to the microsecond, so a slow answer shows as a gap between a `+<= Recv data+` and the `+=> Send data+` after it.

A trace file that cannot be opened, such as one in a folder that does not exist, stops `surl` before it listens, with exit code `23`. So does a trace file that is also the `--log-file` file, since two writers on one file would interleave into nonsense.

On the client side, `-s` keeps `curl` quiet while it fetches the trace.
