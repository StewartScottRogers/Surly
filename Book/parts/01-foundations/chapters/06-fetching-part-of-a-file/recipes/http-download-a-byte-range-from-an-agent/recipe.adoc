=== Fetching a Byte Range from an Agent

==== Problem

You want an artificial intelligence (AI) agent to read just a slice of a large file over Hypertext Transfer Protocol (HTTP), with Model Context Protocol (MCP) tool calls, and to recognise the answer, and the file's length, when it asks for bytes past the end.

==== Solution

Write the agent's side as a C# program on the official MCP software development kit (SDK): it starts `surl-mcp` and `curl-mcp`, calls `start_server` with the file, then calls `transfer` with a `Range` header and reads the status, the `Content-Range` and the body:

==== Discussion

`surl-mcp` and `curl-mcp` are the two programs' MCP servers; the program starts each by name from `PATH` with `StdioClientTransport`, confined to the folder it runs in by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. `mcp.json` beside this recipe is the same configuration for an agent's own client. The arguments after `--` pick the tool and the range.

`start_server` starts a server on a free port with `records.txt` in memory, thirty lines of ten bytes, 300 bytes in all, so byte 100 starts `record 10`; the program fetches from the first of its `bound_urls`. `surl` serves ranges of any file it serves, with nothing to switch on.

`transfer` has no range field. The range goes in its `headers` list as `Range: bytes=100-199` (<<rfc9110>>): first and last byte, counted from zero, both included. The answer is text holding JavaScript Object Notation (JSON): `statusCode` `206`, a `Content-Range` of `bytes 100-199/300` among the `headers`, the bytes sent before the slash and the whole file's length after it, and `body` with `totalBytes` `100` and the bytes as `content`.

A range that starts past the end gets `416` with `Content-Range: bytes */300` and a 26-byte body, `416 Range Not Satisfiable`, that holds none of the file. To `transfer` that is an answer, not a failure: `failure` is null and the call is not a tool error, so the agent has to read `statusCode`. The `Content-Range` tells it how long the file is, so it can ask again for bytes that exist. A range with its end before its start is ignored, and the whole file comes back with `200` and no `Content-Range`; an agent that asked for a slice should check for `206` before trusting the body. Two ranges in one header come back as `206` with a multipart body, each part carrying its own `Content-Range` between boundary lines, and no `Content-Range` on the response itself.

The `curl` tool runs `curl` with the arguments given, so `-r 100-109` asks for a range as on the console and the bytes come back in `standardOutput`, followed here by the status that `-w "%{http_code}"` prints. With `-f`, the `416` makes `curl` exit `22`, and `curl-mcp` reports that as a tool error with a `failure` of kind `CurlExit`; `-s` keeps `curl`{apos}s own messages out of the answer. Pick `transfer` to read the status and headers yourself, and the `curl` tool with `-f` to have a range past the end fail outright.
