=== Skipping Unchanged Files with ETags in C#

==== Problem

A sync job in your .NET code should fetch only what changed: the first run takes every file and keeps its entity tag, the next run gets `304 Not Modified` for the files the server has not changed, and a file changed between runs is fetched again, and a test should prove it.

==== Solution

Host the files in a `SurlServer` that runs on a clock the test moves, and have the job send each `GET` with the tag saved from the last fetch in an `If-None-Match` header, keeping the body only when the answer is `200`:

==== Discussion

`SurlServerOptions.Files` holds `a.txt` and `b.txt` in memory. `TimeProvider` is the one clock the server runs on, and the file times come from it. `TestClock` is a `TimeProvider` that stands still at 2 January 2024 until the test calls `Advance`, so the tags and dates do not depend on when the test runs and a change can be put exactly five seconds, or zero seconds, after the last one. `RecordExchanges` keeps the bytes each client sent and the server sent back, which the program reads at the end to count the requests and the answers.

`surl` sends every file with an entity tag (ETag), a validator that changes whenever the file does (<<rfc9110>>). Its tag is strong, made from the file{apos}s write time and its length in hexadecimal (<<surl-readme>>): `alpha` and a newline is 6 bytes, and its tag ends in `-6`.

The job is `Sync`. For each file it sends a `CurlRequest` with `HttpMethod.Get`, and, once it has a copy, a header `If-None-Match` holding the saved tag. A `304` means the copy is current: the answer has no body and the job keeps what it has. A `200` carries the body and a new `ETag`, read from `CurlResponse.Headers`; the job writes the body to `local-<case>/` on disk and keeps it with the tag. The `tags` case prints each answer: a `304` carries the very tag the job saved. One `CurlClient` serves every request.

The first run fetches both files. The second sends both tags and gets two `304` answers. `server.Files.PutAsync` then rewrites `a.txt` with the clock five seconds on, and the third run fetches `a.txt` alone: six `GET` requests in all, three answered `200` and three `304`, and on disk `local-changed/a.txt` holds the revised text.

The other cases are where a date would fall short. `Last-Modified` counts whole seconds (<<rfc9110>>), so a rewrite in the same second carries the same date; its tag changes, here by its new length, and the third run fetches it. A file rewritten with an earlier date, as a restore from a backup can do, gets a new tag too and is fetched. With the clock moved five seconds back, `b.txt`{apos}s `Last-Modified` also moves back to 15:04:00, because `surl` sends none later than its `Date`; a job comparing dates would fetch it again for nothing, but its tag has not changed and the server still answers `304`. A file deleted on the server answers `404 Not Found`. `SendAsync` does not throw for it; the job sees the status and keeps its local copy, rather than overwrite it.
