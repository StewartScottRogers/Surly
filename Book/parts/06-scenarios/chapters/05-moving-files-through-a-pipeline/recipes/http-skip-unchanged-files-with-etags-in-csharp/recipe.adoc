=== Skipping Unchanged Files by Date in C#

==== Problem

A sync job in your .NET code should fetch only what changed: the first run takes every file, the next skips the ones the server has not changed, and a file changed between runs is fetched again, and a test should prove it.

==== Solution

Host the files in a `SurlServer` that runs on a clock the test moves, and have the job send a `HEAD` for each file and a `GET` only when the `Last-Modified` it gets differs from the one saved with the local copy:

==== Discussion

`SurlServerOptions.Files` holds `a.txt` and `b.txt` in memory. `TimeProvider` is the one clock the server runs on, and the file times and the `Last-Modified` header come from it. `TestClock` is a `TimeProvider` that stands still at 2 January 2024 until the test calls `Advance`, so the dates do not depend on when the test runs and a change can be put exactly five seconds, or zero seconds, after the last one. `RecordExchanges` keeps the bytes each client sent, which the program reads at the end to count the requests the server answered.

The job is `Sync`. For each file it sends a `CurlRequest` with `HttpMethod.Head`, which returns the headers and no body, and reads `Last-Modified` from `CurlResponse.Headers`. If it saved that same value with its local copy, the file is unchanged and no `GET` is sent; otherwise it sends the `GET`, reads the body, writes it to `local-<case>/` on disk and keeps it with the new date. An unchanged file{apos}s `HEAD` is answered `200` with the very `Last-Modified` saved with the copy, `Tue, 02 Jan 2024 15:04:05 GMT` from the test{apos}s clock; the `dates` case prints both. One `CurlClient` serves every request.

The first run fetches both files. The second finds both dates unchanged and sends only the two `HEAD` requests. `server.Files.PutAsync` then rewrites `a.txt` with the clock five seconds on, and the third run fetches `a.txt` alone: its `Last-Modified` is now 15:04:10, six `HEAD` and three `GET` requests in all, and on disk `local-changed/a.txt` holds the revised text.

The failure paths are where a date falls short. `Last-Modified` counts whole seconds (<<rfc9110>>), so a rewrite in the same second carries the same date: the third run calls `a.txt` unchanged and the local copy stays stale. An entity tag (ETag), a validator the server changes with the content, would catch it; Surl is adding entity tags and conditional requests, and until a recipe shows them, this one relies on dates alone. The comparison is for equality, not for newer, and that differs from `curl -z` on the console. A file rewritten with an earlier date, as a restore from a backup can do, is fetched again here, where `-z` would skip it. With the clock moved five seconds back, `b.txt` is fetched again too, unchanged: its stored date now lies ahead of the server{apos}s clock, and `surl` sends a `Last-Modified` no later than its `Date`, 15:04:00 for both. A spurious fetch is the cheap mistake; a missed change is the costly one. A file deleted on the server answers the `HEAD` with `404 Not Found`. `SendAsync` does not throw for it; the job sees the status and keeps its local copy, rather than overwrite it with nothing.
