=== Handling a Full Disk During Upload

==== Problem

As an agent, you test a pipeline step that uploads tonight{apos}s export over File Transfer Protocol (FTP) for the next step to read over Hypertext Transfer Protocol (HTTP). You want one upload path to report out of space, and proof that the uploader reports the failure and leaves no half-written file behind.

==== Solution

Write the agent{apos}s side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK). It starts one server with `surl-mcp` behind an FTP and an HTTP listener, with `/archive` out of space; uploads with `curl-mcp`{apos}s `curl` tool, reads the path back with its `transfer` tool, and looks in the store with `read_file`:

==== Discussion

`start_server` starts a server as `surl` with the same `arguments` would. Its two `listen_urls`, `ftp://` and `http://` on free ports, serve one store, so what the uploader writes is what the next step reads; `bound_urls` lists them in that order. `--allow-anonymous` lets the client log in with no account, `--allow-uploads` turns on writing, and `--max-filesize 100000` gives each file 100,000 bytes of room. `--fault "out-of-space;path=/archive"` makes every store under `/archive` fail as a full disk would; a fault loosens the server on purpose and is for tests only. `files` holds last night{apos}s export and an `/incoming` folder.

The `curl` tool runs one `curl` command line given as `args`, reading the export from the folder `CURL_MCP_ROOT` names: `-T` uploads it, `-sS` keeps the answer to errors only. Into `/archive` the answer is `exitCode` 25 and a tool error, with `curl: (25) Failed FTP upload: 552` in `standardError`; `552` is the reply FTP keeps for exceeded storage (<<rfc959>>). That is the uploader{apos}s report.

The `transfer` tool makes one request from fields, here only a `url`, and answers `statusCode` and `body`. The next step{apos}s read of `/archive/2026-11-20.csv` is `statusCode` 404 with a short error text for its body, `404 Not Found`, and not a tool error: a missing file is an answer (<<rfc9110>>), so an agent that skips the status would carry on with that text as if it were the export. `read_file` reads the store by `server_id` and `path` and answers `byte_count`; for the path that was refused it is a tool error, `No file at /archive/2026-11-20.csv.` Last night{apos}s export there is still served unchanged. The same export to `/incoming` is stored, comes back over HTTP as itself, and is 22 bytes in the store. `get_events` with `kinds` `fault_applied` lists each time a rule acted, with its `rule_id`, its `fault_kind`, `out_of_space`, and its `target`: once for the refused `/archive` upload, never for `/incoming`.

A 300,000-byte export to `/incoming` runs out of room partway: the server stops it at 100,000 bytes, answers `552` and resets the data connection. `curl` waits for that reply when its write fails, so the `exitCode` is `70`, `Exceeded storage allocation`, and the answer is a tool error, which is what an agent should act on. Nothing half-written is left: the next step gets 404 and `read_file` finds no `big.csv`. That refusal is the size limit, not the rule, so `get_events` lists no `fault_applied` for it.

The rule is on the path, not the listener: the `curl` tool{apos}s `-T` to the `http://` listener is an HTTP `PUT`, answered `413`; `-f` makes that `exitCode` 22 and `-w "%{http_code} "` prints the status. Nothing is stored, and the rule shows in `get_events`.
