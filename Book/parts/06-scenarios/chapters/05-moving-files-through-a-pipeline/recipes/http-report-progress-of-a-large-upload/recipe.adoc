=== Reporting Progress of a Large Upload

==== Problem

Your .NET code uploads large files and should report progress as it goes, and you want a test to check that the reports climb to the full size and that the server stored exactly that much.

==== Solution

Give the `CurlRequest` an `IProgress<CurlTransferProgress>` that records every report, upload 16 MiB to an in-process `SurlServer` that takes uploads, and compare the last report and the stored file with what was sent:

==== Discussion

`SurlServerOptions.AllowUploads` is `surl --allow-uploads`: without it the server takes no `PUT`. `AllowAnonymous`, `surl --allow-anonymous`, lets a client in with no login. Both loosen `surl`{apos}s defaults on purpose, for a test; the second case leaves `AllowUploads` off to show the refusal. The program fetches `warm-up.txt` first, because the first request in a process sets up the engine and takes a few seconds.

The upload is a `CurlRequest` with `HttpMethod.Put`. `CurlContent.FromStream` sends its body from a stream, read as the engine asks for it, and the length given with it is the size the engine announces. `CurlRequest.Progress` takes an `IProgress<CurlTransferProgress>`, and the `CurlClient` calls its `Report` each time libcurl{apos}s progress callback runs (<<libcurl-api>>). Each `CurlTransferProgress` carries `UploadNow` and `UploadTotal`, the bytes sent so far and the bytes to send, the download pair the same way, and `Phase`, which says which way bytes are moving: `Connecting` before any body byte has moved, then `Uploading`.

`Report` runs on the engine{apos}s own thread, while the transfer runs, so `ProgressLog` takes a lock and only appends. A `Progress<T>` would instead post each report to a synchronization context, so a report could arrive after `SendAsync` had returned; a test that wants the reports in order and complete records them itself, and a user interface can still post from `Report` (<<curl-readme>>). A `Report` that throws aborts the transfer (<<curl-readme>>).

There are ten or more reports, each `UploadNow` at least the one before, and the last says all 16,777,216 bytes of 16,777,216 were sent. The `CurlResponse` to the `PUT` is `201 Created`. Progress counts what left the client; what proves the upload is the server{apos}s own copy, so the program reads it back with `server.Files.ReadAsync`, a `SurlFileContents` whose `ByteCount` is 16,777,216 and whose bytes have the same SHA-256 as the data sent.

Without `AllowUploads`, the server answers `405 Method Not Allowed` before taking the body. The reports stop at `Connecting`, and the last says 0 of 0 bytes. A progress bar driven by them never reaches the end, which is right, and the status code is what says why.
