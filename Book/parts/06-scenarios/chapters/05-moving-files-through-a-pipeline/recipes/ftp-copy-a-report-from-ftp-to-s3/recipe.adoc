=== Copying a Report from FTP to S3

==== Problem

A nightly job downloads a report over File Transfer Protocol (FTP) and uploads it to an Amazon Simple Storage Service (S3) bucket; you want the whole hop tested against local servers, and the object{apos}s bytes compared with the source.

==== Solution

Run an FTP server holding the report and an S3 server with a bucket, then make the hop with one `curl` command: the download, `--next`, the upload:

==== Discussion

Two `surl` processes stand in for the two ends. The FTP one serves the folder `ftp-site` (`--directory`) and has one account, `--user nightly:s3cret`. The S3 one serves `store`, where each folder is a bucket, with one key pair as its `--user` and `--allow-uploads`. Both take `--cert` and `--key`: `s3://` is served over Transport Layer Security (TLS) only, and the FTP server needs a certificate to offer TLS at all. The certificate made in setup names `127.0.0.1` and the host `curl` gives any bucket, `*.s3.us-east-1.amazonaws.com`, and `--cacert server.pem` makes `curl` trust it on both hops.

The first half logs in to FTP: `--ssl-reqd` makes `curl` upgrade the control connection to TLS before it sends the password (<<rfc4217>>), `-u nightly:s3cret` logs in, and `-o report.csv` keeps the download. Without `--ssl-reqd` the password would cross in the clear, so `surl` refuses the login with `530` before checking it, and `curl` exits `67`. That refusal is `surl`{apos}s default for a password over plain FTP.

`--next` starts a fresh set of options for the second half, so each half carries its own `--cacert` and `-u`. `--connect-to ::127.0.0.1:8081` sends the bucket{apos}s host name to the S3 server, `-u` with the access key ID and secret signs the request, and `-T report.csv s3://reports/2026-11-20.csv` puts the file as that key. `-s` hides the progress meter and `-S` still prints an error.

The comparison is the test. `cmp` finds the object in the S3 server{apos}s folder identical to the FTP server{apos}s file, Windows line ends included: neither hop touched a byte (<<rfc959>>). A job cannot read either server{apos}s disk, so the second comparison is the one it can make: get the object back over S3 and compare it with the file it downloaded.

`--fail-early` is what keeps a bad night from looking like a good one. Without it, a report missing on the FTP server fails the download with exit `78`, but `curl` goes on to the upload, finds the `report.csv` the last run left behind, and publishes it under the new date; the command exits `0`, because `curl` exits with the last transfer{apos}s code. The bucket then holds the last run{apos}s report twice. With `--fail-early` the command stops at the download with `78`, and the bucket has no object for that date: getting it is `404 NoSuchKey`, exit `22` (<<aws-s3-api>>).
