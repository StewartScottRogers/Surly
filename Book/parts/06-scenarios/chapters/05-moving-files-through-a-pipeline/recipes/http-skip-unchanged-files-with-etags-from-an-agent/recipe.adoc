=== Skipping Unchanged Files with ETags

==== Problem

You want an artificial intelligence (AI) agent to run a sync job that fetches only what changed: every file on the first run, with its entity tag kept, a `304 Not Modified` for each unchanged file on the next, and a file changed between runs fetched again.

==== Solution

Write the agent{apos}s side as a C# program on the official Model Context Protocol (MCP) software development kit: it starts a server through `surl-mcp`{apos}s `start_server`, fetches each file with `curl-mcp`{apos}s `curl` tool and `--etag-compare` and `--etag-save`, and changes the server between runs with `put_file`:

==== Discussion

`start_server` starts a Hypertext Transfer Protocol (HTTP) server holding `a.txt` and `b.txt` in memory; `bound_urls` in its answer names the port, and `server_id` names the server for the other `surl-mcp` tools. The server sends each file with an entity tag (ETag), a validator that changes whenever the file does (<<rfc9110>>).

The `curl` tool runs a `curl` command line, given as `args`, inside `CURL_MCP_ROOT`, and answers JavaScript Object Notation (JSON) text with `exitCode` and the output streams. The job makes one call per file. `--etag-save local-changed/a.txt.etag` writes the tag of the reply beside the copy, and `--etag-compare` with the same file sends it back as `If-None-Match`; when the tag file does not exist yet, as on the first run, `curl` fetches the file anyway. `-o` and `--create-dirs` save the copy, `-s` keeps the output to what `-w "%{http_code}"` prints, and `-f` makes an error status a failure (<<curl-manual>>). The copies and their tags are ordinary files on disk under `CURL_MCP_ROOT`, for the next step to read.

The `tags` case shows the comparison itself. A `transfer` call with `method` `HEAD` returns the headers and no body: the file is answered `200`, and its `ETag` is the one `--etag-save` wrote. Run with `-v`, the `curl` tool{apos}s `standardError` holds both heads: `curl` sent that tag as `If-None-Match`, and `surl` answered `304 Not Modified` itself, with no body, so the local copy is left alone.

The first run prints `200` for both files, the second `304` for both. `put_file` then rewrites `a.txt` in the server{apos}s store, and the third run fetches it again and still skips `b.txt`. The program does not wait before the rewrite: a date counts whole seconds and could miss a change in the same second, but the rewrite gives `a.txt` a new tag.

`delete_file` removes `a.txt` from the store. The next fetch of it is answered `404 Not Found`; `-f` makes `curl` exit `22` before it writes anything, so the local copy stays as it was. Without `-f` the same fetch prints `404` and exits `0`, and `-o` writes `surl`{apos}s short error body, `404 Not Found`, over the local copy. With `-f`, an agent reads the `exitCode` of `22` as "gone on the server" and decides for itself whether to delete its copy.
