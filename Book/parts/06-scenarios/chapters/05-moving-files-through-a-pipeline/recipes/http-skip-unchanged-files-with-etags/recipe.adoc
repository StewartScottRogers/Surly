=== Skipping Unchanged Files with ETags

==== Problem

A sync job should fetch only what changed: the first run takes every file and keeps its entity tag, the next run gets `304 Not Modified` for the files the server has not changed, and a file changed between runs is fetched again.

==== Solution

Serve the files with `surl`, and fetch each one with `curl --etag-compare --etag-save`, which sends the tag saved with the local copy and takes a new copy only when the server{apos}s tag no longer matches. The loop is a short script and needs a POSIX shell (Git Bash on Windows):

==== Discussion

`surl` with `--directory site` serves the two files and sends each with an entity tag (ETag), a validator that changes whenever the file does (<<rfc9110>>). `surl`{apos}s tag is strong and is made from the file{apos}s last-write time and its length (<<surl-readme>>), so a rewrite changes it even within one second. The setup dates both files 2 January 2024 with `touch`.

Two `curl` options make the job, both naming the same file beside the copy. `--etag-save local/a.txt.etag` writes the `ETag` of the reply to that file, one quoted tag on a line. `--etag-compare local/a.txt.etag` reads it back and sends it as `If-None-Match` (`-v` shows the header). When the tag file does not exist yet, as on the first run, `curl` fetches the file anyway; `-s` keeps quiet about the missing tag file. `-w "%{http_code} $f\n"` prints one line per file (<<curl-manual>>).

The first run prints `200` for both files and saves each body and its tag. The second sends both tags; `surl` finds them current and answers `304 Not Modified` itself, a reply with no body, so `curl` leaves the local files as they were. After `a.txt` is rewritten on the server its tag changes, and the third run fetches `a.txt` again and still skips `b.txt`.

A tag is a better test of change than a date. A file restored from a backup can come back with new content and an older date. `curl -z`, which fetches only when the server{apos}s date is newer than the local copy{apos}s, sees nothing newer and reports `304`, keeping the stale copy; the recipe shows that too. The restored file{apos}s tag differs from the saved one, so the ETag job fetches it.

`-f` protects the copy the job already has. A file deleted on the server is answered `404 Not Found`. Without `-f`, `-o` writes `surl`{apos}s short error body, `404 Not Found`, over the local copy; with it, `curl` exits `22` and leaves the local file alone, and the job can decide what a deletion means.
