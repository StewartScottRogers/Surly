=== Cancelling a Stuck Transfer

==== Problem

A server in your pipeline sometimes stalls, and you want your .NET code to give up on the transfer cleanly, with the connection freed and the next transfer working, and a test that proves it.

==== Solution

==== Discussion

`SurlFault.Delay` is `surl --fault "delay;..."`: it makes the server hold a matching exchange before answering. `Stage = FaultStage.Command` holds it after the request has arrived, so the client has connected and sent its request and is waiting for a reply that does not come, and `Path` limits it to `/stuck.txt`. A fault makes `surl` misbehave on purpose, which is why `SurlServerOptions.Faults` is empty by default. `/hello.txt` is answered at once, and the program fetches it first because the first request in a process sets up the engine and takes a few seconds.

`CurlClient.SendAsync` takes a `CancellationToken`. `CancelAfter` cancels it one second in, while the `CurlRequest` for `/stuck.txt` is still waiting for its headers; the client aborts the transfer and `SendAsync` throws `OperationCanceledException`, between one and five seconds after it started. The next `CurlRequest` on the same client gets `200 OK` at once. The aborted connection is closed, not handed back for reuse with a reply still owed on it: with `RecordExchanges` the server keeps what each connection carried, one `SurlExchangeRecord` each in `server.Exchanges`, and no connection carries `/hello.txt` after `/stuck.txt`. Whether the next request opens a connection of its own is not fixed. `CurlResponse.Info.NumConnects` is 1 when it does and 0 when the client reuses a connection kept from before, and both have been seen, 1 on Windows and 0 on Linux, so the program prints it without depending on it.

`CurlClientOptions.Timeout` is the other way to give up, libcurl{apos}s `CURLOPT_TIMEOUT_MS` for every request the client makes (<<libcurl-api>>), the spelling of `curl -m`. It ends the same stuck request with a `CurlException` whose `Code` is `OperationTimedOut`, curl{apos}s exit code 28, rather than an `OperationCanceledException`, and the client goes on working the same way. A token suits a caller that decides when to stop, such as a test{apos}s own time limit or a user pressing Cancel; `Timeout` suits a limit every request should share. A catch for one does not catch the other.

Cancelling closes the client{apos}s side at once; the server learns of it only when it sees the connection gone, and then ends its wait and frees the connection. With `MaxConnectionsPerAddress = 1`, `surl --max-connections-per-address 1`, the next request races that notice: if the server has seen the client go, it is answered `200 OK`; if not, it is refused `503 Service Unavailable` for the abandoned request it is still counting. Which one wins depends on the platform and the moment, so a client that cancels and retries at once against a tight limit should expect either, and retry a `503` after a moment.
