=== Handling a Full Disk During Upload

==== Problem

In a C# test, a pipeline step uploads tonight{apos}s export over File Transfer Protocol (FTP) and the next step reads it over Hypertext Transfer Protocol (HTTP). You want one upload path to report out of space, so the test proves the uploader reports the failure and leaves no half-written file for the next step.

==== Solution

Host one server in the test that takes FTP uploads and serves the same store over HTTP, with `/archive` out of space by fault rule; upload with `Curl.Api`, read the path back over HTTP, and look in the store:

==== Discussion

`SurlServerOptions` is `surl`{apos}s command line as properties. `ListenUrls` holds an `ftp://` and an `http://` listener on free ports, both serving one store, so what the uploader writes is what the next step reads; `BoundUrls` lists them in that order. `AllowAnonymous` (`--allow-anonymous`) lets the client log in with no account, `AllowUploads` (`--allow-uploads`) turns on writing, and `MaxFileSize` (`--max-filesize`) gives every file 100,000 bytes of room. `Faults` takes `SurlFault.OutOfSpace()` with `Path` `/archive`: every store under that folder fails as a full disk would, as `--fault "out-of-space;path=/archive"` does. A fault loosens the server on purpose and is for tests only. `Files` holds last night{apos}s export and an `/incoming` folder.

The uploader is a `CurlRequest` `PUT` with the export as `Body`, sent on a `CurlClient`; on an `ftp://` URL that is `STOR`. Into `/archive` it throws `CurlException` with `Code` `UploadFailed`, `curl`{apos}s exit 25, and the message carries the server{apos}s `552`, the reply FTP keeps for exceeded storage (<<rfc959>>). The program reports it by exiting 1. The next step{apos}s `GET` over HTTP returns a `CurlResponse` with `StatusCode` 404 and throws nothing: a missing file is an answer, not an error (<<rfc9110>>). Its body is 14 bytes of error text, `404 Not Found`, so a next step that does not check the status would carry on with that text as if it were the export.

The check reads the store without a request: `server.Files` is the `SurlServerFiles`, and `ReadAsync` returns a `SurlFileContents` or throws `SurlNotFoundException`. Nothing is at `/archive/2026-11-20.csv`, and last night{apos}s export there is still served whole. `Log` with `LogLevel` `Verbose` (`-v`) writes the server{apos}s log to a `StringWriter`; it records of the refusal that `the partial upload was deleted`. The same export to `/incoming` is stored, read back over HTTP byte for byte, and its 22 bytes are in the store.

A 300,000-byte export to `/incoming` runs out of room partway: the server stops it at 100,000 bytes, answers `552` and resets the data connection. The client waits for that reply when its write fails, so the exception{apos}s `Code` is `RemoteDiskFull`, `curl`{apos}s exit 70. The server kept nothing: the next step gets 404, the store has no `big.csv`, and the log records the partial upload deleted.

The rule is on the path, not the listener: a `PUT` of the export into `/archive` over the `http://` listener returns a `CurlResponse` with `StatusCode` 413, and nothing is stored.
