=== Exchanging a Password for a Token

==== Problem

Your client logs in with Basic to fetch a token, then calls the API with it as a Bearer token. You want a C# test to run the whole flow over Hypertext Transfer Protocol Secure (HTTPS) and check what the server recorded.

==== Solution

Host the server with `Surl.Api`, holding one password account, one Bearer token and the token as a file; make the two calls with `Curl.Api`; then read the logins the server judged:

==== Discussion

`surl` does not issue tokens; it holds accounts. In `SurlServerOptions.Accounts`, `SurlAccount("app", "s3cret")` is the client's password, `--user app:s3cret`, and `SurlAccount("", "tok-7f3a9c")`, an empty user name, is a Bearer token (<<rfc6750>>), `--user :tok-7f3a9c`. The file `token.txt` holds the same token, so the test plays the identity provider by choosing the token before the server starts, and only a caller who logged in can read it. `SelfSigned` makes a throwaway certificate for Transport Layer Security (<<rfc8446>>), and the client trusts exactly that one through `CurlTlsOptions`: `CurlTlsPeerOptions.CertificateAuthorityBlob` takes `SelfSignedCertificatePem`, `curl --cacert` with the certificate in memory.

The flow is two `CurlRequest`s through one `CurlClient`. The first carries `CurlAuthenticationOptions` with the user name and password and `HttpAuthentication` set to `HttpAuthenticationMethods.Basic` (<<rfc7617>>); the body of the `CurlResponse` is the token. The second sets `XOAuth2Bearer` to that token and `HttpAuthentication` to `HttpAuthenticationMethods.Bearer`, `curl --oauth2-bearer`, and gets the orders. Over `http://` `surl` would refuse both unchecked; <<http-exchange-a-password-for-a-token>> shows that refusal.

`RecordExchanges` keeps what the server saw, and `FindEvents` with a `SurlEventQuery` whose `Kind` is `SurlEventKind.LoginJudged` returns each login judged, oldest first, as a `LoginJudgedEvent`: `Mechanism`, `Account` and `IsAccepted`. A Bearer login's account is `bearer token`, never the token itself. That record is how the test proves the client used the token: `surl` does not scope accounts to paths, so the password alone would also reach the API, as <<http-exchange-a-password-for-a-token>> shows.

The failure paths are the client's. A wrong password is answered `401 Unauthorized` at the first step, the program stops there, and the record holds one refused Basic login. A token the server does not hold is answered `401` by the API after a good login, and the record holds the Bearer login as refused. The program exits 1 on either, as a test would fail.
