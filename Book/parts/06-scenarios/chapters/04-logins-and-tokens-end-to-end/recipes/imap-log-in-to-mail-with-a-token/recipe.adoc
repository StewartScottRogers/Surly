=== Logging In to Mail with a Token

==== Problem

Your mail client logs in with OAUTHBEARER or XOAUTH2; you want a server that accepts only those and a test that sends and reads mail with the token.

==== Solution

Run one `surl` with Transport Layer Security (TLS) mail listeners, `--auth oauthbearer,xoauth2` and the token as an account with an empty user name. Send as Bob with the token over `smtps://`, then read as Ann with the same token over `imaps://`:

==== Discussion

The story has four parts: the server, the happy path, what the server recorded, and the ways in that stay shut. A server first. `surl` issues no tokens and checks none against an identity provider: `--user :tok-abc123` is an account with an empty user name whose password is the token, and the test supplies the string its client will send (<<surl-readme>>, <<rfc6750>>). `--auth oauthbearer,xoauth2` names the only mail logins it accepts and offers (<<surl-readme>>); `surl` warns on every start while `--auth` is given. The certificate and key come from `openssl` in the recipe. One command line holds four listeners over one mail store: `smtps` and `imaps` over TLS, `smtp` and `imap` without, so the refusals have somewhere to happen.

The two mailboxes carry `;protocols=http`. That key replaces the mail protocols an account logs in on, so Ann{apos}s and Bob{apos}s passwords can receive mail but are not accepted on any mail protocol. Without it the mailbox accounts would still log in by password, and the server would not be a token-only one. The case `why-protocols-http` shows the reason: on a second server with the same `--auth` and an ordinary mailbox, Ann{apos}s password still logs in over `imaps`, since `curl` falls back to the IMAP `LOGIN` command and `--auth` names SASL mechanisms only. The token is not tied to a mailbox either: the user name the client gives picks the mailbox it reads.

The happy path is the solution: Bob sends with `--oauth2-bearer`, the envelope and `-T lunch.eml` (<<rfc5321>>) over `smtps://`, and the server answers `250`; Ann reads the body with `;SECTION=TEXT` (<<rfc9051>>). The `Return-Path` and `Received` lines of the stored message record the send: the envelope sender, and `with ESMTPSA`, SMTP with TLS and a login. The `xoauth2` case sends again with `--login-options AUTH=XOAUTH2`: the exchange shows `AUTH XOAUTH2`, `235` and a `250` for the mail.

The failure paths are what a token-only server is for. A password is no way in over `smtps` or `imaps`, exit 67. A wrong token over `smtps` is refused, exit 67, login denied. Over plain `smtp` the server offers no token login, so `curl` sends none and is refused at `MAIL` with `530`, exit 55; over plain `imap` the token is refused, exit 67. A logged-in token still obeys the mail domain: a recipient outside `example.com` is refused `550` at `RCPT`, exit 55. The case `refusals-stored-nothing` counts Ann{apos}s `INBOX` with an IMAP `STATUS` command: two messages, the two sends that worked. The refusals stored nothing.

The server options: `--cert` and `--key` are the certificate and key, `--mail-domain` serves mail for a domain and `--mailbox` adds a mailbox and its account. On the `curl` side, `--cacert server.pem` makes `curl` trust that certificate, `-u` is the login, `--mail-from` and `--mail-rcpt` the envelope, `--crlf` the line ends mail needs, `-X` an IMAP command in place of the default, `-s` keeps the progress meter out, `-S` keeps error messages in, `-v` prints the exchange, `-w` prints the last reply code, and `--next` starts a second transfer in the same command.
