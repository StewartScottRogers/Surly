=== Exchanging a Password for a Token

==== Problem

Your client logs in with Basic to fetch a token, then calls the API with it as a Bearer token. You want your artificial intelligence (AI) agent to run the whole flow over Hypertext Transfer Protocol Secure (HTTPS) and check what the server recorded.

==== Solution

Write the agent's side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it starts the server through `surl-mcp`{apos}s `start_server`, makes the two calls with `curl-mcp`{apos}s `curl` tool, and reads the logins back with `get_events`:

==== Discussion

`surl` does not issue tokens; it holds accounts. In `start_server`{apos}s `arguments`, `--user app:s3cret` is the client's password and `--user :tok-7f3a9c`, an empty user name, is a Bearer token (<<rfc6750>>). The file `token.txt`, given in `files`, holds the same token, so the agent plays the identity provider by choosing the token before the server starts, and only a caller who logged in can read it. `--cert server.pem --key server.key` serve Transport Layer Security (<<rfc8446>>); `surl-mcp` reads the files from `SURL_MCP_ROOT`, where `setup` made them.

`curl` runs `curl` with the argument list given, in `CURL_MCP_ROOT`, so `--cacert server.pem` trusts exactly that certificate; `curl-mcp`{apos}s `transfer` tool has no option for a certificate authority, which is why this recipe uses `curl`. The first call, `-u app:s3cret` with no method named, sends Basic (<<rfc7617>>), and the token is its `standardOutput`. The second sends it with `--oauth2-bearer` and gets the orders. `-s` keeps it quiet and `-f` turns an error status into exit 22, which the answer's `exitCode` carries, so the agent stops at the step that failed.

`get_events` with `kinds` set to `login_judged` answers each login the server judged, oldest first, with `mechanism`, `account` and `is_accepted`. A Bearer login's account is `bearer token`, never the token itself. That record is how the agent proves the client used the token: `surl` does not scope accounts to paths, so the password alone would also reach the API, as <<http-exchange-a-password-for-a-token>> shows.

The failure paths are the client's. A wrong password fails the login with exit 22, the agent never calls the API, and the record holds one refused Basic login. A token the server does not hold fails the API call with exit 22 after a good login, and the record holds the Bearer login as refused.
