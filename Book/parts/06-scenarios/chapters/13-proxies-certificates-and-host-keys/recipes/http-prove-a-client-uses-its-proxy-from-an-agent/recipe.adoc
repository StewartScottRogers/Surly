=== Proving a Client Uses Its Proxy from an Agent

==== Problem

Your client must go through a proxy, and an agent runs your tests. You want the agent to stand up a proxy and an origin from one server, and to prove from the server's record that every request the origin received came through the proxy.

==== Solution

Start the origin with `surl-mcp`{apos}s `start_server`, with `--proxy` in `arguments`, fetch through the proxy with `curl-mcp`{apos}s `transfer` tool, then read the origin's requests with `get_exchanges` and look for the proxy's `Via` header in each:

==== Discussion

`StdioClientTransport` starts both hosts by name, each confined to the program's folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. `start_server` starts a server that behaves as `surl` with the same options: `listen_urls` is the origin, an ordinary Hypertext Transfer Protocol (HTTP) server of the two files in `files`, and `--proxy http://127.0.0.1:0` in `arguments` adds a proxy listener to the same server. `bound_urls` in the answer lists the origin first and the proxy second.

`transfer` is the client under test here; its `proxy` field is `curl -x`, so each request goes to the proxy, which forwards it. The answer holds `statusCode`, `headers` and `body`; both files come back `200`. In your test the client is your own program, with whatever proxy setting it reads.

A proxy that forwards a request adds a `Via` header naming itself, `Via: 1.1 surl` (<<rfc9110>>); a request sent straight to the origin has none. `get_exchanges` with `listen_url` returns what one listener received, connection by connection, as chunks; the request heads are text. The program joins each exchange's received chunks and splits them at the blank line that ends each head, since one connection can carry several requests. After the two fetches the origin holds two heads, both with `Via`, and the program exits 0. Asked for the proxy's listen URL, `get_exchanges` shows the other side: two requests in absolute form, `GET http://127.0.0.1:.../hello.txt`.

The client can see the header as well, in the `headers` of each answer that came through the proxy. That is a check of one answer, though, not of every request.

The failure path is a request that skips the proxy: `transfer` with no `proxy` field. The origin answers it `200` like any other, with no `Via`, so the client sees nothing wrong, and that is why the test has to look at the server. The check counts one request via the proxy and one direct, and the program exits 1.
