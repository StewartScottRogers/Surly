=== Keeping the Server Log for Failures

==== Problem

As an artificial intelligence (AI) agent: when a continuous integration (CI) run fails you want the server's log and trace kept as an artifact, with no password or token in it.

==== Solution

Write the agent's side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it starts a server with `start_server`, runs the tests with `curl`, and when one fails writes what `get_events` and `get_exchanges` answer into `ci-logs/`, the bytes the clients sent left out:

==== Discussion

`surl-mcp` has no log file: `start_server` refuses `--log-file`, `--trace` and `--trace-ascii`, which belong to whoever runs the host. What it has instead is a record of every server it started, and an agent reads it with two tools. `get_events` answers the events in order: each exchange started and ended, and each login judged, with its scheme, account, mechanism and `is_accepted`. `get_exchanges` answers each exchange's bytes as `chunks`, in the order they crossed, each marked `sent` or `received`. Together they are the log and the trace (<<mcp-spec>>).

`start_server` here listens for Hypertext Transfer Protocol Secure (HTTPS) and for File Transfer Protocol (FTP) over Transport Layer Security (FTPS, <<rfc4217>>) on free ports. `arguments` are `surl`{apos}s own options: `--cert server.pem` and `--key server.key`, made by `setup` in the folder the host is confined to (<<rfc8446>>), and two `--user` accounts, a password and a Bearer token, the account with an empty user name (<<rfc6750>>). `files` holds the report. The tests go through `curl-mcp`{apos}s `curl` tool, the `curl` command line run in-process: `-u` logs in with the password, `--oauth2-bearer` sends the token, `--cacert server.pem` trusts exactly that certificate, `-f` fails on an error status, `-sS` keeps quiet but for the error, and `-o` writes the body into the folder. A failing `curl` is a tool error whose answer holds its exit code: with the wrong FTPS password, 67.

On that failure the agent writes two files. The events are kept whole, as `get_events` answered them: they name each login's method and account and never its secret. The exchanges are not fit to keep as answered: the `received` chunks hold every byte a client sent, so the `PASS` command is there with the password in clear, written after TLS has been taken off. The agent keeps each `sent` chunk as text and, for each `received` chunk, only how many characters arrived. What is left holds neither password nor the token, and still holds the `530 Login incorrect` that ended the run. A passing run keeps nothing.
