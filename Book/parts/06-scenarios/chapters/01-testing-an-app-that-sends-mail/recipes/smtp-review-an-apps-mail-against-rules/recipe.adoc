=== Reviewing an App's Mail Against Rules

==== Problem

You want an artificial intelligence (AI) agent to read every mail an app sent and check that each has a `From`, a `Date` and a `Message-ID` and names no address outside your domain.

==== Solution

Write the agent{apos}s side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it starts a Simple Mail Transfer Protocol (SMTP) server with `surl-mcp`{apos}s `start_server` that keeps all the domain{apos}s mail in one catch-all mailbox, sends as the app through `curl-mcp`{apos}s `curl` tool, then lists every message with `list_messages`, reads each with `read_message` and checks it against the rules:

==== Discussion

The program starts `surl-mcp` and `curl-mcp` by name from the path, each confined to the program{apos}s folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`; `mcp.json` beside this recipe is the same configuration for an agent{apos}s own client. The argument picks the scenario.

`start_server` takes an `smtp://` listen URL on port 0 and `surl`{apos}s options in `arguments`. `--mail-domain example.com` serves mail for that domain and refuses every recipient outside it. `--mailbox` adds a mailbox for the app to log in as and one called `review@example.com`, and `--mail-catch-all example.com=review@example.com` puts the mail for every address of the domain that has no mailbox of its own into that one (<<surl-readme>>). So whoever the app writes to, Dan or Fay, the agent finds the mail in one place.

The `curl` tool runs `curl`{apos}s own arguments and answers in text that is JavaScript Object Notation (JSON), with `exitCode`. As the app, the program prepends `-s` and logs in with `-u`, names the envelope with `--mail-from` and `--mail-rcpt`, and uploads a message file from the folder with `-T` (<<curl-readme>>). The files already end each line in a carriage return and line feed.

`list_messages`, given the `server_id`, the `owner` `review@example.com` and the `mailbox` `INBOX`, lists the messages in unique identifier (UID) order, each with its `uid`. A long run would page with `after_uid` and `limit`; two messages need one call. `read_message` with the same three and a `uid` answers the message{apos}s exact bytes as `text`. The review is the agent{apos}s own code. The header is everything up to the first empty line, and a line that starts with a space or tab continues the field before it (<<rfc5322>>). A message passes if it has a `From`, a `Date` and a `Message-ID` field, the three an Internet message is meant to carry, and every address in `Return-Path`, `From`, `Sender`, `Reply-To`, `To`, `Cc` and `Bcc` ends in `@example.com`. The program prints `ok` or `FAIL` with the reasons for each UID and exits `1` when any fails.

The server and the review guard different things. A recipient outside the domain in the envelope is refused at `RCPT` with `550` (<<rfc5321>>): the `curl` tool exits `55`, nothing is stored, and the review, with nothing to read, fails too. A `Cc` field naming `eve@elsewhere.org` is only text in the message: the envelope said `gus@example.com`, so the server delivers it, and only the review catches it. Nor does the server fill in what the app left out. It adds a `Return-Path` with the envelope sender and a `Received` field at the top of each message, but no `Date` or `Message-ID`, so a missing one is the app{apos}s.
