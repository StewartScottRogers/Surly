=== Checking a Mail's Attachment from an Agent

==== Problem

As an artificial intelligence (AI) agent testing an app that sends a report as a Multipurpose Internet Mail Extensions (MIME) attachment, you want to fetch the stored message and compare the attachment{apos}s bytes with the report.

==== Solution

Write the agent{apos}s side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it calls `surl-mcp`{apos}s `start_server` for a Simple Mail Transfer Protocol (SMTP) and an Internet Message Access Protocol (IMAP) listener, sends the mail through `curl-mcp`{apos}s `curl` tool as the app would, fetches the attachment{apos}s part with the same tool, decodes it and compares it with `report.csv`:

==== Discussion

The program starts `surl-mcp` and `curl-mcp` by name from the path, over standard input and output, each confined to the program{apos}s folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`; `mcp.json` beside this recipe is the same configuration for an agent{apos}s own client. The argument picks which mail the app sends.

`start_server` takes `listen_urls`, an `smtp://` and an `imap://` URL on port 0, and answers `bound_urls` with the real ports, in the same order, and a `server_id`; the two servers share one mail store (<<surl-readme>>). Its `arguments` are `surl`{apos}s own options: `--mail-domain example.com`, and a `--mailbox` each for the app and for Ann, a mailbox and the account that logs in to it by its whole address.

The `curl` tool runs `curl`{apos}s own arguments and answers in text that is JavaScript Object Notation (JSON), with `exitCode` and the `standardOutput` `content`; the program prepends `-s` to keep the progress meter out. As the app, it logs in with `-u`, gives the envelope with `--mail-from` and `--mail-rcpt`, and uploads the message from the folder with `-T`, `--crlf` ending each line in a carriage return and line feed (<<rfc5321>>). The message carries `report.csv` in base64 as its second part. As the test, it fetches `INBOX;UID=1;SECTION=2`, that part{apos}s body as stored, still base64 (<<rfc9051>>). The program decodes it with `Convert.FromBase64String`, which skips the line ends, and compares the bytes with `report.csv` from the folder; equal, it passes and exits `0`.

`read_message` reads the stored message without a client and sets no flag: given the `server_id`, the `owner`, the `mailbox` and the `uid`, it answers the message as `text`. The program finds the attachment{apos}s `Content-Disposition` line in it, which names the file, a check an agent can make before fetching anything.

Both mistakes are delivered like any mail, so only the comparison finds them. Last week{apos}s report decodes to 69 bytes, not 85, and the program exits `1`. A mail with no attachment has no `Content-Disposition` line, and fetching a part that is not there is not an error: the `curl` tool exits `0` with nothing on standard output. The program checks for an empty part before decoding and fails with `no attachment`.
