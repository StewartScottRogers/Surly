=== Routing Mail Through Aliases from an Agent

==== Problem

As an artificial intelligence (AI) agent testing an app that mails `support@` and `alerts@` over Simple Mail Transfer Protocol (SMTP), you want aliases forwarding those addresses to real mailboxes, and the test checking where each message landed.

==== Solution

Write the agent{apos}s side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it calls `surl-mcp`{apos}s `start_server` with a `--mail-alias` per address, sends each mail through `curl-mcp`{apos}s `curl` tool as the app would, reads the delivered events after each send, and reads every target mailbox from the store:

==== Discussion

The program starts `surl-mcp` and `curl-mcp` by name from the path, over standard input and output, each confined to the program{apos}s folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`; `mcp.json` beside this recipe is the same configuration for an agent{apos}s own client. The argument picks the scenario.

`start_server` takes an `smtp://` and an Internet Message Access Protocol (IMAP) listen URL on port 0, which share one mail store, and `surl`{apos}s own options in `arguments` (<<surl-readme>>). `--mail-domain example.com` serves the domain; each `--mailbox` is a mailbox and the account that logs in to it by its whole address; `--mail-alias support@example.com=ann@example.com,bob@example.com` forwards `support@` to Ann and Bob, and the second alias forwards `alerts@` to the operations mailbox. Each option and its value are separate array items, so nothing needs quoting.

The `curl` tool runs `curl`{apos}s arguments and answers in text that is JavaScript Object Notation (JSON), with `exitCode` among the fields. As the app, the program logs in with `-u`, gives the envelope with `--mail-from` and `--mail-rcpt` (<<rfc5321>>), and uploads a message file from the folder with `-T`; `--crlf` makes sure every line ends in a carriage return and line feed, and `-s` keeps the progress meter out. Without Transport Layer Security the server offers only `CRAM-MD5`, a login that never sends the password, so no loosening option is needed.

The agent learns where a message went from the server, not from `curl`. `get_events` with `kinds` `store_changed` and `store` `mail` lists the mail store{apos}s changes; each delivery is one event whose `name` is the mailbox and the message{apos}s unique identifier (UID), such as `ann@example.com/INBOX/;UID=1`. Passing the last `sequence` seen as `after_sequence` returns only what the next send did. The mail to `support@` produced two deliveries, one per alias target; the alert produced one. The check at the end reads the store directly: `list_messages` lists an owner{apos}s `INBOX`, and `read_message` returns a message{apos}s `text`, from which the program takes the `Subject` field (<<rfc9051>>). It passes only if Ann, Bob and the operations mailbox each hold exactly the one message meant for them.

Mail to `alert@`, a typo for `alerts@`, is the quiet failure. The address is in the domain but is neither a mailbox nor an alias, so the server accepts it and discards it, and `curl` exits `0`; a sender is never told which addresses exist (<<surl-readme>>). The events show it at once: no delivery follows that send, and the operations mailbox is empty. A typo in the alias itself is caught earlier. A target with no mailbox, `opps@example.com`, makes `start_server` a tool error whose structured content carries `surl`{apos}s `exit_code` `2`, `exit_code_name` `FailedInit`, and its message in `lines`, so the agent fixes the setup before any mail is lost.
