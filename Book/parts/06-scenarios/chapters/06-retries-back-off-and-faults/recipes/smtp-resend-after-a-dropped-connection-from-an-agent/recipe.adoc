=== Resending After a Dropped Connection

==== Problem

Your app sends mail over Simple Mail Transfer Protocol (SMTP), and the first connection to the server is dropped before the server says a word. You want your agent to start a server that does that, to watch the sender connect again, and to prove that exactly one copy of the mail was delivered.

==== Solution

The agent starts `surl-mcp` with a mail server, adds a rule that drops the first connection, sends with the `curl` tool of `curl-mcp`, tries again after an error, and reads what the server kept with `surl-mcp`{apos}s own tools. ==== Discussion

`start_server` takes the listen URL, `smtp://127.0.0.1:0` for a free port, and `arguments`, which are `surl`{apos}s own words: `--mail-domain example.com` and a `--mailbox` for the app and for Ann. Its answer carries the `server_id` and the `bound_urls`. `add_fault` then adds one rule to the running server, `drop;scheme=smtp;times=1`, and answers the rule{apos}s `fault_id`, `f1`. `drop` closes a connection without answering; with no `stage` it acts when the connection is accepted, before the greeting, `scheme=smtp` limits it to the SMTP listener, and `times=1` spends it after one connection (<<surl-readme>>). The rule is added after the start, so no connection of the host{apos}s own can have spent it.

The app is the `curl` tool, which runs `curl`{apos}s own arguments (<<curl-readme>>): `-u` is the app{apos}s login, `--mail-from` and `--mail-rcpt` the envelope, `-T order.eml` the message from the folder `curl-mcp` is confined to, `--crlf` turns line feeds into the carriage return and line feed a message is made of, `-s` keeps the progress meter out, and `-w "%{response_code}"` puts the server{apos}s last reply in `standardOutput`. One call is one try. A dropped connection answers `exitCode` `56`, a receive failure, with `000` for the reply code, and the agent waits a second and calls again, up to the number of retries it is given. The second call answers `exitCode` `0` with reply `250` (<<rfc5321>>). A failing `curl` call still answers its JSON, so the agent reads `exitCode` and the reply rather than relying on `isError`.

What the server kept is read without a client. `list_mailboxes` with the owner `ann@example.com` gives each mailbox with its `message_count`: one, the dropped connection having stored none. `get_events` with `kinds` `fault_applied` shows the rule acted once, `drop` by `f1`, and with `store_changed` shows one message stored; `get_exchanges` for `smtp` lists two connections, the dropped one and the retry.

Mail is delivered asynchronously, so the agent does not read the store at once after an accepted send. `wait_for_event` with `kinds` `store_changed`, the `after_sequence` of the last delivery it saw and a `timeout_ms` of ten seconds answers with the delivery event, or with `timed_out` true if none comes, so a lost message fails the test rather than hanging it. A dropped connection delivers nothing, so it does not wait.

Where the connection drops matters, and three more rules show it. `drop;scheme=smtp;times=2` drops the first two connections. A send with no retry exits `56` once and Ann holds nothing; a second send, with one retry, is dropped again, its retry is the third connection and is accepted, and Ann holds one message: three connections, two dropped, one copy. `drop;scheme=smtp;stage=command;command=DATA;times=1` drops the connection when the sender asks to send the message, before the server has taken it. The message is not stored, the retry is accepted, and one copy arrives. With `command=QUIT` the connection drops after the server has stored the message and answered `250`. `curl` already has its reply and exits `0`, the agent does not resend, and Ann holds one message. A sender that read the dropped goodbye as a failed send, and sent again, would leave two; a test that wants one copy has to tell a drop before the reply from a drop after it.
