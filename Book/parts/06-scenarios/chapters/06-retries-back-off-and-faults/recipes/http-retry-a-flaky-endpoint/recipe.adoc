=== Retrying a Flaky Endpoint

==== Problem

Your client is meant to retry, with a growing wait, when a server answers `503 Service Unavailable`. You want a Hypertext Transfer Protocol (HTTP) endpoint that answers `503` twice and then serves the file, so a test can show that the client backs off, retries and succeeds on the third try.

==== Solution

Give `surl` a `--fault` rule that answers the first two requests for `/hello.txt` with `503`, and fetch it with `curl --retry 3`; the checked claims below then count, in `surl`{apos}s log, what the server saw:

==== Discussion

`--fault "error;scheme=http;reply=503;path=/hello.txt;times=2"` is one fault rule. `error` answers a request with the reply the rule names instead of serving it; `reply=503` must be an HTTP error status, 400 to 599, and `scheme=http` says which protocol's error shape it is in. `path=/hello.txt` limits the rule to that path, and `times=2` spends it after two answers, so every request after them is served from `site`, the folder `--directory site` serves. The quotes keep the semicolons from the shell. `surl` writes a warning on start, `--fault: 1 fault rule(s) make this server misbehave on purpose`, because a server that misbehaves on purpose looks broken to every other client.

`curl --retry 3` allows three retries after a failure `curl` counts as transient: a timeout, or a status such as `408`, `429`, `500`, `502`, `503` or `504` (<<curl-manual>>). `503` (<<rfc9110>>) is one, so `curl` waits and asks again. With no `--retry-delay` the wait starts at one second and doubles each time; `curl` says so on standard error, which `--no-progress-meter` keeps free of the progress bar: `Retrying in 1 second. 3 retries left.`, then `Retrying in 2 seconds. 2 retries left.` The third request is served, `curl` writes the file and exits `0`, and `-w "%{http_code} %{num_retries}\n"` prints the final status and the number of retries it made, `200 2`.

The server keeps its own account. `-v` sets the log level to verbose, which logs each request line and what the server did with it, and `--log-file surl.log` writes the log to a file instead of standard error. `grep -c` counts three requests for `/hello.txt` from that one command, and two of them `answered 503 Service Unavailable by fault rule f1`; `f1` is the first rule's ID. A test can assert on either side, and the two agree.

The failure paths are the other servers, each with the same rule and a folder of its own, since one `surl` holds a folder at a time; `-s` keeps `curl` quiet there. Without `--retry`, `curl` takes the first `503` as its answer and exits `0`, because to `curl` any status is a successful conversation; `-f` makes the second `503` a failure, exit `22`, and the third request is served, because the rule is spent. `--retry 1` is too few: the one retry gets the second `503`, and `curl -f` gives up with `22` after one retry. A status `curl` does not count as transient, such as a `404` for a file that is not there, is not retried at all.

`--retry-delay 1` turns the back-off off: `curl` waits one second before every retry instead of doubling. A test that wants to prove the client backs off checks the two waits, not just the final status.
