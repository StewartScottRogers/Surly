=== Logging In with a Secure Shell Key

==== Problem

A test logs in to a Secure Shell (SSH) File Transfer Protocol server with a key pair instead of a password, and you want a local server that accepts that one key and nothing else.

==== Solution

Make a host key and a key for the user, give `surl` the user's public key as an authorized key, and log in with `curl --key`:

==== Discussion

In a public-key login the client proves it holds a private key by signing with it, and the server checks the signature against public keys it has been told to accept for that user (<<rfc4252>>). No secret crosses the connection. The setup makes three Rivest-Shamir-Adleman (RSA) key pairs with `ssh-keygen`: `host_key` for the server, `alice_key` for alice, and `other_key`, which nobody authorized. Each writes its private key to the named file and the public half beside it with `.pub` added.

`--authorized-keys alice:alice_key.pub` gives the user `alice` the public keys in that file, which is in the OpenSSH `authorized_keys` format, one key a line (<<surl-readme>>). A single `.pub` file is already one such line. The option splits at the first colon: the user name, then the file. A file that cannot be read stops `surl` at start with exit `37`. Here it is the only account, so `alice` has no password: a password login as `alice` is refused, and so is anyone else's.

`--hostkey host_key` is the server's own key, which every SSH listener needs. `-k` skips checking it to keep this recipe about the client's key; <<scp-pin-the-host-key>> pins it instead, which is what to do outside a test.

On the `curl` side, `--key alice_key` names the private key and `--pubkey alice_key.pub` its public half. `curl` works the public half out from the private key when `--pubkey` is left off, and the login succeeds the same way, though `curl`'s manual (`curl --manual`) says that depends on how `curl` was built, so naming it is the safer habit. `-u alice:` names the user with an empty password after the colon; with the user alone, `curl` stops and prompts for a password (`curl --manual`). The user can go in the URL instead, `sftp://alice@127.0.0.1:8080/`, which never prompts.

A key that is not in `alice`'s file, `alice`'s key offered as another user, and a password are each refused, and `curl` exits `67`, login denied. `--directory site` serves the files under `site`. In the claims, `-s` hides the progress meter and `-S` still shows an error.
