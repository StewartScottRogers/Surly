=== Per-User SSH Keys in C#

==== Problem

Two deploy users log in to a Secure Shell (SSH) File Transfer Protocol (SFTP) server with their own SSH keys, and one must not be able to log in as the other. You want each key accepted for its own user and refused for the other, from a C# test with `Surl.Api` and `Curl.Api`.

==== Solution

Start a `SurlServer` with a host key and one `--authorized-keys` word pair for each user, then log in as each user with a `CurlClient` and that user{apos}s private key. The `setup` lines in `recipe.yml` make the keys with `ssh-keygen`:

==== Discussion

`SurlServerOptions` is `surl`{apos}s command line as properties. `ListenUrls` holds `sftp://127.0.0.1:0`, port 0 for a free one, `HostKeyFiles` is `--hostkey`, and `Files` holds the file in memory. `SurlServerOptions` has no property for `--authorized-keys`, so the program adds its words to `AdditionalArguments` one at a time: `--authorized-keys deploy-a:a_keys` for the user with two keys, and `--authorized-keys deploy-b:deploy_b.pub` for the other. In a public-key login the client signs with a private key and the server checks the signature against the public keys listed for that user (<<rfc4252>>).

`CurlClient.Create()` makes the client, and a `CurlRequest` is the method and the URL; the user goes in the URL, `sftp://deploy-a@127.0.0.1:port/hello.txt`. `CurlSshOptions` on the request carries the key: `PrivateKeyFile`, `PublicKeyFile`, and `AuthenticationTypes` set to `SshAuthenticationTypes.PublicKey`. A `CurlTlsOptions` whose `Origin`, a `CurlTlsPeerOptions`, has `VerifyPeer` false is `-k`, skipping the host key check, to keep this recipe about the users{apos} keys. A successful login returns a `CurlResponse` whose `Body` the program reads.

A key that is not listed for the user is not an answer but an error: `SendAsync` throws a `CurlException` whose `Code` is `LoginDenied`, 67. That covers `deploy-a`{apos}s key offered as `deploy-b`, `deploy-b`{apos}s key offered as `deploy-a`, `deploy-a`{apos}s second key offered as `deploy-b`, and any key offered as `deploy-c`, a user with no keys. The second key in `a_keys` logs in as `deploy-a`.

With `RecordExchanges` on, `FindEvents` with a `SurlEventQuery` for `SurlEventKind.LoginJudged` answers `LoginJudgedEvent` values: `Mechanism`, `Account` and `IsAccepted`. `deploy-a` was accepted by `publickey`. `deploy-b` was never accepted, and there is no refused login for it either: the client offers a public key before it signs with it, `surl` refuses the offer, and `AuthenticationTypes` holds the client to public keys, so it tries no other method that would be judged. A test that wants to see a refused key looks for the `LoginDenied` exception, not for an event.
