=== Uploading and Renaming over Secure Shell

==== Problem

A test uploads a file to a Secure Shell (SSH) File Transfer Protocol server under a temporary name and renames it when the upload is complete, so nothing reading the folder sees half a file, and you want a local server to check that against.

==== Discussion

SSH File Transfer Protocol (SFTP) is a file system protocol run inside a Secure Shell connection (<<rfc4251>>): besides reading and writing files it can list folders, rename, remove and make them. `-T notes.txt` uploads the local file to the path the URL names, `/notes.part`. `-Q` sends one of those other commands. Given as `-Q "rename /notes.txt /kept.txt"`, it runs before the transfer; with a dash in front, `-Q "-rename /notes.part /notes.txt"`, it runs after the transfer has succeeded (<<curl-readme>>). So the file is written under one name and appears under the other only once it is whole. Paths start at the root of what `surl` serves.

The listing afterwards has `notes.txt` and no `notes.part`. A URL ending in `/` names a folder: `-l` asks for its names, one a line, and without `-l` `curl` prints the long listing `surl` writes in the style of Unix `ls -l`, permissions, owner, size, date and name. A rename before the transfer shows up in the listing of the same call. Renaming a file that is not there fails, `No such file or directory`, and `curl` exits `21`, quote command error, without transferring anything. The same listener answers Secure Copy (SCP), and `-T` uploads over `scp://` as well.

Two of the `surl` options loosen something, and each refusal is the default:

* `--allow-uploads` accepts uploads and the commands that change files, rename among them (<<surl-readme>>). Without it, an SFTP upload is refused, `Permission denied`, and `curl` exits `9`, remote access denied; an SCP upload exits `25`, upload failed; a rename is refused with `Permission denied`, exit `21`, and the file keeps its name. Downloads work either way. It is off because anyone who can log in could otherwise write into everything `surl` serves.
* `--list-directories` answers listings. Without it, `surl` answers a listing as if the folder were not there, `No such file or directory`, and `curl` exits `78`, remote file not found. A listing tells whoever asks the name of every file, so it is off until asked for.

The rest is the usual SSH setup. `--throwaway-hostkey` makes a host key at start, for tests only, and `-k` skips checking it (see <<sftp-serve-with-a-throwaway-host-key>>, and <<scp-pin-the-host-key>> for doing it properly). `--user alice:s3cret` adds the account and `-u alice:s3cret` logs in as it. `--directory site` serves the files under `site` and takes the uploads. In the claims, `-s` hides the progress meter and `-S` still shows an error, which is where the refusals are read.
