=== Per-User SSH Keys from an Agent

==== Problem

Two deploy users log in to a Secure Shell (SSH) File Transfer Protocol (SFTP) server with their own SSH keys, and one must not be able to log in as the other. You want each key accepted for its own user and refused for the other, with an artificial intelligence (AI) agent driving `surl-mcp` and `curl-mcp`.

==== Solution

Write the agent's side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it starts an SFTP server with one authorized key file for each user through `surl-mcp`, then logs in as each user through `curl-mcp`{apos}s `curl` tool with that user{apos}s private key. ==== Discussion

`start_server` takes `surl`{apos}s own options in `arguments`: `--hostkey host_key` is the server{apos}s key, and `--authorized-keys deploy-a:a_keys` and `--authorized-keys deploy-b:deploy_b.pub` give each user the keys in a file, one public key a line. The files lie under `SURL_MCP_ROOT`. In a public-key login the client signs with a private key and the server checks the signature against the public keys listed for that user (<<rfc4252>>). `files` puts the file in memory, and `bound_urls` holds the real port.

The `curl` tool runs `curl` with the arguments given: `--key deploy_a` names the private key, `--pubkey deploy_a.pub` its public half, `-u deploy-a:` the user with an empty password, and `-k` skips the host key check to keep this recipe about the users{apos} keys. The key files lie under `CURL_MCP_ROOT`. The answer holds `exitCode`, here `0`, and `standardOutput` with the file.

A key that is not listed for the user is refused: `curl` exits `67`, login denied, `standardError` says so, and the call is a tool error. That covers `deploy-a`{apos}s key offered as `deploy-b`, `deploy-b`{apos}s key offered as `deploy-a`, `deploy-a`{apos}s second key offered as `deploy-b`, and any key offered as `deploy-c`, a user with no keys. A user may have more than one key: the second public key in `a_keys` logs in as `deploy-a`.

`get_events` with `kinds` set to `login_judged` answers a login per event: `mechanism`, `account` and `is_accepted`. `deploy-a` was accepted by `publickey`. `deploy-b` was never accepted, and logins as `deploy-b` were refused: after its key is refused, `curl` goes on to a password and keyboard-interactive, and those are judged and refused too.
