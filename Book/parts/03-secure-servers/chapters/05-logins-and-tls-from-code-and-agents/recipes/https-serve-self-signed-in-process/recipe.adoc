=== Serving HTTPS Behind a Login from C#

==== Problem

Your .NET test needs a Hypertext Transfer Protocol Secure (HTTPS) server that asks for a password, in the same process as the client under test, and the client has to get past both the certificate and the login.

==== Solution

Start a `SurlServer` with `SelfSigned` and one account, and send the `CurlClient` request with the account's login and certificate verification off; or make a certificate in the program and have the client trust it:

==== Discussion

An `https` listen URL needs a certificate before it needs anything else. `SurlServer.StartAsync` with `https://127.0.0.1:0` and no certificate throws `SurlServerStartException`, as `surl` would refuse to start; its first line in `Lines` starts with the exit code, `(58)`, and names the two ways out, `--cert` and `--self-signed`.

`SurlServerOptions.SelfSigned` is `surl`{apos}s `--self-signed`: the server makes a throwaway certificate when it starts. It is a loosening, and what it gives up is the point of a certificate: no client can tell this server from another one, because nothing vouches for its key. `Accounts` takes one `SurlAccount` per `--user`, here `alice` with the password `secret`. Once a server has an account, a request for `hello.txt` needs a login.

`CurlClient.Create()` makes the client, and each `CurlRequest` carries its own option groups. With none, the client verifies the server's certificate, as `curl` does, and the throwaway one fails: `SendAsync` throws `CurlException`, whose `Code` is 60, `PeerFailedVerification`. A Transport Layer Security (TLS) failure is an exception; an answer the server gives is not.

`CurlTlsOptions` is the request's TLS group, and its `Origin` is a `CurlTlsPeerOptions` for the server being fetched from. `VerifyPeer` and `VerifyHost` set to `false` are `curl -k`: the client takes the certificate without checking who signed it or which name it carries. With that, the requests reach the server, and the login decides. `CurlAuthenticationOptions` carries it, `UserName` and `Password`, with `HttpAuthentication` left at its default, Basic (<<rfc7617>>). No login is `401 Unauthorized`; so is a wrong password. Both come back as an ordinary `CurlResponse` with `StatusCode` 401, so a test checks the status, not a `catch`. With `alice` and `secret` the answer is `200 OK` and the file.

Skipping verification is fine for a test that only needs the bytes to arrive. When the test is about the client's own TLS handling, give the server a certificate the client can check. The program makes one with .NET's `CertificateRequest`: a 2048-bit RSA key, the name `127.0.0.1` as an IP address in the subject alternative name, valid for 30 days, signed by its own key (<<rfc5280>>). It writes the certificate and the key as PEM files into a temporary folder; `CertificateFile` and `KeyFile` are `surl`{apos}s `--cert` and `--key`. The client gets the same certificate as `CertificateAuthorityBlob`, `curl --cacert` from memory, and leaves `VerifyPeer` and `VerifyHost` on. The handshake verifies (<<rfc8446>>), the login is accepted, and the answer is `200 OK`. No private key goes into the repository: the program makes a new one every run and deletes the folder at the end.

`await using` stops each server at the end of its block, and the client is disposed last. The program exits 0 whatever the requests got; the printed lines are what a test would assert on.
