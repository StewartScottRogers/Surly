=== Logging In over HTTP with NTLM

==== Problem

A client logs in to a Windows web server with NT LAN Manager (NTLM) or Negotiate, and you want a local Hypertext Transfer Protocol (HTTP) server that asks for that login and checks it.

==== Discussion

`--directory site` serves `site`, and `-u alice:s3cret` adds the account; once an account exists, every request needs a login. A request without one is answered `401 Unauthorized` with a `WWW-Authenticate` header for each method the server accepts (<<rfc9110>>); `-i` shows the response headers along with the body, and `-s` hides the progress meter.

`--auth ntlm` is the loosening option: it sets the methods `surl` accepts and offers to NTLM alone, so the `401` offers `WWW-Authenticate: NTLM` and nothing else. By default the `401` offers Digest, and neither NTLM nor Negotiate; `curl --ntlm` gets `401` and goes no further. NTLM is not the default because an NTLM response is built from a hash of the password: anyone who captures one can try passwords against it offline, or relay it to another server while it is fresh (<<surl-readme>>). `surl` writes a `surl: warning:` line naming the methods it accepts whenever `--auth` is given.

`--ntlm` makes `curl` answer the `401` with NTLM, and `-u` gives it the name and password. NTLM is a challenge and response over three messages on one connection (<<ms-nlmp>>): `curl` asks, `surl` answers `401` with a random challenge, and `curl` sends a value computed from the challenge and the password, never the password itself. So it is accepted over plain `http://`, with no Transport Layer Security (TLS). A wrong password is answered `401` again; `-f` makes `curl` exit `22` on that instead of `0`, and `-S` still prints the error with `-s`.

`--auth ntlm` accepts NTLM and turns the default methods off; it lets no password through in clear. `-u` without `--ntlm` sends Basic, the password in clear, and over `http://` that is refused `403 Forbidden` without being checked. `-o` sends the body nowhere and `-w "%{http_code}"` prints the status, which is how the checked claims read it.

Negotiate is what Windows clients send first: it carries Kerberos when the machine is in a domain, and NTLM when not. `--auth negotiate` makes `surl` offer `WWW-Authenticate: Negotiate`, and it checks NTLM carried inside it (<<surl-readme>>). `--negotiate` makes `curl` answer with Negotiate instead. On a Windows machine in no domain, though, with no Kerberos to use, it finds no credentials to send: Windows answers `SEC_E_NO_CREDENTIALS`, the `401` stands, and with `-f` `curl` exits `22` naming that error. From version 8.22.0, `curl` no longer lets Negotiate fall back to NTLM, so a Windows client of that version with no Kerberos logs in with `--ntlm` or not at all (<<curl-changes>>). Test Negotiate against `surl` with Kerberos, which `--keytab` adds (<<surl-readme>>).
