=== Searching over LDAPS from an Agent

==== Problem

Your app binds to the directory with a simple bind, which `surl` refuses over plain Lightweight Directory Access Protocol (LDAP). You want the same bind accepted over LDAP over Transport Layer Security (LDAPS) against your own certificate, without loosening anything, with an agent driving `surl-mcp` and `curl-mcp`.

==== Solution

The program is the agent's side of the conversation, over the official Model Context Protocol (MCP) software development kit (SDK). It starts one server with both an `ldaps://` and an `ldap://` listener, seeds its directory, and binds as the same account on both:

==== Discussion

The program starts `surl-mcp` and `curl-mcp` by name, each confined to the working folder through `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. The `openssl` line of the recipe made `server.pem` and `server.key` there, a certificate for `127.0.0.1` signed by its own key. `start_server` takes `listen_urls`, here the two addresses on port `0`, and `arguments`, the other `surl` options in `surl`{apos}s own words: `--cert` and `--key` for the certificate, and `--user alice:s3cret` for the account. Nothing that loosens the login is given: `--allow-plaintext-auth` stays off. The answer lists `bound_urls` in the order given, with the ports the system chose.

The directory starts empty. `add_ldap_entries` puts LDAP Data Interchange Format (LDIF) text into it, all or none, and answers how many entries it added: two, the top of the tree and bob. Nothing is written to disk.

The `curl` tool of `curl-mcp` runs `curl` with the arguments the agent gives, and answers in text, as JavaScript Object Notation (JSON), with the standard output, the standard error and the exit code. `-u alice:s3cret` is a simple bind, which sends the name and password as they are (<<rfc4511>>); `-s` and `-S` quiet the progress meter and keep the error message. The URL is the search (<<rfc4516>>), the base distinguished name, the attributes, the scope and the filter separated by `?`. On the `ldap://` listener `surl` refuses the bind `confidentialityRequired` without looking at the password: the right one and a wrong one are both refused with `curl` exit `38`, and on Windows the program prints `Confidentiality Required`, which is how the two refusals differ from the one on the other listener. On the `ldaps://` listener TLS (<<rfc8446>>) encrypts the connection before the first LDAP message, so the bind is checked: the right password is accepted and the search answers with bob{apos}s mail, and a wrong password is refused `Invalid Credentials`, also exit `38`. That is Windows. On Linux and macOS, where `curl` uses the OpenLDAP library, the error names neither phrase, so the program prints none, and the exit codes tell the refusals apart: the wrong password over `ldaps://` exits `67`, `Login denied`, the code that library{apos}s build of `curl` gives `invalidCredentials`, while both binds on `ldap://` exit `38`.

`-k` makes `curl` skip the check of the certificate, which is signed by its own key, so nothing vouches for it. That is a loosening on the client, for a throwaway certificate on your own machine, and it is the only way the program trusts that certificate: on Windows, the last bind, without `-k`, exits `60`, since the Windows LDAP library checks the Windows certificate store, and `--cacert` does not change that. The program prints the exit code and the one phrase the error message holds, not the whole message, because the rest of the wording is the LDAP library{apos}s and differs between platforms.
