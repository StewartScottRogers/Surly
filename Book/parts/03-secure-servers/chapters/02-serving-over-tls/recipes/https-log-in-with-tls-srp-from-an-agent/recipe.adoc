=== Logging In with TLS-SRP from an Agent

==== Problem

Your device authenticates the Transport Layer Security (TLS) connection with a user name and password, TLS-SRP (Secure Remote Password), instead of a certificate, and an agent runs your tests. You want the agent to stand up a server that holds the device's account and needs no certificate, to add, change and remove accounts while it runs, and to see that a client that cannot log in is refused in the handshake.

==== Solution

Start the server with `surl-mcp`{apos}s `start_server`, giving `--tlsuser` and `--tlspassword` in `arguments`, try it with `curl-mcp`{apos}s `curl` tool, ask `wait_for_event` what the server recorded, and change accounts with the TLS-SRP account tools:

==== Discussion

TLS-SRP runs the password check inside a TLS 1.2 handshake, with no certificate involved (<<surl-readme>>). `StdioClientTransport` starts both hosts by name, each confined to the program's folder. `start_server` starts a server that behaves as `surl` with the same options, and `arguments` takes them in `surl`{apos}s own words: `--tlsuser device --tlspassword s3cret` is one account, and it implies `--tlsauthtype SRP`, so the HTTPS listen URL serves TLS 1.2 with the SRP cipher suites and nothing else. No certificate option is given. TLS 1.3 cannot be served that way, so `--tlsv1.3` beside it makes `start_server` a tool error with `exit_code` 2 (`FailedInit`) and `surl`{apos}s line.

The client has to be one that speaks TLS-SRP: your device, or a TLS library built with SRP. `curl-mcp` is not one. Its `transfer` tool has no field for TLS-SRP, and its `curl` tool, which takes a `curl` command line in `args`, follows curl 8.22.0, which dropped TLS-SRP: given `--tlsauthtype SRP --tlsuser device --tlspassword s3cret`, it warns on standard error that each `is deprecated and has no function anymore` and sends a handshake with no SRP suite (<<curl-manual>>). The answer's `exitCode` is 35, a failed handshake, and the call is a tool error. `-k` is there because no certificate exists to verify. So the agent cannot show a login with the right password, and claims none.

The server's side: `wait_for_event` with `kinds` `exchange_ended` returns the first event of that kind, and the refused connection ended with `received_byte_count` 0. The handshake (<<rfc8446>>) ended it before any request was read.

The account tools change the TLS-SRP accounts while the server runs. `add_tls_srp_account` takes `server_id`, `user` and `password` and answers `{"user": ...}`; a user that already has an account is a tool error. `set_tls_srp_account_password` changes a password, the account given at start included, and a user with no account is a tool error. `remove_tls_srp_account` removes one, the one given at start included; removing it again is a tool error. On a server started without TLS-SRP, `--self-signed` here, every one of them is a tool error: `server s1 was not started with TLS-SRP`.
