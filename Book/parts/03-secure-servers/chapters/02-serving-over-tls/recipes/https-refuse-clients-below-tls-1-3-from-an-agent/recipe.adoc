=== Requiring TLS 1.3 from an Agent

==== Problem

You want an artificial intelligence (AI) agent to start a server that accepts Transport Layer Security (TLS) 1.3 only, and to find out what a client limited to TLS 1.2 gets, with Model Context Protocol (MCP) tool calls and no shell.

==== Solution

The program is the agent's side: it starts `surl-mcp` and `curl-mcp`, calls `start_server` with `--tlsv1.3` among its `arguments`, then calls `curl-mcp`{apos}s `curl` tool twice, once as a TLS 1.2 client and once as a TLS 1.3 client. ==== Discussion

`StdioClientTransport` starts each host by name from `PATH`, and `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine both to the folder the program runs in, which is where `server.pem` and `server.key` are. The argument after `--` picks the scenario; with none, the program runs the solution.

`start_server` starts a server that behaves as `surl` with the same options. `listen_urls` is `https://127.0.0.1:0`, port 0 for a free one, and `bound_urls` in the structured answer holds the real address. The TLS options have no argument of their own: `arguments` takes any other `surl` option in `surl`{apos}s own words, one list item each, so `["--cert", "server.pem", "--key", "server.key", "--tlsv1.3"]` is the command line `--cert server.pem --key server.key --tlsv1.3` (<<surl-readme>>). `files` puts `hello.txt` in the server in memory.

`curl-mcp` has a field-based `transfer` tool too, whose `minTlsVersion` sets the lowest version, as `--tlsv1.3` does, and whose `caFile` is `--cacert`, but it has no field that caps the version, as `--tls-max` does, so it cannot play the older client. So that the two clients differ in their version and nothing else, the agent uses the `curl` tool for both, which takes `curl`{apos}s arguments as a list with no shell and no quoting: `--tls-max 1.2` makes the client an older one, `--tlsv1.3` makes it insist on 1.3, and `--cacert server.pem` trusts the certificate, so the only thing that can fail is the version (<<curl-readme>>). The answer is text holding JSON; the program reads `exitCode` and `standardOutput.content`.

Against the `--tlsv1.3` server the TLS 1.2 client exits `35`, the code for a failed TLS handshake, and prints nothing. The exit code in the answer is what an agent reads. The TLS 1.3 client that follows exits `0` with the file, so a refused handshake does not stop the server (<<rfc8446>>). Started without `--tlsv1.3`, as in the `1.2` case, the server serves the TLS 1.2 client as well, because `surl` accepts TLS 1.2 and 1.3 by default.

A range with nothing in it, `--tlsv1.3` with `--tls-max 1.2`, never starts: `start_server` is a tool error whose text is `surl`{apos}s own refusal, and the program exits `2`. An agent reads the message and fixes the arguments, as a person would after the same mistake on the console.

On macOS `surl` cannot serve TLS 1.3: its TLS there is the system{apos}s, which offers a server TLS 1.2 at most. Even without `--tlsv1.3` the TLS 1.3 client exits `35`, and with it every client does. The claims that need a TLS 1.3 handshake are marked Windows and Linux only.
