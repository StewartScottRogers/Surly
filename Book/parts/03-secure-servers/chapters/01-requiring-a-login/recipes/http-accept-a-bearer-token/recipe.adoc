=== Accepting a Bearer Token over HTTPS

==== Problem

The client you are testing sends an `Authorization: Bearer` token, not a user name and password, and you want a server that accepts one token and refuses the rest.

==== Solution

Make a certificate, give `surl` an account with an empty user name whose password is the token, and send the token with `curl --oauth2-bearer`:

==== Discussion

`--user :t0ken-abc` is an account whose user name is empty; `surl` reads its password as a Bearer token (<<rfc6750>>), so a request carrying `Authorization: Bearer t0ken-abc` is let in. `--oauth2-bearer t0ken-abc` makes `curl` send that header, and `--directory site` is the folder served. A different token, or none, is answered `401 Unauthorized`. The empty user name is a user name like any other, so it can be given only once: a second `--user :t0ken-def` stops the start with exit `2`, and a server holds one token.

A Bearer token is a password by another name: whoever holds it is let in, and it travels as it is. So `surl` treats it as one. The recipe serves Hypertext Transfer Protocol Secure (HTTPS), where Transport Layer Security (TLS) (<<rfc8446>>) encrypts the connection before the header is sent. The `openssl` line makes the certificate for `127.0.0.1` and its private key; `--cert server.pem` and `--key server.key` serve them, and `--cacert server.pem` makes `curl` trust that certificate, which no certificate authority signed. `-s`, `-o` and `-w "%{http_code}"` print only the status code.

Over plain `http://` the token would cross the network in clear, and `surl` refuses it without checking it: the recipe's second server, `plain`, is `surl --directory plain --user :t0ken-abc` on `http://127.0.0.1:8081/`, the same token with no certificate, and both the right token and a wrong one are answered `403 Forbidden`. That is the default because anyone who can watch the connection can copy the token and use it.

`--allow-plaintext-auth` turns that refusal off: the third server, `loose`, is the `plain` command with `--allow-plaintext-auth` added, on port 8082, and it checks a token sent over `http://`, letting the right one in and answering a wrong one `401`. It is a loosening option, for tests only, and gives up exactly what the default protects: the token is readable to anyone on the path. `surl` warns on every start while it is on (<<surl-readme>>).
