=== Accepting Basic over HTTPS from an Agent

==== Problem

Your client only speaks HTTP Basic, and must never send its password in clear. You want a server that offers Basic alone, accepts it over Hypertext Transfer Protocol Secure (HTTPS), and refuses it unchecked over plain Hypertext Transfer Protocol (HTTP), with an agent driving `surl-mcp` and `curl-mcp`.

==== Discussion

The program starts `surl-mcp` and `curl-mcp` by name, each confined to the working folder through `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. The `openssl` line of the recipe made `server.pem` and `server.key` there, a certificate for `127.0.0.1` signed by its own key. `start_server` takes `listen_urls`, here an `https://` and an `http://` address on port `0`, and `arguments`, the other `surl` options in `surl`{apos}s own words: `--cert` and `--key`, `--auth basic` for Basic alone (<<rfc7617>>), and `--user alice:s3cret`. `files` holds `hello.txt` in memory. The answer lists `bound_urls` in the order given, with the ports the system chose. `--auth` is a loosening option, and `surl` warns on every start while it is given (<<surl-readme>>).

The `curl` tool of `curl-mcp` runs `curl` with the arguments the agent gives, and answers in text, as JavaScript Object Notation (JSON), with `standardOutput` and the exit code. `-s` silences the progress meter, `-i` puts the status line and the headers before the body, and `--http1.1` keeps the header names as written; the program prints the status, each `WWW-Authenticate` header between brackets, and the body of a `200`. A refusal{apos}s body from `surl` is one line naming its status, such as `401 Unauthorized`, so the program leaves it out.

Over `https://`, with `-u alice:s3cret` for the login and `--cacert server.pem` so that `curl` trusts the certificate, Transport Layer Security (TLS) (<<rfc8446>>) encrypts the connection, and the server checks the login: the right password gets `200` and the file, and a wrong one gets `401`. A request with no login gets a `401` that offers `Basic realm="surl"` and nothing else, and `--digest` with the right password gets that same `401`, since a method that is not offered is not accepted.

Over `http://`, the right password gets `403 Forbidden`, and so does a wrong one: the server does not look at a password that arrived in clear. A request with no login gets `403` with no `WWW-Authenticate` header, because the only method on offer may not be used there. For a test whose client cannot use TLS, `--allow-plaintext-auth` checks Basic over `http://` as well; see <<http-refuse-a-password-in-clear>>.
