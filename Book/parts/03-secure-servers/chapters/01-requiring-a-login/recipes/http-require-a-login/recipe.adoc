=== Requiring a Login over HTTP

==== Problem

==== Discussion

`--directory site` serves the folder `site`, and `--user alice:secret` adds one account, Alice with the password `secret`. The option is repeatable, one account each time, and its value is split at the first colon, so a user name never holds a colon and a password may: Bob's password here is `pass:word`. A user name given twice, or an empty password, stops the start with exit `2`.

With no account configured, which is the default, a `GET` needs no login: the recipe's second server, `surl --directory public` on port 8081 with no `--user`, serves its folder to anyone, and `curl` gets the file with no `-u`. Once any account is configured, every HTTP request on the listener needs a login (<<surl-readme>>). A `GET` with none is answered `401 Unauthorized`, and so is a `HEAD` (`-I`); so is Alice with the wrong password, and Carol, whom no `--user` names. `curl` exits `0` for each, because a `401` is still an answer; `-s`, `-o` and `-w "%{http_code}"` print only the status code.

`curl --digest -u alice:secret` logs in with HTTP Digest (<<rfc7616>>): `curl` sends the request, reads the `401` and its challenge, and sends it again with a response computed from the password and the challenge, never the password itself. That is why it works over plain `http://`. A password sent as it is, the way `curl -u` sends it without `--digest` (HTTP Basic), is answered `403 Forbidden` over `http://`, even with the right password; see <<http-refuse-a-password-in-clear>>.

The password is on the command line, where other local users can read it in the process list. That is fine for a test; for anything else, see <<http-keep-passwords-out-of-the-process-list>>.
