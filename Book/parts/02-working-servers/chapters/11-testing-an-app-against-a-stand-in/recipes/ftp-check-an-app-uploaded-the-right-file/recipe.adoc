=== Checking an App's Upload

==== Problem

Your app uploads a nightly export over the File Transfer Protocol (FTP). You want a test that runs it against a stand-in, fetches what arrived over the Hypertext Transfer Protocol (HTTP), and fails if it is not byte for byte the file you expected.

==== Solution

Run one `surl` that takes uploads over FTP and serves the same files over HTTP, run the app, then run a check that fetches the file and compares it with the expected one. ==== Discussion

One `surl` listens on two URLs, one per protocol, and both read and write one store, here held in memory. FTP and HTTP each need a Transmission Control Protocol (TCP) port of their own, so the two URLs name two ports. `--allow-uploads` lets a client write, which `surl` refuses by default: a server that anyone can write to is a decision, not a default. `--allow-anonymous` lets `curl` log in over FTP, and fetch over HTTP, without an account (<<surl-readme>>). The file the app stores over FTP is served over HTTP at the same path, with no copy made, so the check reads what the server holds and not a file the test wrote itself.

The app uploads with `-T`, and `--ftp-create-dirs` makes the `exports` folder when it is missing (<<curl-readme>>, <<rfc959>>). Without `--allow-uploads` making that folder is the first write the server refuses, so the app exits `9`, not the `25` of a refused upload. Without `--allow-anonymous`, and with no account given, the app{apos}s anonymous login is refused and it exits `67`. The broken variant, given `broken`, leaves out the last row and still exits `0`: nothing in the app{apos}s own result says the file is wrong.

The check is what fails the test. It fetches the file into `arrived.csv` with `-o`, and with `-f`, so a 404 is `curl` exit `22` and not a "404 Not Found" page compared as if it were the export (<<rfc9110>>): when the file never arrived, the check exits `22`. `-s` hides the progress meter and `-S` keeps the error text. `cmp -s` compares the two files byte for byte and says nothing, so the script writes its own line, with the two sizes counted by `wc -c` (piped through `tr -d ' '`, since some `wc` pad the count): with the last row missing it prints `expected 38 bytes, arrived 27` and exits `1`, which is the failing test.
