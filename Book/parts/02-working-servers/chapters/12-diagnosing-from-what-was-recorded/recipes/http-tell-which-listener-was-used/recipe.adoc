=== Telling Which Listener Was Used

==== Problem

One `surl` listens on several URLs, two for Hypertext Transfer Protocol (HTTP) and one for File Transfer Protocol (FTP), and you want to know which one a client actually used: from the log, from the trace, and for certain.

==== Solution

Serve all three from one `surl` with `--trace-ascii`, and with its control endpoint on, then let the clients run and ask the control endpoint for the listen URL of each exchange. The script below puts that beside what the trace says; it needs a POSIX shell (Git Bash on Windows):

==== Discussion

`surl` takes as many listen URLs as it is given and serves `--directory site` on each, so the report is the same on the first HTTP listener, the second and the FTP one. `--allow-anonymous` is there for FTP: without it, and with no account, the FTP listener refuses `curl`{apos}s anonymous login and `curl` exits `67` (<<rfc959>>). It loosens the server and warns on start, so keep it to tests. The app was meant to use the first HTTP listener and was configured with the second; it gets its report all the same, and nothing in the answer says which listener gave it.

`--trace-ascii trace.txt` records every byte both ways, and between the bytes the lines of `surl`{apos}s log (<<surl-readme>>). With a trace given, those lines go to the trace and not to `--log-file`, so `surl.log` holds none of them. For each exchange the log line is `#N * Exchange N opened: http from 127.0.0.1:52340.`: the scheme and the client's address, never the listen URL. That tells the FTP download from the two HTTP fetches, but the two HTTP listeners read alike. The trace also holds each request's `Host` header, and that is the client's word, not the server's (<<rfc9110>>): `curl` fills it from the URL it was given, and `-H "Host: ..."` replaces it with anything. The third client connects to the second listener with a `Host` that names the first; `surl` serves it `200`, and the trace now holds a request naming a listener no client connected to.

The record that knows is the server's own. `--control http://127.0.0.1:8083/` serves an HTTP control endpoint on loopback, and `--control-token-file token.txt` names the file whose first line is the bearer token every request to it must carry; without it the endpoint answers `401`. `curl -H @control.hdr` reads that header from a file, so the token is never on a command line. `GET /v1/events?kind=exchange_started` answers each exchange's `exchange_id` and `listen_url`, the URL that accepted the connection, with its bound port. `which-listener.sh` first waits, at most 10 seconds, until as many exchanges have ended as started, then prints each listen URL beside the trace's scheme and `Host`: exchanges 1 and 3 came through the second HTTP listener, whatever the third one's `Host` said, and 2 through the FTP one. `GET /v1/exchanges?listen_url=...` answers one listener's exchanges alone: none for the first, 1 and 3 for the second.

The control endpoint can change the server's files, mail and accounts as well as read its record, which is why it needs a token and listens only on loopback (<<surl-readme>>). In the clients, `-s` keeps `curl` quiet, `-o` sends a body to nowhere, and `-w` prints the status. The `ready: none` in `recipe.yml` and the `seed:` line wait for the control endpoint, which listens last: `--retry-connrefused` retries while nothing listens, up to `--retry` times, `--retry-delay` seconds apart. A check that connected to each listener first would have opened exchanges of its own.
