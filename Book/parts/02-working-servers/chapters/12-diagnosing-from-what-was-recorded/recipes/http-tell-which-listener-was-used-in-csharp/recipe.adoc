=== Telling Which Listener Was Used in C#

==== Problem

Your C# test starts one in-process server with several listeners, two for Hypertext Transfer Protocol (HTTP) and one for File Transfer Protocol (FTP), and you want it to assert that the client used the right one, by the `ListenUrl` of its recorded exchange.

==== Solution

Start the server with `RecordExchanges` on, let the client fetch, wait for its exchange to end, and compare that exchange's `ListenUrl` with the bound URL of the listener it should have used:

==== Discussion

`SurlServerOptions.ListenUrls` takes as many listen URLs as `surl` does on its command line; three on port 0 get three free ports, and `server.BoundUrls` lists them in the same order, so `BoundUrls[0]` is the app's listener, `BoundUrls[1]` the other HTTP one and `BoundUrls[2]` the FTP one. All three serve the one report in `Files`. `AllowAnonymous` is `surl --allow-anonymous`, there for FTP: without it, and with no account, the FTP listener refuses the anonymous login, and `CurlClient.SendAsync` throws a `CurlException` whose `Code` is `LoginDenied` (<<rfc959>>). It loosens the server, so keep it to tests.

A client configured with the wrong port is served all the same: the `CurlResponse` is a `200` and nothing in it says which listener answered. The record says. `RecordExchanges` keeps every exchange as a `SurlExchangeRecord`, and its `ListenUrl` is the listen URL that accepted the connection, with its bound port, beside its `Scheme` and its `Received` bytes. `server.WaitForExchangeAsync` with a `SurlEventQuery` for `SurlEventKind.ExchangeEnded` waits, for at most 10 seconds here, for the first exchange to end and returns its record, so the test never reads one half kept. The assertion compares `ListenUrl` with `BoundUrls[0]`: the right port passes; the other port fails, and the test prints the listener the fetch really came through. `server.FindExchanges` with `ListenUrl` set in the query answers one listener's exchanges alone, none for the app's listener in that run.

The log is not the place to look. `Log` with `LogLevel.Info` writes one line per exchange, `#1 * Exchange 1 opened: http from 127.0.0.1:52340.`, the scheme and the client's address, never the listener, so it reads the same for both HTTP listeners (<<surl-readme>>). Nor is the request's `Host` header, which is the client's word, not the server's (<<rfc9110>>): with `Headers` on its `CurlRequest` the client may send any `Host`, and one that names the app listener while it connects to the other is served, recorded as sent, and the record still names the other listener. An FTP download's exchange names the FTP listener and scheme `ftp`, and its bytes have no `Host` at all (<<curl-readme>>).
