=== Uploading Several Files from an Agent

==== Problem

You want an artificial intelligence (AI) agent to upload a batch of files to a Hypertext Transfer Protocol (HTTP) server in one `curl` call and then check, from the server{apos}s side, that each one arrived.

==== Solution

Write the agent{apos}s side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): start a server with an account and uploads on, call `curl-mcp`{apos}s `curl` tool once with an `-T` and a URL for each file, then call `list_files` on the folder:

==== Discussion

`start_server` starts a server as `surl` with the same options would: `arguments` carries `--user alice:s3cret`, an account, and `--allow-uploads`; `files` puts `reports/old.txt` in its in-memory store, so the folder `/reports` exists. Its structured answer gives the `server_id` and the real port in `bound_urls`.

The `curl` tool runs one `curl` command line given as `args`, a list with one entry per argument and no shell in between. The program builds `-T a.txt URL -T b.txt URL -T c.txt URL`: each `-T` pairs with the URL after it, and each URL ends in `/reports/`, so `curl` appends the file{apos}s name. `--digest -u alice:s3cret` logs in with Digest on every upload, and `-w "%{http_code} %{url.path}\n"` prints one line per transfer: `201 Created` three times (<<rfc9110>>). The files come from the folder `CURL_MCP_ROOT` names. The answer is text holding JavaScript Object Notation (JSON): `exitCode`, `standardOutput` and `failure`.

The console{apos}s shorter form, `-T "{a,b,c}.txt"`, works here too. `curl-mcp` checks every local path against `CURL_MCP_ROOT` before it runs `curl`, a glob{apos}s by expanding it first, and these three names are inside the root, so all three are uploaded. A name that leaves the root, `../b.txt`, given plainly or by a glob such as `-T "{a,../b}.txt"`, is refused: a tool error with `exitCode` null, and the refusal covers the whole call, so not even `a.txt`, listed before it, is sent. A name inside the root with no file behind it is `curl`{apos}s own failure instead: it uploads `a.txt`, stops at `missing.txt` with exit `26`, and never sends `c.txt`.

`list_files` reads a folder of the server{apos}s store by `server_id` and `path`, without a request, and answers `entries` with each file{apos}s `name` and `byte_count`, in name order. It is the check the agent trusts, rather than the status lines. Without a login each upload is `401 Unauthorized`, with that line as its body; to the `curl` tool that is a successful run, `exitCode` 0 and no tool error, since `curl` without `-f` exits 0 on any answer, and `list_files` shows nothing new.
