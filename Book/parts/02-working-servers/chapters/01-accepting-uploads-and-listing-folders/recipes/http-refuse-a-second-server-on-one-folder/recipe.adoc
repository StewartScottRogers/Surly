=== Refusing a Second Server on One Folder

==== Problem

You start a second `surl` on a folder another `surl` is already serving, perhaps to add a protocol, and it exits at once with code 124.

==== Solution

==== Discussion

`--directory site` makes `site` the store `surl` serves from and writes uploads and its own state into. While it runs, `surl` holds the lock file `site/.surl/lock`, so that two servers never write the same files at once. A second `surl` given the same folder writes `surl: (124) Directory site is in use by another surl process` to standard error and exits `124` before it listens on anything. The recipe sends standard error to standard output with `2>&1` only so the line shows beside the command.

The lock is on the folder, not on the protocol, the port or the spelling. A second `surl` that would serve File Transfer Protocol (FTP) on another port is refused the same way, and so is one given `./site/` for `site`; the line repeats the name as it was given. The first `surl` is untouched by any of this and goes on serving.

What to do instead depends on what the second server was for:

* To serve the same folder over another protocol, give the one `surl` both listen URLs. Here `http://127.0.0.1:8080/` and `ws://127.0.0.1:8081/` share `site`, and a WebSocket request gets the same file a Hypertext Transfer Protocol (HTTP) request does.
* To run a second, separate server, give it another folder. A `surl` on `other` runs alongside the first.
* Otherwise stop the first `surl`, or leave `--directory` off to serve from memory (<<surl-readme>>).

The lock file stays in `site/.surl` after `surl` stops; the operating system releases the lock itself when the process ends, even when it is killed, so a leftover file never blocks the next start (<<surl-readme>>).
