=== Listing a Directory Served over the Web

==== Problem

A test fetches files from a local web server and needs to see which files a folder holds, but asking for the folder's address gets `404 Not Found`.

==== Discussion

The Hypertext Transfer Protocol (HTTP) server in `surl` never lists a folder. A request for a folder is answered `404 Not Found` with an empty body, with `--list-directories` or without it, the same answer a missing path gets. HTTP has no listing of its own (<<rfc9110>>): the index pages other web servers make up are a convention, and `surl` does not make one.

The listing comes from the WebSocket server instead. `ws://127.0.0.1:8081/` is a second listen URL on the same `surl` command, so both listeners serve the one directory. `curl` upgrades its request to a WebSocket (<<rfc6455>>), and `surl` answers a file's path with the file's bytes and a folder's path with the listing, each as one message, then closes. `curl` writes the message to standard output and exits `0`.

The listing is one name a line, files and folders together, a folder's name ending in `/`. Names that begin with a dot are left out, so neither `.hidden` nor `surl`{apos}s own `.surl` folder appears. A subfolder is listed the same way, with or without the trailing slash.

`--directory site` names the folder that both listen URLs serve. `--list-directories` is the option that turns listings on. Without it the WebSocket server refuses a folder `404`, as if it were not there, and still sends files. It is off by default because a listing tells a stranger the name of every file, including the ones nobody was told about (<<surl-readme>>).

Each listen URL serves only its own scheme: the `http` port does not take a WebSocket upgrade, so `ws://` to that port fails. A refused upgrade, `404` included, makes `curl` exit `22`. In the claims below `-s` keeps `curl` quiet, `-o` sends the body nowhere, and `-w "%{http_code}"` prints the status.
