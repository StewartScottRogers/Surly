=== Forwarding Mail with an Alias

==== Problem

You want mail to `support@example.com` to reach two real mailboxes, and you want to see what `surl` does when an alias is set up wrongly, such as one that is also a mailbox.

==== Solution

Give `surl` a `--mail-alias` that names the alias and the mailboxes behind it. The form mails `support@` before the cases run, and an Internet Message Access Protocol (IMAP) search finds the message in both mailboxes:

==== Discussion

`--mail-alias "support@example.com=ann@example.com,bob@example.com"` makes `support@` an address that delivers a copy to each mailbox after the `=`. The quotes keep the comma and the `=` from the shell. The rest is a mail server for one domain: `--mail-domain example.com` serves it, and each `--mailbox` adds a mailbox and the account that logs in to it by its whole address, for the form, Ann and Bob (<<surl-readme>>). The alias is neither; it has no mailbox and no login. One `surl` with both an `smtp://` and an `imap://` listen URL runs them over one mail store, so what the first receives the second reads.

On the `curl` side, `-u` is the form{apos}s login, `--mail-from` and `--mail-rcpt` are the envelope of the message (<<rfc5321>>), `-T help.eml` is the message, and `--crlf` turns the file{apos}s line feeds into the carriage return and line feed a message is made of. `-s` keeps `curl` quiet and `-S` lets it still print an error, and `-o` throws a body away. The IMAP checks are searches by subject, and `--next` starts the next transfer in the same command; each transfer repeats its own options, `-u` included. Delivery is asynchronous, so the second `seed` line does not assume the mail has arrived. `--retry 10` allows ten retries at most, `--retry-all-errors` makes every failure count, which an unfinished delivery is, and `--retry-delay 1` waits a second between tries, until a fetch of Bob{apos}s message by its unique identifier (UID) succeeds, without any fixed sleep (<<curl-manual>>).

The stored copy is the message the form sent. Its `To` field still names `support@example.com`, and no header names Ann or Bob. The sending account{apos}s own `INBOX` is empty, since only the alias{apos}s targets receive the mail (<<rfc9051>>).

Several routes to one mailbox make one copy. One message to `support@` and `ann@` together reaches Ann once, so her `INBOX` and Bob{apos}s hold two messages each, UIDs `1` and `2`, not three.

An alias is an address, not an account. An IMAP login as `support@example.com` is denied with exit `67`. Three mistakes in the alias itself stop `surl` at start with exit `2`, before any mail could vanish: an alias that is also a mailbox, a target that names no mailbox, such as the typo `anne@`, and a target outside every `--mail-domain`. Each prints one line, naming the address.
