=== Waiting for a Client's Upload from C#

==== Problem

The code under test uploads a file to a Hypertext Transfer Protocol server in the background, and your test has to know when the file has landed without sleeping or polling.

==== Solution

Turn on `RecordExchanges`, start the upload, and await `server.WaitForEventAsync` with a `SurlEventQuery` naming the file:

==== Discussion

`SurlServerOptions` has one listen URL on port 0, `AllowUploads` on (`surl`{apos}s `--allow-uploads`), one `SurlAccount` for the client to log in as, and `RecordExchanges`. The last is the switch the wait needs: with it on, the server keeps its events for queries; with it off, the default, `WaitForEventAsync` throws `InvalidOperationException`, as the `off` mode shows, even though the upload itself succeeds.

The code under test is `Upload`: a `CurlClient` sends a `CurlRequest` with `HttpMethod.Put` and a byte-array body, logged in through `CurlAuthenticationOptions` with `HttpAuthentication` set to `HttpAuthenticationMethods.Digest`, `curl --digest`, and returns the status from the `CurlResponse`. The program starts it and keeps the `Task` without awaiting it, as a test does when the upload happens inside the system it is testing.

The test waits with a `SurlEventQuery`. Every property left unset matches anything; this one sets `Store` to `StoreKind.Content`, the store files live in, and `Name` to `/report.csv`, the path. `WaitForEventAsync` takes the query and a timeout and returns the first matching event. It is typed as the base event, so the program casts it to `StoreChangedEvent` to read `Change` (`Written`), `Name`, `ByteCount` and `ExchangeId`, the exchange that made the change. `StoreKind` and `StoreChangedEvent` live in the `Surl.Protocol.Abstractions` namespace, not `Surl.Api`, so the program needs both `using` lines.

Order does not matter. In the `late` mode the upload finishes before the wait begins, and the wait still returns the event, because it looks through the events already kept before it waits for new ones. A test can start the code under test and then wait, with no race between the two.

With the event in hand the test reads what landed with `server.Files.ReadAsync("/report.csv")`, no client of its own. The `SurlFileContents` it returns has the `ContentType`, `text/csv` here, the `ByteCount` and the `Bytes`.

A refused upload changes nothing, so the wait has nothing to find. With no login the `PUT` is answered `401 Unauthorized` <<rfc9110>>; with a Basic login over plain `http://` it is `403 Forbidden`, because `surl` will not check a password sent in clear unless `AllowPlaintextAuthentication` (`--allow-plaintext-auth`) says so. In both modes the program waits one second and the wait throws `TimeoutException`, whose message names the query and the timeout. That is the failure a test wants: the reason is in the message, not in a hang. The program prints the message and exits 1, its own choice.
