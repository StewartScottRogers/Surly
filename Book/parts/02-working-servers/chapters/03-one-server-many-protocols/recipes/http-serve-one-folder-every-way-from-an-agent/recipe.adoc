=== Serving Six Ways from an Agent

==== Problem

You want an artificial intelligence (AI) agent to start one server on six protocols, from the Hypertext Transfer Protocol (HTTP) to WebSocket, fetch the same file over each, and check that the bytes match what the server holds.

==== Solution

Write the agent's side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): one `start_server` call with six listen URLs, one `read_file` for what the store holds, and one `transfer` per bound URL:

==== Discussion

`StdioClientTransport` starts `surl-mcp` and `curl-mcp` by name from `PATH`, and `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine both to the folder the program runs in. The argument after `--` picks the scenario.

`start_server` takes the six listen URLs in one list: HTTP (<<rfc9110>>), the File Transfer Protocol (FTP, <<rfc959>>), the Trivial File Transfer Protocol (TFTP, <<rfc1350>>), Gopher (<<rfc1436>>), the Dictionary Server Protocol (DICT, <<rfc2229>>) and WebSocket (<<rfc6455>>), each on port 0. One server answers them all from one store, which `files` fills with `hello.txt`. The answer{apos}s `bound_urls` gives the real URLs in the order asked, and `log_lines` gives what `surl` printed on start: one `Listening on` line per listen URL, each on its own port.

`read_file` reads the file from the store directly, with no protocol in the way, and is what the fetches are compared with. `transfer` takes a URL of any scheme `curl` knows and answers in text as JavaScript Object Notation (JSON); `body.content` is the text it received. The URL differs only where the protocol does: Gopher puts item type `0` before the path, and DICT looks up the headword `hello.txt` with `d:`. Over HTTP, FTP, TFTP, Gopher and WebSocket, `content` is the same 16 bytes `read_file` returns. Over DICT it is a reply holding them as a definition, lines ended in carriage return and line feed, among the protocol{apos}s status lines, so the agent checks it holds the text rather than equals it.

`statusCode` means something different on each. It is the HTTP status `200`, the FTP reply `226` that ends the transfer, `101` for the WebSocket upgrade, and `0` for TFTP, Gopher and DICT. An agent that judges a fetch by `statusCode == 200` gets five of the six wrong; it should judge by `failure`, which is null for all six.

`--allow-anonymous`, passed in `arguments`, is for FTP alone. `transfer` has no login field, so it logs in to FTP as `anonymous`, and `surl` refuses that login unless told otherwise. The loosening is visible: `log_lines` starts with `surl`{apos}s warning that every login is accepted. Started without it, the FTP fetch is refused with reply `530`, `curl` exit code `67` `LoginDenied`, and the call is a tool error.
