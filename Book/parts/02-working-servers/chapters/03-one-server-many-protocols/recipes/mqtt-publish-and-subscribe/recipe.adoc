=== Publishing and Subscribing over MQTT

==== Problem

A test needs a local MQTT broker to publish a message to and read it back from, with `curl` and nothing else installed.

==== Solution

Start `surl` on an `mqtt` listen URL that accepts anonymous clients and keeps the last message published under `home/`, publish with `curl -d`, and subscribe to the same topic with a plain `curl` of its URL:

==== Discussion

MQTT, once MQ Telemetry Transport, is a publish-and-subscribe protocol: a client connects to a broker, publishes a message to a topic such as `home/kitchen/temp`, and every client subscribed to a matching topic filter receives it (<<mqtt311>>). `surl` on an `mqtt` listen URL is an MQTT 3.1.1 broker, and in one `surl` it is the shared message bus that the extended messaging servers, such as NATS and STOMP, publish to and read from as well (<<surl-readme>>). In the URL `curl` takes, the path is the topic. With `-d 71`, `curl` connects, publishes `71` to the topic and disconnects; without `-d`, it subscribes to the topic and writes what it receives to standard output (<<curl-readme>>). `--next` lets one `curl` command do both, one after the other, with the options of the first transfer reset for the second.

What it writes is not the bare message. For each message `curl` writes the topic's length in two bytes, high byte first, then the topic, then the message: `home/kitchen/temp` is 17 bytes, so the output starts with the bytes `0x00` and `0x11` before `home/kitchen/temp71`. A program reading the output skips the length and the topic to get the message.

A subscribe from `curl` cannot wait for a message that has not been published yet, and `surl` does not make it try: it sends the subscriber the retained message of each matching topic, then ends the connection, and `curl` exits `0`. A topic with no retained message gives no output and exit `0`. A retained message is MQTT's way of leaving a message on a topic for subscribers that come later: a publish with its RETAIN flag set is kept as the topic's retained message (<<mqtt311>>). `curl` never sets the flag, and a broker must not keep a publish without it, so on a broker left as it is, the fourth server, `bare`, a `curl` publish reaches only subscribers already connected and a `curl` subscribe after it receives nothing.

`--topic "home/#;retain"` is what makes the Solution work. It declares the topic filter `home/#` with the flag `retain`, and `surl` keeps every publish on a matching topic as its retained message, whatever the publisher's flag said; that is the broker's choice, made by whoever starts it (<<surl-readme>>). So publish first and subscribe second, as the Solution does. The latest publish replaces the one before, and an empty one, `-d ""`, clears the topic. A topic outside the filter, such as `garden/temp`, keeps nothing. Retained messages are held in memory unless `--directory` names a folder (<<surl-readme>>).

A topic filter may name many topics: a plus sign matches one level and a hash sign, last in the filter, every level below. In a URL they are written `%2B` and `%23`, since both signs mean other things there; `home/%2B/temp` receives `home/kitchen/temp`'s message, written under its own topic name, and so does `home/%23`. A URL with no topic is refused by `curl` itself, exit `3`, before it connects.

`--allow-anonymous` is in the Solution because every MQTT `CONNECT` needs a login, and `curl` sends none unless given `-u`. Without the option, a `CONNECT` with no user name is answered `CONNACK` return code `5`, not authorized; `curl` reports `Expected 0000 but got 0005` and exits `8`, a reply it could not use. A broker that takes anonymous clients lets anyone who can reach it read and write every topic, so it is not the default; `--allow-anonymous` accepts every `CONNECT` unchecked and makes `surl` write a `surl: warning:` line on start (<<surl-readme>>). Use it only on a machine nobody else can reach.

The way in without it is an account, `--user alice:s3cret`, and `curl -u alice:s3cret`. But `mqtt://` has no encryption, so the password crosses the network in clear, and `surl` refuses it unchecked with `CONNACK` `5`, the right password included. `--allow-plaintext-auth` loosens that for a test: the password is then checked, the right one is accepted for the publish and the subscribe alike, and a wrong one is answered `CONNACK` `4`, bad user name or password, and `curl` exits `8`. It too warns on start. The secure way is `mqtts://`, the same broker over Transport Layer Security (TLS), which needs a certificate (<<surl-readme>>).

In the checked claims, `-s` silences `curl`'s progress meter and error messages, and `-S` puts the error message back, so the `CONNACK` code shows on standard error.
