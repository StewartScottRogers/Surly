=== Listening on Several URLs at Once

==== Problem

A test needs the same files served over Hypertext Transfer Protocol on more than one address or port at once, from one server process rather than several.

==== Solution

Stop `surl` with kbd:[Ctrl+C], which stops every listener.

==== Discussion

Where `curl` takes the URLs it fetches, `surl` takes the URLs it listens on, and several of them mean several listeners in one process (<<surl-readme>>). Each binds its own host and port, `surl` writes one `Listening on` line for each, in command-line order, and each answers Hypertext Transfer Protocol (HTTP) requests on its own. Here two ports on `127.0.0.1` and one on `localhost` all serve `hello.txt`.

`--directory site` applies to the whole process, not to one listen URL, so all three listeners serve the same directory: the same file from each, and `404 Not Found` from each for a path that is not there. That is also why they belong in one process. One `surl` holds a directory at a time, and a second `surl` given the same `--directory` is refused, `Directory site is in use by another surl process`, exit `124`, before it listens.

Listening is all or nothing. If any listen URL cannot bind, because another process holds its port, `surl` writes `surl: (45) Could not bind` with that URL and exits `45`, and the listen URLs that could have bound are not left serving: `curl` cannot connect to them, exit `7`. A script that starts `surl` sees exit `45` and no listener, never half a server.

On the `curl` side, `--next` starts another transfer in the same command, so one `curl` fetches from all three listeners in turn; each transfer's output follows the last on standard output (<<curl-readme>>). In the checked claims, `-s` silences the progress meter, `-o` throws the body away and `-w "%{http_code}"` prints the status code.
