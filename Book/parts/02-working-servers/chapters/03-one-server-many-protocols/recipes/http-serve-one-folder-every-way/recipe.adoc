=== Serving One Folder Every Way

==== Problem

You have clients that fetch the same file over different protocols, and you want one `surl` and one folder to serve it over six of them at once, from the Hypertext Transfer Protocol (HTTP) to WebSocket.

==== Discussion

The six protocols are HTTP (<<rfc9110>>), the File Transfer Protocol (FTP, <<rfc959>>), the Trivial File Transfer Protocol (TFTP, <<rfc1350>>), Gopher (<<rfc1436>>), the Dictionary Server Protocol (DICT, <<rfc2229>>) and WebSocket (<<rfc6455>>). Each listen URL starts one of them, and every one of them reads the one store `--directory site` names. Five run over the Transmission Control Protocol (TCP), so each needs its own port. TFTP runs over the User Datagram Protocol (UDP), whose port numbers are separate from TCP{apos}s, so `tftp://127.0.0.1:8080/` shares its number with the HTTP listener.

`curl` fetches every URL on its command line in turn, each with its own scheme, and `-s` keeps its progress meter quiet. The URLs differ only where the protocols do. Gopher puts an item type before the path, `0` for a file, which `curl` does not send. DICT looks words up rather than paths: each file directly in the folder is a headword, so `d:hello.txt` asks for the definition of `hello.txt`. The others name the path as it is.

Five of the six return the file{apos}s bytes alone. Saved with one `-o` per URL, the HTTP, FTP, TFTP, Gopher and WebSocket copies are the served file byte for byte; `-w "%{url.scheme} %{size_download}\n"` counts 16 bytes for each of the first four. A WebSocket file arrives as one message, and `curl` writes the message, not the frame around it. DICT is the exception: its reply wraps the file in the protocol{apos}s own status lines, a greeting, `151` before the definition and `250 ok` after it, so it is longer and not byte for byte. The number in the greeting, `<10@surl>` here, counts the server{apos}s connections.

All six read the folder as it is, not a copy taken at start: a file added to `site` while `surl` runs is served over each of the five at once.

`--allow-anonymous` is there for FTP alone. `curl` logs in to FTP as `anonymous` when a URL has no user, and `surl` refuses that login unless told otherwise, because with no account there is nothing to check. Without the option the FTP fetch is refused, exit `67`, while the same server{apos}s HTTP still serves the file. It is a loosening, the only one here; on a server with accounts, give FTP a user instead (see <<ftp-list-and-upload>>).
