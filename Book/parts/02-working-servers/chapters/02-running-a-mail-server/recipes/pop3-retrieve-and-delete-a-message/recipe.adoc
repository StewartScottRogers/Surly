==== Discussion

Post Office Protocol version 3 (POP3) reads a single maildrop: list it, retrieve a message by its number, delete it (<<rfc1939>>). Here `surl` runs three servers over one mail store: Simple Mail Transfer Protocol (SMTP) on `8080` to deliver into it, POP3 on `8081` to read it, and Internet Message Access Protocol (IMAP) on `8082` to show that a deletion is seen by every protocol (<<surl-readme>>). The message goes in with `--mail-from`, `--mail-rcpt` and `-T`, `--crlf` turning each line ending into the carriage return and line feed a message is made of (<<rfc5321>>).

The URL chooses the POP3 command. `pop3://127.0.0.1:8081/` with no message number lists the maildrop (`LIST`), one line per message: its number and its size in octets. `pop3://127.0.0.1:8081/1` retrieves message 1 (`RETR 1`), which `-o lunch.eml` writes to a file instead of standard output. `-X` sends any other command in place of `LIST`: `-X "DELE 1"` marks message 1 deleted, `-X UIDL` lists each message's unique id, and `-X RSET` unmarks every message marked in the session. `--next` starts another transfer in the same `curl`, with options of its own; the POP3 transfers after it reuse one connection, so the retrieval and the deletion are one POP3 session (<<curl-readme>>). After the Solution, message 1 is gone.

That matters because `DELE` only marks a message. Within the session the marked message is left out of the list and every other message keeps its number; the server removes the marked messages when the session ends with `QUIT`, and `RSET` before then undoes the marks (<<rfc1939>>). The checked claims deliver two more messages and do exactly that: after `DELE 1` the list shows only message `2`, and after `RSET` the next session still has both. `DELE 1` in a session of its own then deletes message 1 for good. Once a deletion is committed, the numbers close up: in the next session the invoice that was message 2 is message 1. A message number is good for one session only; the unique id from `UIDL` is what a client keeps to recognise a message it has already downloaded (<<rfc1939>>).

All three listeners share one store, so a message deleted over POP3 is gone for IMAP too: a search of `INBOX` for its subject finds nothing (<<imap-search-a-mailbox>>).

`--allow-anonymous` lets every command through without a login, and puts every recipient's mail in one anonymous maildrop. Without it, `surl` answers a maildrop command with no login `-ERR [AUTH]`, because a mail server that hands out mail to anyone is not one to run by default; <<smtp-send-and-read-it-over-imap>> checks that refusal and says why the option is for tests only. `surl` writes a `surl: warning:` line when it starts with the option on (<<surl-readme>>).

A message number that is not in the maildrop is answered `-ERR`, whether retrieved or deleted, and `curl` exits `8`, the code it gives for a POP3 reply it did not expect; with `-v` the reply is on standard error (`-ERR No such message`). Exit `0` means every transfer on the command line succeeded.
