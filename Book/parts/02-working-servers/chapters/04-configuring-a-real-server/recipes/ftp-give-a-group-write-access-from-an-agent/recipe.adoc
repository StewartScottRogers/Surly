=== Granting Group Write Access from an Agent

==== Problem

A File Transfer Protocol (FTP) share grants write to one group and read to another, and you want an artificial intelligence (AI) agent to try each account against it and draw up who may read and who may write.

==== Solution

Write the agent{apos}s side as a C# program on the Model Context Protocol (MCP) software development kit (SDK). It starts `surl-mcp` with the groups, the share and the grants, then tries a read and a write as each account, and as no account, through `curl-mcp`{apos}s `curl` tool, and prints the table:

==== Discussion

`start_server` starts a server that answers as `surl` with the same options would (<<surl-readme>>). `listen_urls` holds an FTP and a Hypertext Transfer Protocol (HTTP) URL on port 0, and the answer{apos}s `bound_urls` gives them back with the ports chosen. `arguments` holds `surl`{apos}s own options: four accounts with `--user`; `--group editors=ed,erin` and `--group readers=rita`, which leave Gus in neither; `--share team=team`, which serves the folder `team` under the folder `SURL_MCP_ROOT` names as `/team/`; and `--share-access team=@editors:rw,@readers:r`, which grants the editors read and write and the readers read, a member written with `@` being a group. `--allow-uploads` is still needed, since a grant of `rw` allows a write the server already permits and does not turn writes on. FTP sends the password in clear, and `--allow-plaintext-auth` lets the server check it rather than refuse it unread; it is for a test on your own machine.

The `curl` tool runs `curl`{apos}s own arguments, confined to the folder `CURL_MCP_ROOT` names, and answers JSON text with `exitCode`, `standardOutput` and `standardError`. A read is a download of `plan.txt`; a write is `-T probe.txt`, an upload to a name of the caller{apos}s own. `-u` logs in, and the caller with no account sends none. `-o out.txt` keeps the file out of the answer, `-w "%{response_code}"` puts the reply code in `standardOutput`, and `-s` and `-S` keep the progress meter out and an error in. The agent counts a try as allowed when `curl` exits `0` and, over HTTP, the code is a `2xx`, and otherwise writes down what refused it.

Over FTP the table is the grants: Ed and Erin, the editors, read and write; Rita reads, and her upload is refused `550`, `curl` exit `25`. Gus logs in, but to an account the grant does not name the share is missing, not refused: the server will not change to the folder, exit `9`. With no account the login itself is refused `530`, exit `67` (<<rfc959>>). Over HTTP the same grants give the same table in HTTP{apos}s words (<<rfc9110>>): Rita{apos}s `PUT` is `403 Forbidden`, Gus{apos}s read is `404 Not Found` and his write `409 Conflict`, as for a folder that does not exist, and with no account the server asks for a login, `401 Unauthorized`.

To show a caller with no account finding the share missing, the anonymous case starts the server with `--allow-anonymous`, which lets every caller in, and that caller gets exit `9` over FTP. `--allow-anonymous` accepts every login without checking it, and a login it accepts counts as anonymous, so Ed{apos}s login finds the share missing as well: an agent that checks grants keeps the option off. That server shares the folder with `readonly`, which refuses every write whatever the grant says. A grant that names `editors` without its `@` is looked up as an account: `start_server` is a tool error whose text is `surl`{apos}s message naming the member, and no server starts.
