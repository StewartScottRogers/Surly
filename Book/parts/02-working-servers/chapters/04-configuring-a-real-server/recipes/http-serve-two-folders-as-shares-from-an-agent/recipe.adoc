=== Serving Two Shares from an Agent

==== Problem

You want an agent to serve two folders over Hypertext Transfer Protocol (HTTP) as shares, one readonly, to confirm which one accepts uploads, and to find out what a second server on the same folders does.

==== Discussion

`start_server` starts a server and answers its `bound_urls`. Its `listen_urls` of `http://127.0.0.1:0` takes a free port, and `arguments` are `surl`{apos}s own words: `--share`, `docs=docs;readonly`, a second `--share` for `data=data`, and `--allow-uploads` and `--allow-anonymous`. Folders are named relative to the folder `surl-mcp` is confined to, `SURL_MCP_ROOT`; `curl-mcp` is confined to the same folder, so `-T up.txt` finds the file the program wrote there.

The `curl` tool runs `curl`{apos}s own arguments and answers JSON, with the output in `standardOutput`. An upload into the readonly share, with `-w "%{http_code}"` to print the status, is `403`, although uploads are on, and no file appears; the same upload into `/data/` is `201` and the file is in the folder. `-s` keeps `curl` quiet and `-o up.out` writes the reply body to a file in the folder, so the output is only the status code (<<curl-readme>>). The program reads the folder on disk itself, which an agent can do because the folder is its own.

`surl` keeps a lock on a folder it may write to. A second `start_server` on the writable folder is a tool error, with the text `surl: (124) Directory data is in use by another surl process`: the same message and exit code `124` the console gives. A second `start_server` on the readonly folder is answered like any other and serves the same file, since a readonly share takes no lock. An agent that gets the error should not retry; the first server holds the folder until it is stopped.
