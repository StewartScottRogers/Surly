=== Giving a Group Write Access

==== Problem

You want a File Transfer Protocol (FTP) share that the editors group may write and the readers group may only read, set up with `--group` and `--share-access`, and you want to see that a caller with no account finds the share missing.

==== Solution

==== Discussion

Each `--user` is an account. `--group editors=ed,erin` names a group of two of them and `--group readers=rita` a group of one; Gus is in neither (<<surl-readme>>). `--share team=team` serves the folder `team` on disk as the top-level folder `/team/`; the folder must exist, since `surl` creates none. `--share-access "team=@editors:rw,@readers:r"` says who may use it: a member written with `@` is a group, `rw` reads, lists and uploads, and `r` only reads and lists. The quotes keep the comma list in one argument. Written without the `@`, `editors` is taken for an account name, and `surl` stops at start with exit `2`, naming the member.

With `-u`, `curl` logs in with a user name and password. Ed uploads `draft.txt` with `-T`, and the file lands in the folder on disk. Erin, the group{apos}s other member, uploads as well: the grant follows the group, so adding someone to `editors` is a change to one `--group`. Rita reads `plan.txt` and lists the share with `-l`, and sees both uploads, but her own upload is refused `550` and `curl` exits `25`, as an upload is when `--allow-uploads` is off. `--allow-uploads` is still needed for the editors: `rw` grants a write that the server already permits, it does not turn writes on, and a `readonly` share refuses every write whatever the grant says (<<surl-readme>>).

The grants belong to the share, not to the FTP listener, so the Hypertext Transfer Protocol (HTTP) listener of the same `surl` applies them as well. Rita reads the file over HTTP, `200`, and her `PUT` of a file is answered `403 Forbidden` (<<rfc9110>>).

A share with a `--share-access` is closed to every account it does not name, and the closed share is not refused but missing. Gus logs in, but the server will not change to `/team`, so `curl` exits `9`, and a listing of the root, which names the share for Rita, names nothing for Gus. On `main` a caller with no account gets no further than the login: `530`, `curl` exit `67` (<<rfc959>>).

The `open` server adds `--allow-anonymous`, so a caller with no login is let in, and to that caller the share is missing as well: exit `9` over FTP and `404 Not Found` over HTTP. `--allow-anonymous` accepts every login without checking it, Ed{apos}s included, and a login it accepts counts as anonymous, so on `open` the share is missing to Ed too. Grants by account and `--allow-anonymous` do not mix: a test that needs both the grants and an anonymous caller gets the anonymous caller from a second server, as here. `surl` warns at every start while `--allow-anonymous` is on.

FTP sends the password in clear, so `surl` refuses one over plain `ftp://` without checking it, `530`, exit `67`, as the `strict` server shows. `--allow-plaintext-auth` lets it be checked; it is for a test on your own machine, and `surl` warns at start while it is on. `open` and `strict` share the same folder with `readonly`, which takes no lock on it, so they can run beside `main`, which holds the lock on a writable share. `--list-directories` lets the FTP server answer `-l`. In the checked claims, `-s` silences the progress meter, `-S` keeps error messages, and `-o` with `-w "%{http_code}"` prints only the HTTP status (<<curl-readme>>).
