=== Publishing a Retained Message from an Agent

==== Problem

Your artificial intelligence (AI) agent is testing a device client that subscribes to a Message Queuing Telemetry Transport (MQTT) topic, and it needs a reading already waiting on that topic when the client connects.

==== Solution

A C# program on the Model Context Protocol (MCP) software development kit (SDK) starts `surl-mcp`, starts a broker with `start_server`, calls `publish_message` with the topic, the payload and `retain` true, and checks the result with `read_retained_message`:

==== Discussion

The program starts `surl-mcp`, the MCP server for `surl`, and `curl-mcp`, the one for `curl`, by name from the path, over standard input and output, each confined to the program's folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. The argument picks the scenario. `start_server` starts an MQTT broker on a free port; the program keeps its `server_id` and its `bound_urls` entry in two variables. `surl-mcp` answers in structured content, which the program prints as JSON; `curl-mcp` answers in text that is JSON, which the program parses.

`publish_message` publishes on the server's message bus as a client would, without being one. `topic` names the topic, `sensors/1`, and `payload` is the message as UTF-8 text. `retain` true asks the broker to keep it as the topic's retained message, the one a subscriber is sent the moment it subscribes (<<mqtt311>>). The answer is `published` true.

`read_retained_message` takes the `topic` and answers what the broker kept: the `topic`, the quality of service (QoS) it is kept at, `qos` 0, and the payload as `text`. Without `retain` the message is published but not kept: `read_retained_message` answers `retained` false, which is an answer, not a tool error. A retained publish with an empty `payload` clears what the topic kept, as <<mqtt311>> says it should, and the answer is `retained` false again. A topic with a wildcard, `+` or `#`, can be subscribed to but not published to (<<mqtt311>>), and `publish_message` refuses `sensors/+` with `InvalidTopic`.

The tool is the test's hand on the bus, and it needs no login; a client does. The `curl` tool, from `curl-mcp`, subscribes when given an `mqtt:` URL whose path is the topic, and `-s` keeps the progress meter out of the answer. On this server it connects without a login, the broker refuses the connection, and `curl` exits `8`, a reply it could not use, having read nothing. A broker started with `surl`'s `--allow-anonymous`, passed in `start_server`'s `arguments`, accepts a client with no login, and says so in a warning, the first of the answer's `log_lines`. There the subscription reads the retained message and prints it as MQTT carries it: the topic's length in two bytes, 0 and 9, then the topic, `sensors/1`, then the payload, `21.5`. `curl` exits `0`.

A client's publish is held to the same rule as the tool's. `-d 22.0` makes `curl` publish to the topic instead of subscribing, without the RETAIN flag, and the broker takes it, `curl` exiting `0`, but does not keep it: `read_retained_message` answers `retained` false for `sensors/3`.
