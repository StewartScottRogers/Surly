=== Waiting for an Upload from an Agent

==== Problem

Your artificial intelligence (AI) agent has set a client off to upload a report to a stand-in Hypertext Transfer Protocol (HTTP) server, and it needs to know when the file has arrived without polling the folder.

==== Solution

==== Discussion

The program starts `surl-mcp`, the MCP server for `surl`, and `curl-mcp`, the one for `curl`, by name from the path, over standard input and output, each confined to the program's folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. The argument picks the scenario. `start_server` passes `surl`{apos}s own options in `arguments`: `--allow-uploads` lets a client write into the served files, and `--user alice:secret` is the account it logs in with. `files` gives it an `uploads` folder to write into, holding `README.txt`. The program keeps the `server_id` and the `bound_urls` entry in two variables.

The client here is the `curl` tool, from `curl-mcp`. `-T report.txt` uploads the file with a `PUT` to `uploads/report.txt`, `-u alice:secret` with `--digest` logs in as alice by Digest authentication, `-s` keeps it quiet, and `-w "%{http_code}"` prints the status, `201 Created` (<<rfc9110>>). Without `--digest`, `curl` sends the password itself, by Basic authentication, and this server refuses it with `403 Forbidden`; <<http-refuse-a-password-in-clear>> says why and which option loosens it.

The server keeps a numbered record of events. `wait_for_event` answers the first one that matches its filters, as `event`, or waits up to `timeout_ms` milliseconds for one to happen and then answers `timed_out` true. A matching event kept before the call is answered too, as in the solution, so an agent can start the client first and wait second without missing the upload; sent before the upload, the same wait answers the same change when it happens. `store` `content` keeps only changes to the files, and `name` `/uploads` only changes at that path or under it. The event is a `store_changed`: `change` `written`, the `name` of the file, its `byte_count`, 10, and the `exchange_id` of the connection that wrote it. The program prints an event's fields as `name=value`, leaving out those that differ from run to run: its sequence number, its time, the client's address and the byte counts. `name` matches whole path segments, so `/upload` matches nothing here; that wait, like one for `/reports`, where nothing happened, answers `timed_out` true after its 200 milliseconds. `timeout_ms` must be 1 to 60000, and anything else is a tool error.

`kinds` filters by kind of event instead. With `login_judged` it answers the login the upload made: `account` alice, `mechanism` `Digest`, `is_accepted` true, in the same exchange.

`get_events` takes the same filters and answers the record rather than waiting for it, oldest first, in `events`: here `exchange_started`, with the `listen_url` and `scheme` the client came through (the program prints `url` when it is the server's own), then the login, the write and `exchange_ended`. `has_more` false says that is all of them. `max_events` caps one answer; with 1 it answers only `exchange_started`, and `has_more` true says to ask again.
