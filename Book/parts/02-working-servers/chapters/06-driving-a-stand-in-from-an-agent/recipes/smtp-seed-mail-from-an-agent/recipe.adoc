=== Seeding Mail from an Agent

==== Problem

Your artificial intelligence (AI) agent is testing a mail client, and it needs a message already waiting in a mailbox on a stand-in server before the client logs in to read it.

==== Solution

A C# program on the Model Context Protocol (MCP) software development kit (SDK) starts a server with a Simple Mail Transfer Protocol (SMTP) and an Internet Message Access Protocol (IMAP) listener and an account through `surl-mcp`, calls `seed_mail` with the recipient and the message, and lets `curl`, through `curl-mcp`, read it over IMAP:

==== Discussion

The program starts `surl-mcp`, the MCP server for `surl`, and `curl-mcp`, the one for `curl`, by name from the path, over standard input and output, each confined to the program's folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. The argument picks the scenario. `start_server` takes `listen_urls`, two listeners on free ports, one SMTP and one IMAP, sharing one mail store; `bound_urls` lists them in the same order, and the program keeps them, with the `server_id`, in variables. `arguments` passes `surl`'s own `--user alice:secret`, the account that owns the mailbox.

`seed_mail` delivers into that store as SMTP would, without a client and without a login. `to` is the recipient's address, `alice@example.com`, and `message` the whole message as UTF-8 text, headers first, lines ending in carriage return and line feed as <<rfc5322>> requires. The answer is `delivered` true. An address no account owns is a tool error, `NoSuchAccount`.

The `curl` tool, from `curl-mcp`, then plays the client. `-u alice:secret` logs in and the URL `INBOX;UID=1` names the first message by its unique identifier (UID) (<<rfc9051>>); `-s` keeps the progress meter out of the answer. `curl-mcp` answers in text that is JSON; the program parses it and prints `curl`'s exit code and its `standardOutput` as a JSON string, so the carriage returns show. It is the message seeded, byte for byte.

The agent can read the store without a client too, and without disturbing it. `list_messages` takes the `owner` and `mailbox`, and `after_uid` to skip the messages up to that UID, and answers each message's `uid`, `size` and `flags`; it shows that the IMAP fetch set `\Seen` on UID 1. `read_message` takes the same two and a `uid` and answers the message's exact `text`, but sets no flag: after it reads a second seeded message, `list_mailboxes`, which takes the `owner`, still counts that message as unseen, two messages and one `unseen_count`.

`seed_mail` is not a loophole for clients. A client sending to the SMTP listener with `--mail-from` and `--mail-rcpt`, the envelope's sender and recipient (<<rfc5321>>), and `-T note.eml`, the message from a file, is refused at `MAIL` with `530` until it logs in. `curl` exits `55`, and `-S` puts its message, `MAIL failed: 530`, in the answer's `standardError`. The same command with `-u alice:secret` exits `0`, and `list_messages` with `after_uid` 1 finds the message after the seeded one, as UID 2.
