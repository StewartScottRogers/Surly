=== Downloading in Parallel Segments from an Agent

==== Problem

Your client fetches large files as several byte ranges at once. You want an artificial intelligence (AI) agent, driving `surl-mcp` and `curl-mcp`, to fetch a file in ranges, join it byte for byte, and show the ranges the server received.

==== Solution

Write the agent{apos}s side as a C# program on the official Model Context Protocol (MCP) software development kit (SDK): it seeds a file with `start_server`, sends four `transfer` calls at once with a `Range` header each, joins the bodies in order, compares digests, and reads the ranges back with `get_exchanges`:

==== Discussion

`StdioClientTransport` starts each host by name from `PATH`, and `SURL_MCP_ROOT` and `CURL_MCP_ROOT` confine both to the folder the program runs in. The argument after `--` picks the scenario.

`start_server` takes the file in `files_base64`, 400,000 bytes from a `Random` with a fixed seed, so the program knows exactly what the server holds. The `transfer` tool has no range field; a range is a header, `Range: bytes=first-last`, both ends counted (<<rfc9110>>), in `headers` as a list of `name` and `value` pairs. The program starts all four calls before it awaits any. Each answer is `206 Partial Content` with a `Content-Range` naming the bytes and the whole length, and the bytes come back in `body.content` as base64, `isBase64` true, since random bytes are not text. `isTruncated` false matters: `transfer` returns at most one mebibyte of body, and a truncated part would join to the wrong file. A range that starts past the end is answered `416 Range Not Satisfiable` with `Content-Range: bytes */400000`; to `transfer` that is an answer, with `failure` null, not a tool error, so an agent has to read `statusCode` itself.

The parts are joined in range order, never in the order the calls answered, and the program compares SHA-256 digests of the result and the original. The `curl` tool does the same job as one command line: four transfers separated by `--next`, each with `-r`, `-o segmentN`, `-s` and `-f`, run side by side with `--parallel` and `--parallel-immediate` (<<curl-manual>>). The files land inside `CURL_MCP_ROOT`, where the program reads them back and joins them.

`get_exchanges` is the server{apos}s side: every chunk with `direction` `received` is a request head, and the four `Range` lines in them are the four the agent asked for. That the calls really ran side by side shows in `get_events`. Against a server started with `--fault "delay;stage=command;ms=1000"` in `arguments`, which holds every request a second, the `exchange_started` and `exchange_ended` events, in `sequence` order, show four connections open at once (<<surl-readme>>). Without the hold, how many overlap depends on timing, and the program does not claim a number.
