=== Making a Server Fail on Purpose

==== Problem

You want a Hypertext Transfer Protocol (HTTP) server that fails when you tell it to, answering an error, stalling, hanging up or refusing a login, so you can test how your client copes with each.

==== Discussion

`--fault` takes a kind, then keys that scope it, each after a semicolon. `error;scheme=http;reply=503 Service Unavailable;times=1` answers a request on an `http` listener with the status in `reply` instead of what it asked for: `hello.txt` is in `site`, served by `--directory site`, and the request still gets `503` (<<rfc9110>>), with a short text body that repeats the status line. `times=1` spends the rule after one use, so the next request is served. Without `times` a rule applies every time. An `error` rule needs `scheme` or `listener`, and its `reply` must be an HTTP error status, 400 to 599: `reply=200 OK` is refused at start, as is a kind `surl` does not know, both with exit code `2` and a `surl: option --fault:` line naming the problem.

The point is the client's side. With `--retry 1`, `curl` counts a `503` as a transient error and tries once more (<<curl-manual>>); against the second server, `flaky`, whose same rule answers the first request `503`, it gets the file on the second try, and `-w "%{num_retries}\n"` prints `1`. Standard output cannot be taken back, so the first answer{apos}s body, `503 Service Unavailable`, is there before the file. `-s` keeps `curl` quiet and `-o` sends a body nowhere.

`flaky` has three rules. They are tried in the order given and the first that matches applies, so a rule scoped by `path` comes before a broad one. `delay;stage=command;path=/slow.txt;ms=2000` holds each request for `/slow.txt` two seconds and then answers it, `200`; `-w "%{time_total}"` shows the wait. With `-m 1`, `curl` gives up after one second and exits `28`, a timeout. `drop;stage=command;path=/gone.txt` cuts the connection when that request arrives, with nothing written, and `curl` exits `56`, a failure to receive. A `delay` or `drop` acts as the connection is accepted, before any request, unless `stage=command` makes it wait for the request; only then is there a path to look at, so `drop;path=/gone.txt` without it is refused at start.

The third server, `accounts`, has two rules about who and where. `--allow-uploads` and two accounts, `--user alice:s3cret --user bob:s3cret`, make uploads possible, and `--digest` with `-u` and a user name and password logs in with HTTP Digest. `refuse-login;account=bob` refuses Bob's right password as if it were wrong, `401 Unauthorized`, while Alice logs in. `out-of-space;path=/uploads` makes the store refuse an upload under `/uploads` as if it had no room, `413 Content Too Large`, the answer to an upload past the size limit (see <<http-limit-upload-size>>), while `-T`, which uploads a file, puts the same one elsewhere, `201 Created`.

`--fault` is an option for tests: a server with a rule misbehaves for every client that matches it, which is why there is none unless given. A rule can also take `listener`, `command` and `after-bytes`, and an HTTP `error` rule `body`, the text its answer carries in place of the status line, and one server takes at most 256, as `surl --aihelp testing` prints. To add and remove rules while the server runs, see <<http-inject-a-fault-from-an-agent>>.
