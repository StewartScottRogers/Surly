=== Timing Out an Idle Client

==== Problem

You want a Hypertext Transfer Protocol (HTTP) server that closes a connection a client has left open and unused, or kept too long, so you can check that your client notices and connects again.

==== Solution

==== Discussion

`--idle-timeout 1` closes an exchange once no byte has moved on it in either direction for one second. For HTTP an exchange is a connection, and `curl` keeps its connection open after the first fetch so that the next one to the same server can use it. `--rate 1/3s` makes `curl` start at most one transfer every three seconds, so the connection sits idle for three. `surl` closes it after one, and `curl` finds it closed when the second fetch is due and connects again. `-w "%{http_code} %{num_connects}\n"` prints each fetch's status and the number of new connections it made: `1` for both, and both are `200`. `-s` keeps `curl` quiet, and each `-o` sends one body nowhere. `--directory site` serves the folder `site`, and each server has a folder of its own.

The same two fetches against the second server, `plain`, which has the default idle timeout, share one connection: the second makes no new one, `0`. `--idle-timeout` with a short limit is for a test that wants the close to happen while it watches.

`--max-time` limits how long one exchange may last, idle or not, measured from the moment the connection is accepted. The third server, `capped`, has `--max-time 3`. Three fetches two seconds apart keep the connection busy, so the idle timeout never applies, but by four seconds the connection has lived past three and `surl` has closed it: the second fetch reuses the connection and the third makes a new one. `surl`{apos}s `--max-time`, which `-m` also spells, takes the name of `curl`{apos}s client-side option, where it limits how long `curl` waits for a whole transfer (<<curl-manual>>); here it is the server's side of the same idea.

A request still waiting for its answer when `--max-time` runs out gets no answer at all. The fourth server, `stalled`, has `--max-time 1` and `--fault "delay;stage=command;ms=3000"`, which holds every request three seconds before answering (see <<http-inject-a-fault>>). After one second `surl` closes the connection with no bytes, and `curl` exits `52`, an empty reply from the server: no status line ever arrived, so there is nothing in <<rfc9110>> to read.

`--idle-timeout` is different, on purpose: it counts only the silence the client causes. While a `delay` fault holds a request, the idle clock is stopped, so the wait never closes the connection (<<surl-readme>>). The fifth server, `held`, has `--idle-timeout 1` and the same three-second delay, and its request is answered `200`.

Neither limit is a loosening. The defaults are 120 seconds idle and 3600 for one exchange, as `surl --aihelp limits` prints with the idle rule above, and `0` turns either off. A limit reached ends only the connection that reached it; `surl` goes on serving.
