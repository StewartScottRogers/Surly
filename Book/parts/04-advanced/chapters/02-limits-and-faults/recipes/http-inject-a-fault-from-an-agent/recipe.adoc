=== Making a Server Fail from an Agent

==== Problem

Your artificial intelligence (AI) agent tests a client against a stand-in Hypertext Transfer Protocol (HTTP) server and wants the server to fail for one part of the test and behave for the rest, without restarting it.

==== Solution

A C# program on the Model Context Protocol (MCP) software development kit (SDK) starts a server through `surl-mcp`, calls `add_fault` to make it answer `503 Service Unavailable`, fetches through `curl-mcp`, then calls `remove_fault` and fetches again:

==== Discussion

The program starts `surl-mcp`, the MCP server for `surl`, and `curl-mcp`, the one for `curl`, by name from the path, over standard input and output, each confined to the program's folder by `SURL_MCP_ROOT` and `CURL_MCP_ROOT`. The argument picks the scenario, and each run starts a fresh server. `start_server` starts a server on a free port with `hello.txt` in memory; the program keeps its `server_id` and its `bound_urls` entry in two variables. `transfer`, from `curl-mcp`, is the client: it answers in text, which the program parses as JavaScript Object Notation (JSON), and the program prints the status and, for a `200`, the body.

`add_fault` takes the server's ID and one rule, written exactly as `surl`{apos}s `--fault` option takes it (see <<http-inject-a-fault>>), and answers the rule's `fault_id`. IDs are `f1`, `f2` and so on, counted for each server. `error;scheme=http;reply=503 Service Unavailable` answers every HTTP request with that status, so the fetch that follows gets `503` (<<rfc9110>>). `remove_fault` takes the server's ID and the `fault_id` and answers the ID back, and from the next request on the server behaves: `200` and the file. An agent that means to take a rule away again keeps the ID it was given.

`list_faults` answers every rule the server holds: its `fault_id`, its `item` as `surl` spells it, with spaces and slashes percent-encoded, and `remaining`, the uses it has left. A rule with `times=1` applies once and is spent, after which the fetch is `200`, but `list_faults` still lists it, with `remaining` 0, until `remove_fault` takes it away. A rule given to `start_server` in `arguments`, as `--fault` and its item, is listed the same way, as `f1`, with `remaining` null: a rule without `times` has no limit.

A rule can do more than answer an error. `drop;stage=command;path=/hello.txt` cuts the connection when the request arrives, and `transfer` answers no status at all but a `failure` with `curl`{apos}s exit code, `56`, a failure to receive. The other kinds, `delay`, `refuse-login` and `out-of-space`, are the console recipe's.

The server keeps an event each time a rule applies. `get_events` with the server's ID and `kinds` set to `fault_applied` answers them; each names the rule's ID, its kind, the stage it applied at, `command` for a request, and the path, so an agent can check that the failure it planned is the one the client met.

`add_fault` checks a rule as `surl` checks `--fault` at start. `reply=200 OK` is not an HTTP error status, so the call is a tool error with `surl`{apos}s reason, `option --fault: key reply does not fit the http error shape`, and nothing is added: `list_faults` answers no rules. `remove_fault` with an ID the server does not hold is a tool error too, `server s1 has no fault rule f9`. A tool error is `IsError` set on the result with the reason as text, not an exception, so the program goes on to its next call.
