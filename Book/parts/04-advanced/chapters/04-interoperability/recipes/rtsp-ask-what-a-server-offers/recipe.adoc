==== Discussion

RTSP is the control protocol of a media stream: a client describes, sets up, plays and tears down a stream with requests that look like Hypertext Transfer Protocol (HTTP) requests, and the media itself travels separately (<<rfc2326>>). `OPTIONS` is the request that asks a server what it supports; the answer lists the methods in its `Public` header.

The `curl` tool has no option that chooses an RTSP request. It sends one, `+OPTIONS * RTSP/1.0+` with `CSeq: 1`, whatever path the URL names: asking for `rtsp://127.0.0.1:8080/hello.txt` sends the same `+*+`, as `-v` shows. Choosing `DESCRIBE`, `SETUP`, `PLAY` and the rest is for programs that use the library underneath `curl` (<<curl-manual>>, <<surl-readme>>). So from the command line, `OPTIONS` is the question to ask, and it is the right one for checking a server.

`surl` answers `RTSP/1.0 200 OK`, echoes the `CSeq`, and names in `Public` the ten requests it serves: `OPTIONS`, `DESCRIBE`, `ANNOUNCE`, `SETUP`, `PLAY`, `PAUSE`, `TEARDOWN`, `GET_PARAMETER`, `SET_PARAMETER` and `RECORD`. The answer has no body, so `curl` prints nothing without `-i`, which puts the response's status line and headers on standard output. `--directory site` serves the files under `site` as streams to programs that ask for them; `OPTIONS` names no file.

Logins are HTTP's. With no account, `OPTIONS` needs none. The claims run a second `surl` with `--user alice:s3cret`, which adds one account, and no `--directory`, since `OPTIONS` reads no file and two `surl` processes cannot share a data directory. Once there is an account, every request needs a login, `OPTIONS` included: without one, `surl` answers `401 Unauthorized` and offers Digest (<<rfc7616>>) three times, with the algorithms MD5 (Message Digest 5), SHA-256 and SHA-512-256 (two forms of Secure Hash Algorithm 2). `--digest` with `-u alice:s3cret` makes `curl` answer that challenge with a hash of the password instead of the password, and it does so on the connection it already has: `-w "%{http_code} %{num_connects}"` prints `200 1`, the final status and the one connection opened for both requests. With `-f` the same login exits `0` and prints nothing. A wrong password is answered `401` again; `-f` makes `curl` exit `22` on it, where `-S` shows the error that `-s` would hide.

`curl -u` with no method sends Basic, the password itself, and `surl` answers it `403 Forbidden` unchecked, the right password included. `curl` has no `rtsps`, so RTSP always travels in plain text and Basic would put the password on the wire; `--allow-plaintext-auth` is the loosening that would accept it, for a test only (<<surl-readme>>).

In the claims, `-s` hides the progress meter, `-o` throws the body away, and `2>&1` brings `-v`'s trace to standard output.
