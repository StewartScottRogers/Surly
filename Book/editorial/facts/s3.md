# s3 facts
Checked against: surl 1.0.0 (Surl 9ad60d80c), curl (Curl 7d167fa10a), 2026-11-20, windows (Curl.Api PUT re-probed; the rest carried from Surl 763754785 / Curl b9ca725077).

## Listen URLs and readiness
`s3://127.0.0.1:{{port}}/` is TLS from the first byte, TCP, `ready: port`. Needs `--cert`/`--key` (or `--self-signed`): without, exit 58, `surl: (58) s3://127.0.0.1:0/ needs a certificate...`. `--s3-plaintext` serves plain HTTP (warns). Can share a store with an `https://` listener in the same surl.

## Server options that matter
- `--directory store`: each top-level folder a bucket, the path under it the key. One surl holds a folder at a time (a second on the same folder exits 124 `Directory ... is in use`): give each server its own folder.
- `--user AKIAIOSFODNN7EXAMPLE:s3cret`: access key ID and secret. Every request must be SigV4-signed.
- `--allow-uploads`: without it a signed put is 403 AccessDenied; gets still served.
- `--list-directories`: needed for ListObjectsV2 and ListBuckets; without it a signed listing is 403 AccessDenied (same message as unsigned: `AccessDenied: Access Denied`).
- `--allow-anonymous` (loosens, warns): unsigned gets AND unsigned listings (with `--list-directories`) served; an unsigned put is still 403 AccessDenied. A request that carries a login is still judged: unknown key 403 InvalidAccessKeyId, wrong secret 403 SignatureDoesNotMatch.
- `--bucket pics=/gallery`: bucket `pics` is the store path `/gallery` (a content path: leading slash, relative to `--directory`, not a disk path). The folder keeps its own bucket name too; unmapped folders stay buckets; `https` on the same store sees `/gallery/...` and 404s `/pics/...`. A missing folder: exit 37 `surl: (37) Could not open directory /gallery... for bucket pics`. `pics=gallery` (no slash): exit 2 `... is not a content path`. A put into the mapped bucket writes the folder. **Git Bash on Windows rewrites `pics=/x` into a disk path: set `MSYS_NO_PATHCONV=1`** (the verify runner is unaffected).

## Secure by default
Unsigned: 403 AccessDenied. Unknown key: 403 InvalidAccessKeyId. Wrong secret: 403 SignatureDoesNotMatch. Missing key: 404 NoSuchKey. Missing bucket: 404 NoSuchBucket. For each, curl writes nothing, exits 22, stderr `curl: (22) S3 returned error <status>: <Code>: <message>`. Messages: `Access Denied`; `The AWS access key Id you provided does not exist in our records.`; `The request signature we calculated does not match...`.

## Client: curl
- `s3://<bucket>/<key>` takes the bucket as the host and sends to `<bucket>.s3.us-east-1.amazonaws.com:443`; reach surl with `--connect-to ::127.0.0.1:{{port}}` and `--cacert server.pem`. The certificate must name the bucket host: use `DNS:*.s3.us-east-1.amazonaws.com` (Schannel accepts the wildcard) plus `IP:127.0.0.1`.
- `-u KEY:SECRET` signs. No `-u`: unsigned.
- A URL ending in `/` (or the bare bucket) is a ListObjectsV2 with `delimiter=/` and the path as `prefix`; curl prints names one to a line, folders with a trailing `/`, sorted. A query string on the URL is dropped. An empty prefix prints nothing, exit 0.
- `-T file` puts; a URL with no `-T` gets. `--next` runs several transfers with their own options in one command (exit is the last).

## Curl.Api (C#)
- `CurlRequest(HttpMethod.Get, "s3://bucket/key")` with `Network = new CurlNetworkOptions { ConnectTo = [$"::127.0.0.1:{port}"] }`, `Authentication = new CurlAuthenticationOptions { UserName, Password }`, `Tls = new CurlTlsOptions { Origin = new CurlTlsPeerOptions { CertificateAuthorityBlob = File.ReadAllBytes("server.pem") } }`. A throwaway `SelfSigned` cert fails the host check (60) even with `VerifyHost = false`: use an openssl cert from `setup:`.
- A refusal throws `CurlException`, `Code` `HttpReturnedError` (22), `Message` `S3 returned error 403: AccessDenied: Access Denied`. HTTP 404 from an `https://` URL is a response, not an exception.
- PUT: `new CurlRequest(HttpMethod.Put, "s3://pics/up.txt") { Body = CurlContent.FromStream(stream, length) }` with `Authentication` and `ConnectTo` puts the object, 200 (Curl 7d167fa10a, BL-5594: a body on a non-HTTP upload scheme uploads as `-T`). Before that it was `CurlException` 4 `NotBuiltIn`. `server.Files.ReadAsync("/gallery/up.txt")` reads it back as `SurlFileContents` (`Bytes`). A byte `Body` works too. Refusals of a put match the console's: signed, server without `AllowUploads` -> 403 `AccessDenied: Access Denied`; unsigned on an `AllowAnonymous` + `AllowUploads` server -> 403 `AccessDenied` (s3-tell-the-refusals-apart-in-csharp).
- Surl.Api: `ListenUrls = { "s3://127.0.0.1:0" }`, `CertificateFile`/`KeyFile`, `Accounts.Add(new SurlAccount(key, secret))`, `Files["photos/a.txt"]` (in memory), `ListDirectories`, `AllowUploads`, `AllowAnonymous`, `Buckets.Add("pics=/gallery")`; `server.Files.PutAsync("/gallery/x", bytes)` (leading slash required). `DataDirectory = "spare"` with a missing bucket folder: `StartAsync` throws `SurlServerStartException`, `ExitCode` 37, `Lines[0]` `(37) Could not open directory /nowhere for bucket pics`.

## MCP
- `start_server` `arguments`: `--cert server.pem --key server.key --user ... --list-directories --bucket pics=/gallery` ; `files` in memory. A start refusal is a tool error with `exit_code` (37) and the message text.
- curl-mcp `curl` tool (`args`): runs full curl, `-T up.txt` works from `CURL_MCP_ROOT`; answer JSON `exitCode`, `standardOutput.content`, `standardError.content`.
- `get_events` with `kinds: ["login_judged"]`: one event per signed request that named an account (`account`, `is_accepted`); an unsigned request is not judged. Some answers (a missing bucket) do not appear, so assert only the first few.
- `list_files` (`path` `/photos/2026`, answer `entries[].name`), `read_file` (`path` `/gallery/up.txt`, answer `text`).

## Gotchas
- Windows: `-subj "/CN=..."` is mangled by Git Bash for ad hoc probes; use `MSYS_NO_PATHCONV=1`.
- MCP probes outside verify need `surl-mcp` and `curl-mcp` on PATH (verify makes shims).

## Delete, and a signed run (s3-sign-a-run-of-s3-requests and twins, Surl 9ad60d80c / Curl 7d167fa10a, 2026-11-20)
- curl's `s3://` sends DELETE (Curl 0680b97577, DeleteObject): `-u K:S -X DELETE -w "%{http_code}" s3://b/k` is 204, exit 0, also for a key that holds nothing; wrong secret 403, exit 22, `curl: (22) S3 returned error 403: SignatureDoesNotMatch: ...`. Curl.Api `HttpMethod.Delete` on `s3://` the same (204; `CurlException` `HttpReturnedError` for 403). Before that build: exit 4 / `NotBuiltIn`, `s3:// does not support -X DELETE`.
- Delete over https to the bucket host with SigV4: `curl --aws-sigv4 aws:amz:us-east-1:s3 -u KEY:SECRET -X DELETE --connect-to ::127.0.0.1:P --cacert server.pem https://b.s3.us-east-1.amazonaws.com/k` -> 204; a key with no object is 204 too. Curl.Api: `CurlAuthenticationOptions.AwsSigV4 = "aws:amz:us-east-1:s3"`. `GET https://b.s3.../?list-type=2` with the same signing gives the ListObjectsV2 XML. A cert with `DNS:*.s3.us-east-1.amazonaws.com` covers every bucket.
- Over https a refusal is an ordinary 403 whose body is `<Error><Code>SignatureDoesNotMatch|AccessDenied|InvalidAccessKeyId</Code>...<RequestId>random</RequestId></Error>`; curl exit 0 (22 with `-f`). Unsigned DELETE: AccessDenied; signed DELETE without `--allow-uploads`: AccessDenied.
- Wrong secret: put, list (s3://) exit 22 `S3 returned error 403: SignatureDoesNotMatch`; Curl.Api `HttpReturnedError`. Nothing stored.
- `-T f s3://b/k s3://b/` puts then lists in one command; exit is the last transfer's, so a refused put followed by a served listing is exit 0 (seen with uploads off).
- `get_events kinds:["login_judged"]`: a wrong-secret run of put+list, delete, list gave 4 refused, then 4 accepted for the right one; with uploads off, 4 requests gave only 3 accepted events (do not count those).

## Auditing a bucket after a sync (s3-audit-a-bucket-after-a-sync, 2026-11-20)
- One curl-mcp call with several `-T out/x s3://reports/x` pairs and `--cacert server.pem --connect-to ::127.0.0.1:P -u KEY:SECRET` puts them all; a missing local file in the list: exit 26 `curl: (26) Failed to open/read local data from file/application` after the earlier puts, a tool error. surl-mcp `list_files /reports` answers `entries[] {name, kind, byte_count}` for the bucket folder; `put_file`/`delete_file` change it with no login. Signed `curl s3://reports/` lists names one a line; without `--list-directories`: exit 22 `S3 returned error 403: AccessDenied: Access Denied`, while `list_files` still works.

## Plain HTTP (s3-serve-a-plain-http-endpoint and twins, Surl 9ad60d80c / Curl 7d167fa10a, 2026-11-21, windows)
- `--s3-plaintext`: no certificate needed; warns on start `surl: warning: --s3-plaintext: s3 is served as plain HTTP, without TLS` (in `--log-file`, in Surl.Api `Log`, and in surl-mcp `start_server` `log_lines`). Without it and with no cert: exit 58 (`SurlServerStartException.ExitCode` is an enum: cast to int; surl-mcp: tool error with `exit_code` 58).
- curl reaches it over `http://`: `curl --aws-sigv4 aws:amz:us-east-1:s3 -u KEY:SECRET http://127.0.0.1:P/photos/hello.txt` (path style) or `http://photos.s3.us-east-1.amazonaws.com/hello.txt` with `--connect-to ::127.0.0.1:P`. Put: `-T up.txt` the same way. Refusals are 403/404 with an XML `<Code>`; curl exit 0 without `-f` (22 with, message `The requested URL returned error: 403`). curl's own `s3://` against it: exit 35 (`SslConnectError` in Curl.Api).
- Curl.Api over http: `Authentication = { UserName, Password, AwsSigV4 = "aws:amz:us-east-1:s3" }`; a body PUT works; refusals are responses, not exceptions. `SurlServerOptions` has no plaintext property: `AdditionalArguments = { "--s3-plaintext" }`.
- `get_events login_judged` on that server: a put refused for uploads off is still judged (accepted) here; assert the first few only.

## HTTPS and S3 on one store (http-move-uploads-to-s3 + twins, Surl 9ad60d80c / Curl 7d167fa10a, 2026-11-21, windows)
- `surl --directory store --cert .. --key .. --user KEY:SECRET --allow-uploads --list-directories s3://H:P1/ https://H:P2/`: two ports (both TCP). `curl -u KEY:SECRET -T f https://H:P2/b/k` (Basic over TLS) writes `store/b/k`, the same object as `s3://b/k`; each reads the other's uploads byte for byte.
- HTTP PUT: 201 new, 204 replace; S3 put: 200 both times. HTTPS PUT with no login: 401 (exit 0 without -f).
- `-v` log: HTTP `PUT /b/k: 201, N bytes stored at <path>` and `Login accepted: Basic KEY`; an S3 put logs `< PUT /k HTTP/1.1` (no bucket: it is in Host) and `Login accepted: AWS4-HMAC-SHA256 KEY`; since Surl a423807a5d (BL-1554) also `* PUT /k: 200, N bytes stored at <path>` (key only, no bucket; before, no stored line). `LoginJudgedEvent.Scheme` / MCP `scheme`: `https` vs `s3`.
- `--auth aws-sigv4` with both listeners (warns `surl: warning: --auth: accepted methods are aws-sigv4`): Basic PUT over https 403, nothing stored; s3 put 200. Surl.Api `AuthenticationMethods = new List<string> { "aws-sigv4" }`.
- Finding (not claimed): `curl --aws-sigv4 aws:amz:us-east-1:s3 -u K:S https://127.0.0.1:P/b/k` over HTTP/2 (curl's default ALPN) is refused (401 with no `--auth`, 403 with `--auth aws-sigv4`), right or wrong secret; with `--http1.1` it is 200 / PUT 201. Use `--http1.1` for SigV4 over https until fixed.
- Curl.Api: one CurlClient serves both the https:// and the s3:// requests (`ConnectTo` only on the s3 ones). MCP: `list_files /uploads` and `read_file` see uploads from both listeners at once.

- SigV4 over HTTP/2 and HTTP/3 is refused by surl until Surl BL-1547..1549 land (surl did not check `:authority` as `host`; a Surl bug, High). Until then, SigV4 recipes over https use `--http1.1`. S3 and GCS answer HTTP/1.1 only (Surl ADR-0108 decision 5).

## Syncing a folder (s3-sync-a-folder-to-a-bucket and twins, Surl 5da5b3eaf / Curl c84035f797, 2026-11-22, windows)
- `curl -T "site/{a.csv,b.csv,c.csv}" s3://reports/` (quotes keep the shell off the braces) puts each file under its own name, exit 0; with a refusal curl tries every file (two errors for two) and exits 22; a name in the braces that is not a file stops with exit 26 `Failed to open/read local data from file/application` after the earlier files were put. `-T site/c.csv s3://reports/` puts `c.csv`.
- Signed ListObjectsV2 over https (`curl --http1.1 --aws-sigv4 aws:amz:us-east-1:s3 -u K:S --connect-to ::127.0.0.1:P --cacert server.pem "https://reports.s3.us-east-1.amazonaws.com/?list-type=2"`): one line of XML, `<Contents><Key>..</Key><LastModified>..</LastModified><ETag>"<md5 hex of the content>"</ETag><Size>N</Size>..`. Seeded and put objects alike have the MD5 as ETag. Without `--http1.1` this is refused until Surl BL-1547.
- `surl -v --log-file f`: each put logs `#N * PUT /key: 200, BYTES bytes stored at <disk path>` (the path is escaped, `\x5C` for a backslash; claim only the count, `grep -c "bytes stored"`).
- Surl.Api: `RecordExchanges = true` keeps events; `server.FindEvents(new SurlEventQuery { Store = StoreKind.Content })` gives `StoreChangedEvent`s (`using Surl.Protocol.Abstractions`), a put's has an `ExchangeId`, a seeded `Files[...]` one has none. surl-mcp `get_events` `kinds ["store_changed"] store "content"`: `events[]` with `change`, `name`, `byte_count`, `exchange_id` (absent for a seed). Curl.Api: `Http = new CurlHttpOptions { HttpVersion = HttpVersion.Http11 }` (`using Curl.Api.Options.Http`), `AwsSigV4 = "aws:amz:us-east-1:s3"`.

## Multipart upload with curl (surl-repeat-a-failure-with-a-fixed-seed and twins, 2026-11-22, windows)
- Over `--s3-plaintext` with `--aws-sigv4 aws:amz:us-east-1:s3 -u K:S`: `-X POST "http://h:p/b/k?uploads"` answers `<InitiateMultipartUploadResult ...><UploadId>32 hex</UploadId>`; `-T part "...?partNumber=1&uploadId=ID"` 200 with `ETag: "md5"`; `--data-binary @complete.xml "...?uploadId=ID"` with `<CompleteMultipartUpload><Part><PartNumber>1</PartNumber><ETag>"md5"</ETag></Part></CompleteMultipartUpload>` stores the object. `-X DELETE "...?uploadId=ID"` aborts (204); an unknown ID is 404 `NoSuchUpload`. `GET /b?uploads` (ListMultipartUploads) is 501 `NotImplemented`.
- Git Bash turns an argument holding `</ETag>` into a Windows path (MSYS conversion), so the XML goes in a file. Curl.Api: the part answer's `ETag` is in `CurlResponse.Headers`; a byte `Body` on POST completes.
- The UploadId comes from the seedable source: see config.md `--random-seed`.

## Checking an upload from an agent (s3-check-what-an-upload-stored-from-an-agent; Surl 5da5b3eaf / Curl c84035f797, 2026-11-22, windows)
- `--user K:S --s3-plaintext --allow-uploads` and `files {"photos/hello.txt": ...}` (the bucket must exist): `curl -sS --aws-sigv4 aws:amz:us-east-1:s3 -u K:S -T report.csv http://127.0.0.1:P/photos/reports/report.csv` is exit 0 and an empty body. Events on `store:"content"`: `created` `/photos/reports`, then `written` `/photos/reports/report.csv` (`byte_count`), then `metadata_stored`; a REPLACING put's wait can return the earlier put's `metadata_stored` first, so loop until `change == "written"`, moving `after_sequence` on.
- `read_file` answers `{path, byte_count, modified_at, content_type: "text/csv", text}` (`base64` instead of `text` for non-UTF-8, not probed here); a key that was never stored (wrong secret -> body `<Code>SignatureDoesNotMatch</Code>`, uploads off -> `AccessDenied`, both curl exit 0) is a tool error from `read_file`, and `wait_for_event` times out as `{"timed_out":true}` with no `event`. `list_files /photos/reports` -> `entries[{name,kind:"file",byte_count}]`.

## Ranges, multipart over TLS, and the AWS SDK (batch-14: s3-resume-a-ranged-download, s3-upload-a-large-object-in-parts, s3-test-an-aws-sdk-client-locally, and twins; Surl v0.1.5 d64faa4bb / Curl 2145a49eae, 2026-11-24, windows)
- curl's `s3://` ignores `-r` and `-C -`: it sends no `Range` and gets 200 with the whole object (`-r 0-9` gave `200 4000000`). Ranged gets go over `https://<bucket>.s3.us-east-1.amazonaws.com/key` with `--aws-sigv4 aws:amz:us-east-1:s3 -u K:S --connect-to ::127.0.0.1:P --cacert server.pem`: `-r A-B` 206; a start past the end 416 `InvalidRange`. The s3 listener offers http/1.1 only, so no `--http1.1` is needed there. Finding for Curl (batch-14).
- `drop;after-bytes=N` on the s3 listener: over `https://` curl exits 56 (Curl.Api `RecvError`), as on HTTP; curl's `s3://` exits 2 `Unable to read data from the transport connection: An existing connection was forcibly closed by the remote host..` (Windows), a .NET message and the wrong code. Finding for Curl (batch-14). `-C` and `-r` together: `curl: --continue-at is mutually exclusive with --range`, exit 2.
- Multipart over TLS (SigV4 https as above) works as over plaintext. Parts but the last under 5 MiB: every part 200, complete 400 `EntityTooSmall`, upload still open (abort 204). Completed object: HEAD `ETag "<32 hex>-<parts>"`, full Content-Length.
- `--max-filesize` (Surl.Api `MaxFileSize`, long) counts the whole upload across parts: 12M with 5 MiB parts of a 13,000,000-byte file: parts 1-2 200, part 3 400 `EntityTooLarge` and the server drops the upload (abort then 404 `NoSuchUpload`, no temp file left); a single part larger than the limit is 400 but the upload stays (abort 204). A single put over the limit: 400 `EntityTooLarge` (`Your proposed upload exceeds the maximum allowed object size.`). An initiated upload keeps a `.surl-upload-<id>` file in the bucket folder until completed or aborted.
- AWS SDK for .NET (AWSSDK.S3 4.1.2, pinned in build/packages.yml) against `--s3-plaintext` (Surl.Api `AdditionalArguments`): `ServiceURL = http://127.0.0.1:P`, `ForcePathStyle = true`, `AuthenticationRegion = "us-east-1"`, `BasicAWSCredentials`. With the default `RequestChecksumCalculation` a PutObject is sent `X-Amz-Content-SHA256: STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER` + `X-Amz-Trailer: x-amz-checksum-crc32` (aws-chunked) and surl answers 501 `NotImplemented` (`A header you provided implies functionality that is not implemented`); a finding for Surl (batch-14). `RequestChecksumCalculation.WHEN_REQUIRED` sends a plain signed put: 200, ETag the MD5. Get, ListObjectsV2, 404 `NoSuchKey`, 403 `SignatureDoesNotMatch` (`AmazonS3Exception.ErrorCode`) all as S3. TLS with the SDK not probed.

## Signature mismatches (s3-explain-a-signature-mismatch, Surl v0.1.8 9f8005dff / Curl 2145a49eae, 2026-11-25, windows)
- surl-mcp `get_exchanges` of an `s3://` (TLS) exchange holds the request head decrypted: `Authorization: AWS4-HMAC-SHA256 Credential=K/<date>/us-east-1/s3/aws4_request, SignedHeaders=host;x-amz-content-sha256;x-amz-date, Signature=...` for curl `--aws-sigv4 aws:amz:us-east-1:s3` over https. A SigV4 signer in C# (HMACSHA256 chain over date, region, service, aws4_request) reproduces curl's signature from the recorded head.
- 403 `SignatureDoesNotMatch` for a wrong secret and for a canonical path that differs (signed `/photos/hello.txt`, sent `/hello.txt` virtual-hosted). Service `s4` in the scope: `AuthorizationHeaderMalformed`; body hash header wrong: `XAmzContentSHA256Mismatch`; `-H "x-amz-date: <yesterday>"`: `RequestTimeTooSkewed`; a query `?versionId=x&acl`: 501 `NotImplemented`.
- Not claimed (reported): a scope region of `eu-west-1` is accepted (200); the error body has no `CanonicalRequest`/`StringToSign` as AWS's does. Keys with a space or `+` sign and fetch fine with curl's `s3://` and SigV4 https.
- Fixed in Surl fef1d8e (BL-1665, 2026-11-25): the AWS SDK's default checksummed put (STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER, X-Amz-Trailer x-amz-checksum-crc32) is taken, 200, same ETag; s3-test-an-aws-sdk-client-locally no longer sets RequestChecksumCalculation.
